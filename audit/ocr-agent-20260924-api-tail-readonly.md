The product path explains the bounded fix opportunity: `src/ocr_workbench/agent/routes.py:145` calls `grant_selection` after `create_run`; `src/ocr_workbench/agent/selection.py:103` loops through exact per-scope permissions and calls `policy.grant` individually; `src/ocr_workbench/agent/policy.py:33` opens a separate `Store.transaction` for each grant; `src/ocr_workbench/store.py:289` opens a SQLite connection with WAL and `synchronous=FULL` for every transaction. The 23-grant request spends nearly all 325.5 endpoint milliseconds across 36 transaction lifetimes, not SQL execution or lock acquisition. A scoped batching design could validate permissions and snapshot, then insert all exact grants inside one transaction with the existing duplicate checks, scope digests, source, expiry, and run identity preserved. That requires tests for idempotence, rollback on a failed grant, and no partial authorization after a concurrent selection change. It might save part of message endpoint time, but cannot remove the 826 ms pre-service slice or the state tail, and therefore is **not** a demonstrated acceptance fix.

**Decision before the formal track: do not change product code yet.** Keep the frozen candidate, original per-request HTTP transport, 1,000/2,000 ms thresholds, 30-second UI assertion, and original failed/pass receipts. The E 10-second evidence identifies a bounded message-grant optimization candidate but not a fix for the dominant non-endpoint tails. Recheck on the intended medium under the unchanged formal workload (three repeats, four-hour mixed soak), retaining full API/DB spans and paired diagnostics outside the acceptance calculation. If tail failures recur, instrument separately client construction/connect, ASGI admission-to-endpoint, endpoint-to-`server_exit`, and browser event receive/render/receipt; then test the grant batching separately against an unchanged baseline before changing or requalifying the frozen source.
