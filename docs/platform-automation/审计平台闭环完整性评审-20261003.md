以下按阻断现有功能落地的影响排序。P1 表示本轮闭环交付前应解决，P2 表示影响持续使用的完整性问题；不要求引入新平台能力。

1. **P1：当前打包脚本漏掉新增取证组件，并存在整个平台启动失败的路径。**

   `scripts/build_base_candidate.py:472` 开始复制平台源码、契约、Data 模块与门户，但没有复制 `modules/image_forensics`、`config/forensics.json`，也没有归集其运行时。`src/workbench_platform/app.py:52` 在配置数据目录时无条件初始化取证；`src/workbench_platform/forensics/service.py:37` 无条件读取上述配置，第 39 行还读取模块来源清单。按当前构建路径，这不只是“图像工具不可用”，而是可能在应用 startup 阶段使门户整体无法启动。

   独立构造探针已复现缺少该配置时的 `FileNotFoundError`。这属于源码与构造级验证，本次没有执行全量候选构建，不把探针写成正式包启动结果。另一个独立运行缺口是现有配置仍将 Python 指向 `F:/CodexBackups/图像篡改识别/20261003_111113/project/.venv/Scripts/python.exe`。

   最小补齐：归集匹配模块、配置、来源清单与依赖；运行时从包内登记路径解析。可选工具缺少安装条件时应在对应工具入口显示原因，平台首页和其他工具仍可启动。冻结一次当前源码，构建一个候选，在新的 F 盘目录完成首次启动、缓存重启及四工具最小工作验证。

2. **P1：首次原生作业创建失败后，普通用户无法继续。**

   本次在隔离外部 Chromium 中拦截首次 OCR 作业创建，返回确定的 503，后续项目列表返回空。失败后，“开始处理”禁用；点击“刷新状态”和重新加载页面仍然禁用，浏览器保留 pending 项。没有向真实原生服务提交创建请求。

   `apps/portal/src/features/start/QuickNativeWorkbench.tsx:52` 在 POST 前写入 pending；第 39 行只有找到“已关联且同名”的项目才清除，第 73 行继续以 pending 禁止操作。服务器在创建前失败，或已创建原生项目但关联未完成，均缺少普通用户可执行的收尾路径。OCR 和分类共享该组件；本次浏览器反例执行的是 OCR 分支。

   最小补齐：给创建操作固定请求身份及可查询结果，区分明确未创建、已创建未关联、响应不确定；支持原请求续接或补关联。明确失败后允许重试，保持请求身份。不能仅在所有异常时删除 pending，否则会重新引入重复创建。

3. **P1：简化原生路径与统一“项目输出”仍有断点。**

   简化入口可以创建/选择原生作业、打开原生页面，却只提供跳转统一输出页的链接，没有在此路径读取/归集原生结果。统一输出页直接索引的是 ClearData 作业导出，其余读取已发布 bundle。OCR 和分类的归集按钮仍在高级 workflow 的 handoff/处理上下文中。

   因此，“在原生工具处理并下载”已有路线，但不能保证按当前简化路线完成后，返回平台的“查看项目输出”就能找到该次结果。本次未重跑模型推理，此发现基于当前前后端接点，不宣称已经执行一次真实推理并观察到文件丢失。

   最小补齐：在简化入口列出当前项目的原生结果，提供明确的下载/同步动作，并让输出中心能找回。可以先采用到原生固定输出的可靠入口，不必引入完整证据审批或要求用户补建审计程序。验收时分别做一项 OCR、一项分类，从首页到保存文件，再关闭页面、重启后按项目找回。

4. **P1：图像取证的单文件离线报告不完整。**

   本次实际下载的 `review.html` 与固定成果哈希一致，但 HTML 使用相对地址引用 `preview-exif-normalized.png`、`01-noise.png`、`02-frequency.png`。单击报告下载不会保存这些图片到同一目录；只把报告交给别人或离开运行平台后，原图/热图缺失。报告和 PNG 可以逐件下载，工程文件未丢失，问题在于交付动作没有形成可直接使用的完整报告。

   根因见 `modules/image_forensics/forensic_toolbox/review.py:24` 的相对图片引用，以及 `apps/portal/src/features/forensics/ForensicWorkbench.tsx:51` 的单文件报告下载。输出中心的对应详情也只逐文件下载。

   最小补齐：提供“下载完整报告包”ZIP，或把预览/热图嵌入单个 HTML。下载后关闭服务，在新的 F 盘目录解包/打开，核对所有图片可读、报告身份一致。算法与模型无需因导出修复重新全量评测。

5. **P2：ClearData 旧作业与旧输出超过 100 项后从入口消失。**

   `src/workbench_platform/data_api/service.py:125` 的作业列表和第 147 行的直接输出查询均固定 `LIMIT 100`。输出接口只有 items，没有总数/游标；`ProjectDataOutputs.tsx` 也没有分页或查找旧输出的动作。

   独立合成索引中保存 101 个成功导出，实际只返回 100 个，最早输出被省略。文件没有被删除，但用户不能从常规入口稳定找回历史成果。这是持续使用完整性问题，不是要求支持大规模并发。

   最小补齐：服务端有界分页和基本作业/输出查找，页面显示总量及下一页。101 个输出即可作为反例验收，不必为该修改重新运行模型或十万行比对。

建议只安排三个收口切片：先完成原生创建恢复和简化输出接点；再完成自包含取证报告及 Data 历史输出访问；最后归集独立运行时并冻结一个候选，集中做交付验证。底稿、待办等既有高级功能保留，暂不新增 PDF 编排、模型、复杂权限、调度或审批。

每个工具达到以下标准即可认为首版闭环：选择项目、导入一份支持的资料、执行处理、看到明确成功/失败结果、保存可重新打开的完整输出；关闭页面并重启后仍能按项目找回；一次创建/处理故障后有可执行恢复动作；新 F 盘交付目录可运行，不依赖开发源码和备份目录。对现有审计高级功能复用未受影响的历史检查，只补接点变化涉及的验证。
