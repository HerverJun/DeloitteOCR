# 混元 OCR 识别修复验收 · 2026-10-04

用户在 ClearOCR 的“图片转excel表格”项目中使用 HunyuanOCR-1.5 识别“图解直线检测.png”，任务失败并显示 `Unbundled application runtime DLLs were loaded`。本次修复已在正在运行的源码预览生效，原任务已重试成功，结果及 TXT/JSON 导出均可读取。

## 根因与影响范围

开发启动层在当前数据根创建私有 Python 入口，通过 Windows junction 只读复用原 F 盘候选的 `runtimes/<引擎>/Lib`。运行时审计会解析 DLL 的真实路径，却只接受私有启动包内的路径，因此把来自原候选的 Pillow、pillow-heif 及其依赖共 8 个模块误判为未打包运行库。

混元模型已经完成实际识别，旧尝试中的 `raw.json`、文字和图像产物仍在；错误发生在发布最终 `result.json` 前的 DLL 检查。本问题源自开发预览的目录链接与运行库登记不一致，同样影响采用该链接布局的其他 OCR 引擎。普通独立包中，运行库实际位于其自己的包目录，原严格校验继续适用。

## 修复

- 平台开发启动器从原候选完整封存清单中提取明确链接目录内的 DLL/PYD/EXE 文件身份，保存 `runtime-sources.json`，与原候选清单哈希和原生绑定关联，并将登记文件纳入当前私有包的启动完整性清单。
- OCR 审计继续解析真实模块路径；对于私有包之外的运行库，只接受链接实际目标、登记来源、文件相对路径、大小及 SHA256 全部匹配的文件。不会按整个 F 盘或依赖目录无条件放行。
- 登记文件、链接目标、来源身份或模块内容变化时仍拒绝；系统目录中的 CUDA/应用运行库限制保留。结果中的审计字段如实区分包内模块与已校验的复用模块。

源码：`F:/OCR/output/clear-automation-dev-20261002/worktrees/ocr/src/ocr_workbench/runtime_audit.py` 和同级 `platform/scripts/development_native.py`。原程序包、模型及既有失败产物保持原字节；项目写入及所有本次证据均在 F 盘。

## 验证

16 项定向测试通过：运行库审计 10 项及 6 个子案例、来源登记 1 项、结果发布与隔离进程兼容性 5 项。包括真实 Windows junction、未登记的同目录 DLL、任意其他 F 盘 DLL、同大小内容篡改、链接改向、声明改写、来源身份冲突、路径逃逸以及系统 CUDA 库拒绝。

混元、PP-OCR、PaddleOCR-VL、GLM 四个真实运行时均实际加载 Pillow/HEIF，8 个复用模块分别通过文件哈希核验；后三者仅验证共用运行库，本轮没有重跑其模型推理。
