## 1. 目标与当前起点

最终产品仍是：统一门户、可独立运行的 OCR 与分类工作台、独立的数据清洗比对工作台，以及共享资料、任务、成果、交接和恢复能力。

再次对照用户贴出的原始方案后，将以下要求列为不可省略的产品约束：

- 三个应用平级且各自可用。简单使用无需先建平台工作空间；需要归集资料、任务和成果时再关联。数据应用既能独立处理台账，也能接收 OCR 导出表格。
- Windows、单用户、本地与离线使用是首版范围。平台不绑定某种审计流程，不扩展为多人企业系统，也不把后续 PDF/抽样/报告/流程画布提前列为本期必做应用。
- OCR 与分类保留各自界面、运行时、数据库、旧项目和原生业务语义；平台通过受控 API 接入，不直接写原生业务表。平台 SQLite 管元数据，数据计算由独立受管分析进程承担。
- 数据首版必须覆盖 XLSX、CSV、Parquet 的完整导入、清洗、比对与导出；每步可预览、撤销、另存版本，并把配方应用到新数据。
- 用户正常完成操作后，任务、成果和来源应自动连通；不能把手工填写内部任务 ID 当作普通业务流程的必经步骤。

当前 47 项中，28 项标记 done，规划器认可 27 项；T017 的旧浏览器证据因源码变化过期。T021 正式适配器 8 项、OCR CPU 716 项通过（2 项跳过），等待审计结项。T024 正式钩子 11 项、OCR CPU 716 项通过（2 项跳过），暂挂等待依赖恢复。T032 已实现，但修复轻量环境中的 Pillow 导入依赖后，旧冻结证据失效，待新版本验收。

|---|---|
| P0 工程基础 | 三仓隔离、契约、夹具、检查执行器、原应用基线 |

缺口主要在完整界面、跨应用业务流转、恢复和分发。后续优先把已有后端接成可操作流程。

## 2. 本次修订的核心决定

1. **按可使用的产品流程推进。** 每批至少交付一条用户可操作的完整流程，并提供实际入口、样例输入和可读回输出。测试数量不单独作为阶段成果。
2. **集中全量回归。** 原生源码在一个开发批次内修改稳定后统一跑基线；同一源码、运行时、配置和夹具已通过的基线，不因切换任务 ID 再运行一次。
3. **保留必要的小范围检查。** 数据保真、权限与工作空间隔离、幂等、崩溃恢复、取消和成果完整性仍是必须修复的产品缺陷。
4. **一次规划配套接线范围。** T036/T044 所需后端路由、服务组合、门户路由和测试入口提前纳入范围，避免做一半才反复迁移计划。
5. **资格与工程交付分开推进。** 真实 GPU、独立 Windows、业务样本验收保留原任务。缺资源不阻塞其他工程，也不计为通过。

### 批次 1：先交付可使用的数据清洗比对工作台

涉及：T044 → T046，配合 T047；复用 T040–T043、T045；门户稳定后补 T017。

完整流程：**无需先建工作空间，直接打开数据应用 → 导入两份表格 → 选择工作表/表头/编码/分隔符及列类型 → 清洗和逐步预览 → 选择比对键 → 查看差异 → 导出成果。** 持久草稿使用应用自身会话/作业身份，需要归集时才关联平台工作空间。

- 补齐数据应用注册、真实 API、受管后台作业与门户路由。复用已有计算模块，将导入、清洗和比对接入独立分析进程及有界取消机制；平台服务负责协调，避免在请求处理中直接承担大表计算。
- XLSX、CSV、Parquet 都必须进入同一类型保真、清洗、比对和来源链路。当前 Parquet 底层分析读取/导出不等于该完整链路已经完成；补齐缺失的导入适配。
- 界面覆盖输入、操作步骤、预览、键映射、差异结果、来源定位和成果下载。
- 保存配方和草稿；刷新可恢复输入、步骤与结果版本。配方支持另存版本，并通过明确列映射在另一份新文件上重跑，不能只验证同一数据的历史步骤。所有按钮具备实际行为、加载状态和错误反馈。
- 首版六类固定操作全部可用：去空白、列改名、值映射、显式日期/金额等类型转换、筛选、按字段识别重复；比对展示相同、差异、仅左、仅右及歧义重复键。
- 在独立预期结果上核对重复键、长编号、金额、空值、公式缓存、中文表头、混合日期，以及取消后恢复。
- 用原计划十万行双表验证有界性能、内存/磁盘约束、分页和取消响应；先冻结阈值，再测量。发现实际瓶颈后再优化或扩大规模。

**交付：** 可打开的数据工作台、两份演示输入、真实差异表及来源清单、刷新与取消演示、正式数据验收结果。整个流程不要求启动 OCR 或分类服务。

**退出条件：** T044/T046/T047 对应验收通过；三种输入格式、无工作空间直接使用、配方在新数据重跑、独立计算进程和固定版本重新下载均有证据；门户导航与新增页面的真实浏览器检查通过。到这里应能独立使用第三个应用。

### 批次 2：打通资料、原生应用、任务与成果

涉及：T036、T033、T034、T028；复用 T030/T031/T032/T035 和任务中心。

完整流程：**资料登记 → 搜索选择 → 选择目标原生项目 → 交接 → 查看真实任务状态 → 下载成果 → 返回原件出处。**

- 先交付资料库和成果中心的真实后端与界面：中文/Unicode 搜索、来源/标签/类型筛选、分页、多选、版本和成果下载。
- 补普通用户可操作的“工作空间与原生项目建立链接”流程，结束只能使用预置链接的限制；写入前核验真实项目身份和访问权限。
- 完成分类持久幂等导入 T033，保护现有类别定义与锁定测试集。
- 完成 T034 提交意图、回执、逐项映射与状态核实；unknown 先查询后决定是否重发，部分失败可见且可继续。
- 交接或用户提交任务后自动登记原生任务引用、输入版本与成果关联；手工录入任务 ID 仅保留为诊断/补录能力。首页和任务页提供实际失败、待复核及资源等待入口，区分预测与人工确认。
- 交接范围与应用声明的输入类型一致。OCR 已有 PDF 能力沿用其文档/拆页路径并保留页码出处；当前仅支持图像的幂等端点不能被描述成支持全部 OCR 输入格式。不为此新建独立 PDF 工具应用。

- 界面按原生实际能力显示可用操作；排队、取消请求已发出和模型未就绪均不表示成功。

**交付：** OCR 与分类各一条真实资料交接演示，部分失败/重启恢复演示，成果可下载并追溯原件。实际识别能力按已安装模型与运行模式验证，GPU 资格另记。

**退出条件：** T033/T034/T036/T028 对应行为通过；本批原生源码固定后完成一次适用的原应用全量基线。

## 4. v16 验证安排：一次基线，多项专项检查

采用现有任务和执行器做最小调整，不新建一套检查平台。

| 范围 | 修订后的检查职责 |
|---|---|

| T015/T016 | 导航专项和对应前端检查；通过依赖链要求当前 T003 基线，不再分别重复全量 CPU。 |

| T024/T025 | GPU 入口钩子专项；真实 GPU 仍由 T053 验证。 |
| T032/T033 | 原生真实 HTTP 幂等导入及重启恢复专项；通过依赖链要求当前基线。 |
| T044/T046/T047 | 数据界面、独立预期值、导出读回与有界性能；不因平台 UI 变化重跑 OCR 全量。 |
| T051/T052 | 固定候选的构建、三应用综合回归与真实浏览器检查。 |

执行约束：

- 同一固定实现的一项完整基线可由多个依赖任务引用其已验证状态；专项任务仍各自运行自己的正式检查并留真实回执。
- 不伪造“重新运行”的回执，不将不同源码的通过日志改成当前源码通过。仅计划元数据变化的迁移必须保存原回执身份和明确来源。
- 来源清单覆盖实际执行路径、契约、配置、锁文件和夹具。不得因为文件变化就随意删除相关来源；也不把未执行、无影响的整仓目录反复冻结到所有任务。
- 上游仅换了 attempt 或补了文档，不自动要求重跑未受影响下游。实际代码/契约/数据格式变化按影响清单处理。
- 新增原生导入、schema 或服务组合变更，先跑迁移、原生 HTTP、轻量平台环境兼容和相关任务投影检查，及早发现跨环境问题，再进入全量基线。
- 全量测试放在本批源码固定后；检查通过且无新变更，不追加“保险性再跑一遍”。
- 真实浏览器集中在页面/API 接线稳定后执行；截图使用外部 Chromium 的禁 GPU 参数，完成后退出本批拥有的浏览器与服务。

落地顺序：保存 v15 任务/检查/状态与回执 → 一次 v16 迁移调整上述检查归属、批次优先级与配套写域 → 校验依赖和验收覆盖 → 从批次 0 继续。T044/T046 的配套写域需包含缺失的 Parquet 保真导入、跨文件配方、worker 执行接线及相应测试；保留既有 T041/T042 的历史成果和证据。现有工具不支持的新规则须先落实再应用；不得仅改 plan_digest 让检查变绿。

## 5. 推进纪律与完成条件

- 一个执行者、一个活动开发任务；批次可以包含多个任务，依赖允许时逐项推进，不同时编辑相同目录。
- 每次代码提交形成一个完整行为变化。每个开发批次至少有一次可操作演示和可下载/读回的结果。
- 每约 30 分钟同步检查点；每批报告“新能做什么、实际入口、输入输出、剩余阻碍”。NEXT 与账本同一轮更新。
- 连续两个工作检查点若只有计划、回执或预算迁移，应停止扩大执行工具，回到可独立交付的功能；核心正确性失败仍须定位修复。
- 一个任务预计超过半天且行为可独立验收时，在领取前拆清切片。不能用不断扩张的 running 任务隐藏缺口。
- 优先修复数据错误/丢失、权限或空间串用、重复提交、取消恢复失效、核心流程不可用。样式微调和无证据的性能优化排在可用流程之后。
- 不新增通用插件市场、工作流画布、远程计算或新的微服务架构；已有三个应用边界保持独立。

本计划保留全部原始任务。工程交付、设备合格、业务合格和 v1 合格分别以各 gate 的真实证据判定。用户要求的关机仍以完整目标完成为前提：保存代码、状态与报告，确认本任务进程收尾后执行；阶段演示或带外部资格缺口的报告不自动触发关机。
