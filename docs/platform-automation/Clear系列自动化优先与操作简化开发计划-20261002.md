## 1. 固定的产品主线

普通工作入口为“新建处理批次”：选择资料与模板，预检通过后启动。运行中查看阶段、成功/失败数量和需要补充的信息；完成后首先查看结果摘要、待处理项和成果。

使用者不应为了一个常规批次分别新建多个原生项目、反复选择模型、逐步点击导入/清洗/比对、手工归集成果或填写内部ID。已有项目关联与实例身份由模板和平台上下文复用；无法确定的首次关联只请求一次具体选择。

提供少量明确场景模板：

| 场景 | 自动执行范围 | 必须向人交回的事项 |
|---|---|---|
| 两表清洗与比对 | 导入左右资料，重放已确认清洗规则，应用固定匹配政策，比对，生成固定版本成果并归集。 | 新表结构、歧义列映射、重复键及需要解释的差异。 |
| 图像批量分类 | 导入固定资料集，复用已绑定项目与模型，批量分类，汇总、生成结果并归集。 | 模型建议复核、失败、规则冲突和抽查样本。 |
| 文档识别与提取 | 在真实能力允许时导入文档、批量识别/提取，保存结果与来源并归集。 | 识别失败、结构不完整、不可靠字段及需要校对的内容。 |

不要求所有资料依次经过分类、OCR和比对。先完成各自明确的闭环，再接有真实输入/输出契约的组合模板。文档提取到表格比对的字段契约未明确前，不宣称已支持任意票据自动入表。

## 2. 自动执行与结果认可分别设计

流程自动执行使用已有算法和明确配置。用户启动一次后，普通成功阶段连续执行，不再逐步重复确认；输入身份、规则或能力发生变化时，暂停需要重新决定的部分。

分类模型的高分不等于财务审计低风险，也不等于业务正确率。当前自动接受默认关闭；保留该事实。自动通过需要独立版本化政策及业务验证、来源记录和抽查安排，不能把 `auto_accept` 全局改为开启来制造自动化效果。执行失败、证据缺失和规则冲突必须在摘要中可见。

每个批次分别保存：

- 执行状态：排队、执行、等待资源/补充输入、部分完成、成功、失败、取消或待核实。
- 原始输出：原始模型建议、分数、结果分类与来源，不被人工处置覆盖。
- 处置记录：未处理、人工确认、暂缓、重开；若启用规则自动通过，记录所用政策版本和依据。
- 成果状态：尚未生成、已生成、归集成功或归集失败，绑定固定结果版本。

已有资产标签不能代表本次结果已经复核。执行成功、导出成功和复核完成分别表达，不共用一个“完成”勾选。

## 3. 减少操作的具体变化

| 当前操作负担 | 调整后的正常路径 | 异常路径 |
|---|---|---|
| 新批次反复配置导入、清洗、匹配键和容差。 | 首次确认后保存模板；新资料匹配同一结构时复用。 | 缺列、重名、类型变化或角色不明时显示具体问题；不悄悄按列位置匹配。 |
| 导入、重放、比对、导出和归集需要分段点击。 | 一个批次运行连续编排已有动作，后台完成并记录成果。 | 展示失败阶段；有明确重试能力时只重试未完成部分。 |
| 每次进入工具重新理解项目/模型关联。 | 模板绑定当前工作空间、项目关联和模型版本。 | 已删除项目、模型失效或能力变化时请求替代选择并形成新模板版本。 |
| 用户逐条打开结果弹窗、确认、关闭再找下一项。 | 默认进入异常队列，大图/原件与判断并排，保存并下一项。 | 暂缓、重开和人工说明有真实持久记录；批量操作显示明确选中范围。 |
| 作业完成后仍面对输入与参数。 | 首屏显示结果摘要、自动处理覆盖、待处理数量和已归集成果。 | 归集失败与部分结果单列，不把“处理成功”写成“全部完成”。 |

高级编辑、原生工作台、模型训练和运行诊断继续可访问，放在模板配置、维护或详情中；日常批次无需理解编码器、批大小、API文档或ONNX格式。

“自动生成成果”指在本机产生并登记可核对文件，不要求浏览器自动下载每一个文件。用户可在成果区按需下载，避免自动弹出多个下载窗口。

## 4. 首版技术边界

复用现有工作空间、资料集、原生项目、任务、清洗配方、比对政策和成果接口。新增批次/处理模板与必要处置记录属于小范围领域增量，不能再用“纯样式改动”代替实际契约和数据兼容检查。

处理模板保存不可变版本：输入角色和允许类型、导入选项、必要列和明确映射、左右清洗规则、比对键/类型/空值/金额政策、模型或引擎版本、输出与归集要求。运行时绑定模板版本、输入清单身份和子任务回执；新资料生成自己的来源身份。

执行由后端持久化管理。浏览器负责发起、显示和必要选择，不用 React effect 或内存定时器充当跨阶段调度器。复用现有资源队列与GPU所有权约束，不建立另一套资源抢占规则。

响应丢失时先查询已有操作；只有确认未提交时才按协议继续。相同运行请求重放返回原批次与子任务，不重复导入或生成成果。取消后等待原生真实终态，后续阶段不再启动。失败后保留成功项及来源，恢复只推进未完成部分。

数据政策保持：长编号与前导零、十进制金额、原件、版本和来源不变；重复键不自动强行配对；清洗不覆盖原始资料；归集绑定固定成果，不以重新计算替代缺失原成果。现有首次完整性校验与缓存策略不变。

OCR处于仅校对模式时，识别模板必须报告能力不足；可以处理已有结果，但不能显示“已自动识别”。没有实际暂停/恢复能力的原生任务不展示可执行控制。

首版不建设通用拖拽流程设计器，不新增模型算法，不要求云服务，不建立Codex定时任务或自动新聊天。监控目录与定时处理作为后续扩展，先把显式启动的一次批处理做完整。

首个可运行里程碑为 N00、N01 和 N02 的ClearData切片，不等OCR/分类全部完成才让用户看到效果。N03/N04按原生能力逐一接入；组合模板只有在字段和来源契约得到真实验证后纳入交付。

主要源码范围为平台 `packages/contracts/`、`src/workbench_platform/` 与相应门户 feature，数据模块沿用 `modules/data_workbench/`；分类限定在处置/结果API与相应工作台，OCR限定在能力适配、批处理连接和复核显示。模型、引擎算法和既有数据政策不因流程简化改写。

## 6. 验收以减少机械操作和可靠恢复为准

| 检查 | 必须看到的结果 |
|---|---|
| 同结构资料复用模板 | 文件/资料选择和模板确认后一次启动，成功流程无需再手点清洗、比对、生成文件和归集；记录实际人工动作数。 |
| 输入结构变化 | 缺列/重名/类型变化给出具体待补充项；不默认把第一列当业务主键，不按位置静默改变映射。 |
| 请求重放与响应丢失 | 返回原运行身份，查询已提交操作；导入、子任务和成果无重复。 |
| 刷新、关闭页面与服务恢复 | 页面不承担执行；读回持久阶段与回执，恢复只推进未完成部分。 |
| 部分失败与取消 | 覆盖数量守恒；保留成功结果与原件；取消后不继续派发后续动作，提供具体恢复入口。 |
| 人工/自动处置 | 原始预测保留；本次结果的处置状态真实可核对；暂缓不计完成，重开恢复待处理状态。 |
| 连续和批量复核 | 保存后进入下一项且保持筛选；批量范围明确，跨页全选与当前页选择有清楚区别。 |
| 数据与来源 | 已有小表预期、20位前导零编号、金额/空值/重复键、输入和结果版本、实际下载读回通过。 |
| 成果归集 | 正确工作空间、固定结果/导出身份和来源；归集失败可见，重试不生成重复成果。 |
| 原生能力与政策 | OCR仅校对模式不冒充识别；分类自动接受不未经政策验证就开启；技术执行完成不冒充审计结论。 |

先选一个真实可解释的小批次记录基线，再用相同任务验证模板复用路径，分别记录首次配置和重复批次的人工动作、介入次数、错误与恢复情况。未取得数据前不宣传“减少80%操作”等数字。纯样式不写镜像测试；幂等、恢复、处置状态和数据保真需要有真实意义的契约/集成检查。
