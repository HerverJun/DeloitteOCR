## 1. 结论

**严重问题尚未整体消除。006修好了一条明确图片提取路径和若干恢复缺陷，但不能据此认定“用户怎么描述常见任务都能顺利做完”。** 当前仍存在入口分流过窄、临时故障难以续作、追加目标被拒绝、跨工具空转保护不足、暂停任务阻挡无关工作等结构性问题。下一轮应先修这条用户工作链，暂缓新增能力和界面精修。

正式入口仍为0.12.1；本次重查的是冻结的0.13.0 candidate-006及匹配的门户源。候选的修复未进入正式入口，这是用户仍可能遇到旧问题的一层原因；但仅发布006也不能解决本报告确认的剩余问题。

## 2. 从用户实际遭遇回看

2026-10-16，一句“为我提取图片中的文字”实际耗时794.6秒，20次模型请求；开始OCR前等了167秒，OCR成功后又过了136秒才收尾，最终仍为partial。这是“普通任务被编排成复杂流程”的真实事故。006对这句原话的零模型路径已通过，不能继续把这次事故说成006又发生了。

另一条真实任务是“读取PDF第2页并与第5页金额比较，保留原文/编号/金额精度，有实质歧义先问我”。旧005最终52次请求、partial，006后来2次复核完成，已修复历史交付错误。**后续2次复核成功不证明新用户从零提交同类复合任务就能直接顺利完成。** 此任务中的金额口径提问是用户明确允许的真实业务澄清，不属于应删除的无意义确认。应消除的是后面的内部反复核实、交付失败及人工恢复负担。

事故与新复现必须分开：本轮没有新增真实模型首跑或浏览器验收；以下当前问题由冻结候选的精确控制流、隔离协作者和界面调用点重现。它们足以确认某些入口和恢复会被挡住；对“实际会调用多少轮、结果区具体体验”仍须按第6节做真实旅程验证。

### 3.1 口令修补没有解决通用工作流程

“为我提取图片中的文字。”命中短路；“帮我识别一下这张图片里的文字”“提取图片文字，谢谢”“把这张图里的字抄出来”不命中。明确PDF页提取也没有同等聊天短路。它们进入Harness不等于必然出现20轮，但说明最常见自然表达仍暴露给原来较长的工具编排流程。继续往白名单加几句话不能作为根治。

同时，主输入框的发送按钮要求`connection.available`，即使后端具备本地零模型能力也会被挡住。用户必须自己发现另一组按钮；这与“描述目标，系统完成常规准备”的主流程不一致。

定位：[聊天目标分流](/F:/OCR/output/architecture-revision-20261017/delivery/Clear-0.13.0-architecture-candidate-006/platform/src/workbench_platform/agent/runtime.py:534)；[主发送入口的模型条件](/F:/OCR/output/architecture-revision-20261017/delivery/Clear-0.13.0-architecture-candidate-006/platform/apps/portal/src/features/agent/AgentWorkbench.tsx:386)。

### 3.2 “已保存进度”不等于用户能够继续

连接故障或控制进程退出被转成failed，而继续接口只接受paused/running/waiting_job/needs_verification等状态。复现中provider_unavailable、harness_exited、truncated_response、耗尽重试后传出的rate_limited都落failed，随即继续被拒绝。

未知模型响应被保守地挡住是有理由的；问题在于接下来只告诉用户“结束本轮后以新目标继续”。应该保住同一个用户目标与已做工作，在明确安全的边界恢复；未知**业务写入**仍必须先查回执，不能为了“不中断”改成盲目重发。

定位：[故障如何收尾](/F:/OCR/output/architecture-revision-20261017/delivery/Clear-0.13.0-architecture-candidate-006/platform/src/workbench_platform/agent/runtime.py:436)；[继续任务的状态限制](/F:/OCR/output/architecture-revision-20261017/delivery/Clear-0.13.0-architecture-candidate-006/platform/src/workbench_platform/agent/runtime.py:482)；[Harness中断错误](/F:/OCR/output/architecture-revision-20261017/delivery/Clear-0.13.0-architecture-candidate-006/platform/src/workbench_platform/agent/harness.py:98)。

### 3.3 继续、改要求、并行工作不是一条顺畅的链

图片提取执行中追加“提取完再比较两张图金额”，后端明确拒绝；用户按提示暂停后再追加，依然拒绝。界面这时仍把发送标成“补充并继续”。当前没有静默吞掉追加内容，真正问题是产品承诺和可用路径不一致，要求用户停止原工作才能推进新的需求。

此外，暂停的Harness与另一独立workspace图片操作仍发生冲突。保护同一个可变对象是必要的，但把无关项目一并挡住，会再次把“继续工作”变成“先处理旧任务/停掉别的工作”。

定位：[直接任务拒绝追加](/F:/OCR/output/architecture-revision-20261017/delivery/Clear-0.13.0-architecture-candidate-006/platform/src/workbench_platform/agent/runtime.py:569)；[Harness冲突判断](/F:/OCR/output/architecture-revision-20261017/delivery/Clear-0.13.0-architecture-candidate-006/platform/src/workbench_platform/application_services/direct_scope.py:25)；[对所有活跃任务做准入检查](/F:/OCR/output/architecture-revision-20261017/delivery/Clear-0.13.0-architecture-candidate-006/platform/src/workbench_platform/agent/store.py:328)。

### 3.4 防空转必须看目标进展

现有逻辑只在相邻动作的工具、参数和结果签名完全相同时累加。相同失败动作AAA达到3；交替“交付失败→读结果→交付失败→读结果”8步计数始终为1，因此这一保护本身挡不住换工具的无效循环。显式用户预算等仍可停止执行，不能据此宣称现版必然无限运行。

应以“新增了什么有效结果、解决了哪个缺失条件”判断进展。真实长任务可以有很多步骤；无效巡查不能因为工具名变了就继续消耗模型。

定位：[当前重复动作计数](/F:/OCR/output/architecture-revision-20261017/delivery/Clear-0.13.0-architecture-candidate-006/platform/src/workbench_platform/agent/harness_service.py:434)。

## 4. 下一轮真正的改进目标

用户只需提出目标并提供资料；只有缺少会改变结果的业务信息时才提问。准备服务、关联范围、搬运ID、等待工具和封装下载由系统完成，不变成用户待办。

常规任务稳定执行到可用结果；短暂故障保留目标和进度，修复后继续，不让用户重新讲一遍。追加要求围绕已做工作续接，不要求把原任务推倒重来。已完成的原文/表格先能拿到，后续分析失败不把它们一起藏住。一个暂停任务不影响真正无关的项目。

本轮验收先看**是否被迫重来、是否需要无意义干预、是否反复空转、结果是否可用**。2秒控制开销、文件清单、文档一致性等工程要求保留，但不再拿它们代替这几项严重问题是否解决。

## 5. 重排后的8项任务

先执行UF-007，固定并真实复现J01/J04/J05/J07；修复优先顺序为UF-001、UF-002、UF-006，再接UF-003/004/005，最后UF-008交付。UF-007的旅程在每轮修复后重跑相关场景。所有任务尚未实施，不能把本次规划写成已修好。

### UF-001 同一用户目标走同一条简洁流程，不依赖固定口令或专用按钮

用户痛点：用户说法稍变就进入完整Agent；聊天发送还要求模型连接，本来能做的本地操作被入口挡住。

改进：

- 依据目标、资料类型和必要参数统一识别图片提取、PDF页提取、明确Data操作及已有模型预测；常规前置准备由服务端完成。
- 明确操作继续零模型；确需自然语言解析时使用有边界的一次解析，把参数交给已有业务动作，不让模型逐步搬内部ID。
- 复合目标保留所有条件；结果分析才用模型，不能因出现“文字”就吞掉比较/解释/制表要求。
- 用户输入框按任务实际能力启用；模型未连接时已支持的明确本地任务仍能从主流程发起。

验收：

- J01各自然说法、图片/PDF入口及正常参数不要求用户知道执行模式、原生项目ID或服务准备。
- 同样的明确目标不能因“谢谢”等修饰触发完整工具发现/计划维护/上下文整理；专用按钮是便利入口而非唯一可靠入口。
- 复杂要求进入分析且不降低交付条件；模型次数按任务必要性记录，简单提取不再出现十几二十轮。

### UF-002 短暂故障后继续原任务，不让用户重新开始

用户痛点：模型连接、限流重试耗尽或Harness中断后任务进入failed；现有继续接口拒绝failed，未知模型响应还要求结束本轮后另起目标。

改进：

- 区分明确未执行/明确拒绝、控制器故障、未知模型响应、未知业务写入；为每类提供原用户任务的恢复路径。
- 已明确安全的短暂连接故障做有界恢复；需要修连接时保存任务，修好后一个“继续”从最后有效进度续作。
- Harness进程退出先重建原日志和操作回执，再继续；未知业务写入始终先查原生回执，不盲目重发。
- 内部可新增合法尝试，但用户目标、已完成成果和接受的原生作业保持连续；不要求重新描述目标或重新选资料。

验收：

- J04/J05分别在工具提交前、接受后、工具完成后和交付前打断；恢复后只补未完成步骤，原生已接受作业不增加。
- 恢复失败明确告诉用户“已完成什么、剩什么、需要你做哪一件事”；不能只写“查看步骤/以新目标继续”。
- 认证错误修复后也能续作；用户主动停止不被自动恢复，未知写入不被当成可安全重试。

### UF-003 让补充要求、暂停和继续形成可用的一条工作链

用户痛点：界面说“补充并继续”，直接任务运行中和暂停后却都拒绝追加；用户只能停掉再想办法重开。

改进：

- 把追加要求固定到同一用户任务；已接受的原输入/参数保持不变，后续步骤接续新要求并复用已产出结果。
- 兼容的追加安排在当前步骤之后；真正冲突的范围/引擎变更说明影响并给继续原任务或建立关联修订的明确选择。
- 暂停后可以修订后续目标，再继续；界面文案、可用按钮和后端行为一致。

验收：

- J08中OCR运行时追加“再比较金额”，无需停止重做OCR，后续比较确实完成。
- 暂停后修订能够生效；不能把409拒绝当成已接收，也不能接受后静默丢掉后续要求。
- 原件版本、范围和旧尝试保留；缩小范围、增加资料与用户停止分别验证，不篡改已接受写入。

### UF-004 阻止跨工具空转，按用户目标是否推进决定下一步

用户痛点：当前连续重复保护只看紧邻同一动作；失败交付和结果读取交替发生时不会触发，仍可能反复消耗模型。

改进：

- 用要求覆盖、实际新增结果、已解决障碍和用户新信息判断业务进展，不以工具名称或参数变化冒充进展。
- 同一未解决问题经不同工具反复出现时，先执行有界的已知修复；仍无进展则保存可用成果并给具体阻碍。
- 常规提取/导出/等待由共用业务动作完成；复杂任务按需加载工具，避免重复发现目录、准备项目和核验同一结果。

验收：

- J02和交替失败回放不会连续绕同一障碍；真实业务长流程允许超过20步，健康原生等待不被误判为空转。
- 没有实质业务歧义时不要求用户替系统选择内部修复步骤；有歧义只问影响结果的必要问题。
- 无法完成时交付真实已有成果和缺失条件，不通过删要求或伪造成功收口。

### UF-005 计算结果先可用，后续分析中断也不锁住成果

用户痛点：现有完整交付依赖运行驱动走到发布步骤；控制器失败后的自动成果收取与直接呈现尚缺真实断点验收。

改进：

- 已完成工具的原文/表格/预测及下载进入当前任务成果区，不等待最后一次模型总结。
- 分析未完成时分别展示“原文已完成、比较待继续”等业务状态，避免一个失败标记遮住全部有效结果。
- 模型或Harness中断后仍可读取原生已完成结果，按原版本发布；恢复时复用而非重算。

验收：

- J04/J05在工具完成后断开模型或关闭自有Harness，用户仍能从原任务拿到完整结果与实际文件。
- J06中成功2项立即可用，失败1项恢复后完整交付；用户不需进运行日志找工具ID或手动重新导出。
- 最终分析不完整继续如实标注；保存部分成果不冒充全部目标成功。

### UF-006 一个暂停任务不再拖住无关项目

用户痛点：当前start_run扫描全部活跃任务；存在Harness任务时对非Data新任务保守冲突，独立项目图片任务也会被挡住。

改进：

- 把冲突约束落实到可能写入的实际原生对象和所属范围；同会话顺序继续保留。
- 暂停分析的未知对象范围只保守覆盖其真正可访问资源，不能无条件阻塞另一独立项目。
- 跨workspace指向同一原生项目的链接仍识别为同一对象，不通过删锁换并发。

验收：

- J07暂停项目A的分析后，项目B的独立图片提取和纯读取能继续。
- 真正同对象冲突仍排队或版本拒绝；用户看到明确关联任务，无需停止无关任务或重启软件。

### UF-007 用真实用户目标建立复现与回归，先跑失败场景

用户痛点：此前验证偏向原句快捷路径和缺陷修复后的复核，不能证明自然表达、首次完整流程及中断体验普遍可用。

改进：

- 该次修复先复现J01/J04/J05/J07，再执行完整J01—J09；后续开发只补查受影响旅程，从主输入入口开始，不在提示里注入工具名、内部ID、oracle或“按正确步骤执行”。
- 存下第一轮原始轨迹：用户点了几次、被问了什么、首次结果何时出现、模型和业务动作多少次、卡在哪里、如何恢复。
