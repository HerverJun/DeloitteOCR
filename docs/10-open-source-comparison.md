# 通用图像分类平台：精准性、轻量性、速度性对标与发展方向

> 后续实测与已落地改动见 [v0.2 公开数据评测](11-public-benchmark-and-v02.md)。本文保留 v0.1 的历史起点。

核验日期：2026-09-18。对象：本项目 v0.1，Windows 11 / RTX 4070 Ti SUPER 16 GB / PyTorch 2.9.1 / timm 1.0.29 / ONNX Runtime 1.26.0。

当前平台已具备数据版本、训练、导出、分类与复核的工程闭环。算法处于可信基线阶段：冻结 DINOv2 / ResNet18 编码器、训练线性头、FP32 ONNX 推理。最重要的改进顺序是建立业务评测、优化输入处理、增加轻量模型，随后根据业务错误类型提升特征与训练能力。

本报告结合源码审查、已有集成记录、本轮组件测速及官方公开资料。尚未把所有候选模型放到用户业务数据和同一硬件上进行对照训练，因此不声称某模型在本业务上已经胜出。公开的 ImageNet、零样本、iPhone、CPU、RTX GPU 指标分别保留测试口径。

## 1. 当前实现的量化起点

| 模型 | 编码器参数量 | 当前完整 ONNX | 已有分类循环记录 | 本轮热运行 ORT，batch 16 |
| --- | ---: | ---: | ---: | ---: |
| ResNet18，224 | 11.18 M | 42.63 MiB | 75.4 张/秒 | 约 2961 张/秒 |
| DINOv2 ViT-S/14，224 | 21.63 M | 82.64 MiB | 71.0 张/秒 | 约 801 张/秒 |
| DINOv2 ViT-S/14，336 | 与 224 同级，位置嵌入不同 | 83.11 MiB | 54.8 张/秒 | 约 292 张/秒 |

编码器参数量由已安装 timm 实例化、关闭原分类头后统计；本项目三类线性头另加 1539 / 1155 个参数。ONNX 大小为实际文件字节，参数量和文件体积不是同一指标。

两列速度不能直接相除当作可实现的加速倍数：

- 已有记录只处理 60 张合成图，包含读取、SHA256、解码、预处理、模型执行和逐批写库；计时从 session 创建之后开始，不包含队列等待、包校验、模型初始化。
- 本轮 ORT 记录使用同样的合成图片预先生成输入，5 次预热、30 次计时，FP32 且关闭 TF32；使用普通 `session.run`，包含主机/设备输入输出拷贝，不含图片预处理和写库。吞吐由总图片数 / 总计时时间计算。
- 数据来自不同短时运行、文件缓存已热，不是业务负载验收，也不是端到端 p95 延迟。没有测量候选模型、长期显存峰值或 15 万张真实图片吞吐。

本轮处理 60 张图片的读取、校验、解码和缩放，4 个线程的中位时间约为 **0.596 / 0.614 / 0.632 秒**，分别对应 ResNet18 224 / DINOv2 224 / DINOv2 336。DINOv2 224 的单批 16 张执行中位时间约 19.48 ms；折算 60 张模型计算约 0.073 秒。该合成基准下，输入处理明显重于模型计算。

session 初始化约 0.74–1.15 秒；当前每个分类任务重新加载 session，短小任务受影响尤其明显。该数字包含运行时初始化、图优化、模型装载等步骤，本次未进一步分解。

开发用 `.venv` 实占约 **5.10 GiB**，不包含 node_modules、权重缓存及安装 wheel。前端构建约 1.14 MiB，JS gzip 约 370 KB。主要部署体积来自 ML 运行环境和模型。

实测记录：[组件测速](../reports/component-benchmark.json)、[完整流程验证](../reports/development-validation.json)。复现脚本：[benchmark_components.py](../tools/benchmark_components.py)，需已有演示模型且没有排队/运行任务。

## 2. 代表性开源实现和开放模型的对照

以下是可借鉴的模块及训练/推理方案，并非每项都是与本平台相同形态的完整 Web 产品。

| 对照实现 | 精准性方面 | 轻量性与速度方面 | 对本平台的直接意义 |
| --- | --- | --- | --- |
| [timm](https://github.com/huggingface/pytorch-image-models) | 广泛骨干、增强、微调、蒸馏训练方案，已经支持 DINOv3、SigLIP 2 等 | 可选 MobileNetV4、RepViT 等不同资源档位 | 本平台已使用 timm，但当前只开放两个骨干、一个训练方案，尚未利用大部分能力 |
| [DINOv3](https://github.com/facebookresearch/dinov3) | 新一代通用视觉特征，提供蒸馏的 ViT-S/16 等较小模型 | 官方 ViT-S/16 约 21 M 参数，与当前 DINOv2-S 属同一量级 | 值得进行等预算特征对照；升级不自动意味着本业务准确率提高或部署显著变小 |
| [SigLIP 2](https://huggingface.co/google/siglip2-base-patch16-224) | 图文语义对齐，可做标签文本驱动的零样本分类及图像特征迁移 | 完整图文模型一般较重；固定标签可预计算文本向量，推理部署只保留图像编码器及类别向量 | 补充少样本冷启动和语义类别对照；中文类名、细粒度工业类别需要验证 |
| [MobileNetV4](https://huggingface.co/timm/mobilenetv4_conv_small.e2400_r224_in1k) | 小模型基线，适合后续业务微调或蒸馏 | 本机 timm 的 Conv-Small 去分类头后约 **2.49 M** 参数 | 优先补充轻量档，验证模型体积、CPU 时延及各类召回率 |
| [RepViT](https://github.com/THU-MIG/RepViT) | 官方 ImageNet 对照显示较好的精度/延迟平衡，并提供蒸馏权重 | 本机 timm 的 M0.9 去分类头后约 **4.72 M** 参数；支持部署重参数化 | 作为 MobileNetV4 的另一条轻量候选；原仓库手机时延不能直接套用到 RTX 显卡 |
| [PaddleClas / PULC / PP-ShiTu](https://github.com/PaddlePaddle/PaddleClas) | 成熟分类配方、蒸馏，以及基于特征检索的识别与扩类 | PP-LCNet 等轻量骨干，面向不同硬件的部署优化 | 借鉴训练配方和小模型蒸馏；检索扩类与闭集分类要分别验收，不必因此整体替换现有后端 |
| [Tip-Adapter](https://github.com/gaopengcuhk/Tip-Adapter) | 冻结 CLIP + 少样本特征缓存；提供免训练及轻量适配方案 | 适配成本低，但图片仍需通过编码器；缓存检索有额外存储/计算成本 | 给线性头增加强少样本对照，检验极少标签时的稳定性；这是成熟基线，不宣称是最新 SOTA |
| [ORT TensorRT EP](https://onnxruntime.ai/docs/execution-providers/TensorRT-ExecutionProvider.html) / [OpenVINO](https://docs.openvino.ai/2026/openvino-workflow/model-optimization-guide/quantizing-models-post-training.html) | 压缩/加速后需重新评估准确率、召回与拒识策略 | FP16、INT8、图优化和缓存；TensorRT 面向 NVIDIA，OpenVINO 可作为 Intel 设备候选 | 当前 ORT CUDA 是良好基础，但尚未使用这些优化；先根据目标设备和阶段耗时决定是否接入 |

公开指标示例仅帮助理解这些方案的定位：MobileNetV4 Conv-Small 的 timm 卡片列出约 3.77 M 总参数、ImageNet top-1 74.616%，测试尺寸 256；RepViT 原仓库 M1.0 列出 6.8 M、450 epoch 蒸馏训练 top-1 80.3%、iPhone 12 Core ML 约 1.0 ms。这些数据不是本平台三类合成图的精度对照，RepViT 原仓库参数也不应与 timm 去头/双头变体混为一谈。

另核验了 [MobileCLIP2](https://github.com/apple-aiml-research/ml-mobileclip)：S0 公开图像/文本编码器参数分别为 11.4 M / 63.4 M，ImageNet 零样本 top-1 71.5%。它体现了图文模型的效率方向，但当前仓库 [LICENSE_MODELS](https://github.com/apple-aiml-research/ml-mobileclip/blob/main/LICENSE_MODELS) 把模型用途限制在非商业研究，并明确排除产品开发，故不将该权重列为本平台默认产品接入候选。DINOv3 也使用 [独立许可证](https://github.com/facebookresearch/dinov3/blob/main/LICENSE.md)，不应视作当前 DINOv2 Apache-2.0 权重的许可等价替换。SigLIP 2 Base 与所列 timm MobileNetV4 / RepViT 模型卡标注 Apache-2.0。

## 3. 精准性：最缺少可信业务评测和场景适配

当前优点是采用强预训练特征、分组划分、不可变清单、独立测试划分、按类别阈值和人工复核。DINOv2 冻结特征在少样本场景仍是有竞争力的基线；只有几十张样本时，全量微调可能更容易过拟合。

当前不足：

1. **业务准确性尚未建立。** 验证/测试各只有 12 张合成图片，每类 4 张，不能代表文档、商品或工业图像。没有跨来源、跨时间、设备变化、未知类别的验证。
2. **训练选择有限。** 只有冻结编码器和线性头；学习率 0.03、权重衰减 0.01 固定，没有系统比较原型/近邻、正则化线性分类、部分解冻或适配器。缺少多随机种子和少样本抽样稳定性报告。
3. **输入策略单一。** 所有业务使用 224/336 的白底 letterbox 和同一预处理。整页文档的小字、极小缺陷可能在缩放后丢失；自然图像也未与骨干原始推荐变换比较。需要按业务验证，不宜统一套用强随机裁剪或旋转。
4. **阈值统计支持不足。** 当前校准允许至少 3 个接受样本、观察精确率达到设定值后采用阈值。观察上 3/3 正确不能证明总体精确率达到 95% 或 99%。同一验证集也用于选分类头和阈值；正式验收需要独立数据验证整个决策流程。
5. **拒识与反馈能力较基础。** 缺少未知类测试、概率校准、固定精确率下自动覆盖率曲线、主动选样和独立“未复核”队列。人工标注会更新，但历史预测状态仍保留，复核效率还有提升空间。
6. **防泄漏依赖人工分组。** SHA256 可识别完全相同内容，感知近重复、裁剪版、翻拍版和同文档多页还需要更好的候选关联。

建议以宏平均 F1、关键类别 precision/recall、混淆矩阵、不同来源的表现，以及“达到目标精确率时自动处理多少图片”共同验收。低置信图片全送人工可以降低自动错误率，却可能使自动化覆盖率过低，因此两者必须一起报告。

对于低错误率目标，要用足够多的独立审核样本报告区间。示例：决策规则事先固定，约 299 个独立、代表性自动接受结果零错误，单侧 95% 二项分布错误率上界才约为 1%；总体通过不能替代每个关键类别通过。实际抽样需考虑来源相关性与类别分层。

发展顺序：固定业务测试集 → 在训练/验证数据内比较 DINOv2 与新特征、小模型和简单分类器 → 分析具体错误 → 有证据地引入部分解冻/蒸馏/分辨率或局部信息处理 → 独立验收。文档若确实依赖文字，再增加 OCR 分支；工业任务若依赖小区域，再考虑切块或检测分支。

## 4. 轻量性：训练参数少，部署仍有完整编码器和开发依赖

当前三类线性头只有约千个可训练参数，特征缓存让重复试验成本较低。但线上每张图仍执行完整 11 M / 22 M 编码器，不能用“只训练分类头”来表示推理成本很小。当前 43–83 MiB 模型适合桌面 GPU，却还没有专门针对小内存 CPU/边缘设备的版本。

具体方向：

- 接入 MobileNetV4 Conv-Small 和 RepViT-M0.9，先比较相同标注预算下的冻结特征和轻量微调。以业务精度底线筛选，而不是只看参数数量。与当前 DINOv2 224 编码器相比，两者参数分别约少 8.7 倍和 4.6 倍；这不等于速度同比增加或精度不变。
- 使用已通过业务验证的较强模型做离线教师，把训练数据和允许使用的未标注训练池上的知识蒸馏给小模型。封存测试集不参与蒸馏或选型。
- 拆分开发/训练环境与推理运行包。API、模型、预处理、ORT 及必要运行库可组成推理包，去掉训练库、测试工具和冗余导出材料。当前不导入 torch 的预测命令仍借用 torch wheel 提供的 CUDA DLL，尚未完成真正独立部署验收。
- 为模型增加 FP32 参考包、FP16 GPU 包和适用硬件的 INT8 包。量化校准集需代表真实预处理后的输入；每个版本分别记录设备、精度、阈值及质量回归。
- 训练数据大时，将“一张图片一个 .npy 文件 + 全部特征一次搬到 GPU”改为分片/memmap 和分批拟合。以 15 万张、384 维 FP32 为例，单份特征原始数据已约 220 MiB，还未计算多份复制、Python 对象与掩码。

可将轻量候选目标先设为“模型包约 20 MiB 以内、在目标 CPU 上达标”，但它是选型目标，必须通过实际导出与业务评估后确定，不是当前已实现能力。

## 5. 速度性：当前优先优化输入与调度，再优化 GPU 精度

源码和本轮测速指出以下问题：

- `worker.py` 的每一批按“全部预处理完成 → 模型执行 → 逐项提交结果”执行。虽然有 4 个解码线程，但下一批预处理没有与当前批 GPU 计算重叠。
- Pillow 解码/缩放、NumPy 归一化、SHA256 校验及数组创建均在 CPU。当前测试的输入阶段接近每张 10 ms，远高于小模型按 batch 摊销的执行时间。
- 每个任务重新校验/建立 session，没有有界模型会话缓存。小任务的初始化费用没有包含在界面报告的分类循环时间中。
- 模型走普通 NumPy 输入输出；尚无 I/O binding、预分配缓冲、pinned memory、异步传输或 CUDA Graph。固定 FP32 且关闭 TF32，DINO 导出关闭 fused attention，以数值一致性优先，性能仍有优化空间。
- 特征首次提取对每张图先单独 `file_sha`，预处理又读取并计算一次 SHA，未命中缓存时存在重复文件读取/哈希。
- 写结果在一个批事务中，已经具备基本合并，但批内每条结果都会更新任务计数；更大规模下可测量是否需要批量计数更新。SQLite 是否瓶颈应由阶段计时确认。
- 目前只测过 15 万条账本，未完成 15 万张业务图片的真实 I/O、损坏文件、显存和恢复性能验证。

建议优先级：

1. 增加从提交到完成的总时长，以及读取/哈希、解码/缩放、拷贝、模型、写库各阶段计时，区分冷/热启动、单张延迟与批量吞吐。
2. 建立有界预取队列，让 CPU 提前准备下一批，GPU 处理当前批；控制队列占用，保持批次提交与租约检查。合并已读取字节的校验和解码，保留内容身份校验。
3. 在等价图像处理契约下比较 Pillow 与其他解码/缩放实现、线程数或进程方案，依据样本格式和目标 CPU 选择。不要为了速度跳过 EXIF、透明度或内容校验。
4. 加入有界 session 缓存，以模型哈希、设备、精度配置为键；定义淘汰和显存释放，不能无限常驻所有模型。
5. 输入阶段优化后，再比较 ORT FP32、FP16、TensorRT；在 NVIDIA 机器上优先 GPU 路径，Intel CPU 部署另测 OpenVINO/INT8。TF32/FP16/INT8 的数值差异和接受决策需要各自重新验证，不能直接沿用严格 FP32 的校验结论。
6. 对高置信小模型结果直接输出，困难样本再调用强模型，是可评估的后续方案；必须评估整条级联的误接收和总覆盖率，不能把“小模型高分”等同于正确。

当前合成基准不支持许诺某个端到端加速倍数。先完成分阶段测量和预处理优化，通常比直接升级 GPU 或全面改写 TensorRT 更值得优先验证。

## 6. 推荐的下一轮开发路线

| 阶段 | 开发内容 | 验收依据 |
| --- | --- | --- |
| P0：建立可比较的业务基线 | 导入真实样本、来源分组与近重复检查、固定外部测试集；模型选择仅使用训练/验证数据 | 关键类 precision/recall、宏 F1、自动覆盖率和置信区间；至少比较 3 个训练抽样/随机种子 |
| P1：提高有效吞吐 | 全链路阶段计时、CPU/GPU 重叠、有界 session 缓存、减少重复 I/O | 同机同文件集，至少 1000 张代表图片，分别报告冷/热吞吐、p50/p95、内存峰值、错误完整性；基线身份和输出可追溯 |
| P1：补轻量部署档 | MobileNetV4 / RepViT 候选、推理环境拆分、FP16/INT8 按设备选择 | 在业务精度底线下比较模型 MiB、安装 GiB、CPU/GPU 延迟；净环境部署通过 |
| P2：按错误类型提升精准性 | DINOv3/SigLIP 2 对照、简单分类器与部分解冻、教师蒸馏、场景预处理 | 同一评测协议下质量有稳定提升，且成本可接受；没有显著收益的复杂方案不进入默认流程 |
| P2：降低人工成本与扩大规模 | 复核队列、纠错采样、漂移观察、级联推理，15 万张真实文件验收 | 在给定精确率下提高自动覆盖率、减少复核用时；中断恢复不漏项、不重复提交 |

候选应形成准确率、体积和时延的多个可选点。默认轻量模型满足日常批处理，准确性更高的模型处理困难样本，是值得验证的发展方向；是否采用级联由业务实测决定。
