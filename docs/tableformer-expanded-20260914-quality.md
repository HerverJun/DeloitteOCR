# TableFormer 原始结构框扩大实验：结果与下一步

2026-09-14。已完成开发 80 表、验证 60 表、新测试 120 个文档；共 26,085 个目标格，三路共 780 次对应重放。三路使用同一 PP-OCR 输入和同一对应器，模型、阈值及生产默认策略均未修改。

**结论：TableFormer raw 值得作为下一步实验候选主线，RapidTable 继续保留对照。新测试确认其优势，但尚未达到 90% 覆盖门槛。另发现了必须纠正的旧评测解释：PDF annotation 框与铺满行列网格的 cell 框不是同一种边界。此前不能把所有“框偏大”直接归因于模型。**

## 先说明两个评分口径

原封存指标完整保留：沿用上一轮 canonical PDF `cell.pdf_bbox` 转换到 crop 的标注。按该口径，TableFormer 新测试正确定位覆盖率 **33.97%**、提供框达标率 **46.31%**。

在复核验证集“偏大框”时，发现官方生成过程先保存 PDF annotations，再对结构识别图像标签做行列 dilation：相邻边界移动到两者中点，然后以对应行、列矩形的交集生成格框。官方源码：[保存 PDF 标注](https://github.com/microsoft/table-transformer/blob/0bb3ab71c4ec2a8b6c656c67af40eeaf863f306e/scripts/process_pubmed.py#L1725)、[结构网格 dilation](https://github.com/microsoft/table-transformer/blob/0bb3ab71c4ec2a8b6c656c67af40eeaf863f306e/scripts/process_pubmed.py#L1761)。该文件 SHA、commit 和下载回执已保存。

PDF 的 `pdf_bbox` 也不是 `pdf_text_tight_bbox`：它按原始行列范围对齐，但仍可保留行列间空隙。新测试官方网格面积相对原 PDF cell 框的中位数是 **2.05 倍**。因此，正确覆盖空隙的结构框也可能在旧口径下 IoU<0.5。

为此增加独立的官方网格补充复核，**先重建开发/验证标签并评分，再封存补充规则，最后打开新测试评分**。重建仅使用 canonical 行列、跨度和既有仿射转换，不读取模型框或 OCR 坐标；不改 IoU≥0.5、身份判断、失败分母或对应阈值。三路输出框的数量和坐标完全相同，只改变独立标签的边界约定。

时间边界必须明确：补充规则是在测试模型推理完成后、任何测试评分前锁定的协议修订。它不是从实验开始就预注册的主指标；原主指标与补充指标一并交付。后续开发应将正式采用的边界约定提前固化，再用新的独立测试确认。

## 新测试：120 文档、11,667 格

| 候选来源 | 原封存覆盖率 | 原封存提供框达标率 | 官方网格覆盖率 | 网格错位率 W/A | 网格提供框达标率 C/A |
|---|---:|---:|---:|---:|---:|
| Paddle | 6.15% | 48.48% | 11.96% | 1.283% | 94.19% |
| RapidTable | 6.21% | 36.13% | 10.79% | 0.599% | 62.82% |
| TableFormer raw | **33.97%** | **46.31%** | **73.04%** | **0.070%** | **99.58%** |

原封存错位率：Paddle 14/1,481=0.945%，RapidTable 10/2,004=0.499%，TableFormer 5/8,557=0.058%。网格评分下分别为 19、12、6 个错位。框的数量 A 在两种评分中保持 1,481 / 2,004 / 8,557；变化来自独立 GT 对目标身份和边界重合的判定。

网格口径的正确数分别为 **1,395 / 1,259 / 8,521**。TableFormer 在 **120/120 表**至少有一格正确，其中 25 表覆盖率≥90%；Paddle 为 25/120 表，RapidTable 为 81/120 表。逐表平均覆盖率为 72.57%，不只是少数大表抬高总数。

TableFormer 网格覆盖率的文档 bootstrap 95% 区间为 **68.74%–76.90%**；错位率区间 0%–0.207%，提供框达标率区间 **99.01%–99.90%**。与 RapidTable 相比覆盖增加 **62.24 个百分点**，成对文档 bootstrap 区间 **57.32–66.86 个百分点**；同目标新增正确 7,347 格，失去 85 格。相对 Paddle 新增正确 7,187 格、失去 61 格。

这支持候选来源的优势，也说明它没有逐格包含其他路线的所有正确结果。不能用测试逐格挑选最优路线来报告更高覆盖。

## 扩样后的稳定性

| 划分 | 目标格 | Paddle 原 / 网格覆盖 | Rapid 原 / 网格覆盖 | TableFormer 原 / 网格覆盖 |
|---|---:|---:|---:|---:|
| 开发 80 表 | 8,488 | 2.38% / 4.25% | 8.48% / 16.03% | 35.04% / 74.18% |
| 验证 60 表 | 5,930 | 3.47% / 11.69% | 4.60% / 7.27% | 28.03% / 66.17% |
| 新测试 120 表 | 11,667 | 6.15% / 11.96% | 6.21% / 10.79% | 33.97% / 73.04% |

上次开发前 12 表的 TableFormer C=654 在本轮原口径下原样复现。扩至全开发集后，原口径覆盖由小样本的 48.88% 降为 35.04%，因此不能把 12 表的结果外推。三种划分、两种口径都确认了候选优势。

| 新测试分组 | 目标格 | Paddle 覆盖 | RapidTable 覆盖 | TableFormer 覆盖 | TableFormer 提供框达标率 |
|---|---:|---:|---:|---:|---:|

TableFormer 在这三个分组中没有出现评分错位，但分母有限，不能解释为没有风险。合并格、重复值仍明显低于总体覆盖，是后续开发需要单列验收的重点。

## 失败发生在哪里

下面按目标格给出互斥统计，全部加总为 11,667；“对应器接受”与“独立评分正确”分开。

| 新测试网格口径结果 | Paddle | RapidTable | TableFormer |
|---|---:|---:|---:|
| 正确定位 | 1,395 | 1,259 | **8,521** |
| 推理失败 / 无检测候选 | 0 | 0 | 0 |
| 结构不一致拒绝 | 0 | 204 | 0 |
| 表身份不确定 | 2,915 | 1,809 | 0 |
| 文字锚点失败 | 2,481 | 2,868 | **1,638** |
| 局部对应失败 | 4,785 | 4,768 | **1,454** |
| 几何约束拒绝 | 5 | 14 | 18 |
| 提供框边界未达标 | 67 | 733 | **26** |
| 错位 | 19 | 12 | 6 |
| 身份并列歧义 | 0 | 0 | 4 |

“检测失败 0”只适用于已提供表格裁剪的本实验，不能解释为整页表格检测召回率 100%。主阶段是首个拒绝原因，也不代表不存在其他结构错误。

TableFormer 的文字锚点失败包括重复值歧义 **1,374 格**、无空格锚点 **264 格**；局部对应失败包括无局部锚点 **1,435 格**、顺序冲突 11 格、候选复用 2 格、候选预算超限 6 格。几何拒绝的 18 格均为非连续组。26 个边界未达标框中，23 个相对网格偏大、3 个为偏移或形状问题。

与之对应，原封存口径把 TableFormer **4,580 格**记为边界不达标。验证集中这些未达标输出都是单个原始框，不能归咎于局部对应将多个框拼成过大并集。官方网格复核说明，旧标签口径是这批“偏大”判断的重要来源。

原始 TableFormer 单框在 GT 辅助的一一分配诊断中，网格 IoU≥0.5 可覆盖 **11,208/11,667=96.07%**；当前实际对应只有 73.04%。该差距提示应优先研究如何用可靠锚点找回已有正确候选。此 oracle 忽略文字、跨度和候选并集，不是可上线精度，也不是所有未来算法的绝对上限。原口径下对应 oracle 是 43.34%，同样受边界定义影响。

## 耗时与验证

RTX 4070 Ti SUPER；GPU 推理串行，CPU 对应使用同一 service Python。以下均为新测试 120 表，冷加载不计入逐项分位数。

| 阶段 | 中位数 | P95 |
|---|---:|---:|
| 共享 PP-OCR 每项墙钟时间 | 0.623s | 0.959s |
| Paddle 候选内部计时 | 0.192s | 0.379s |
| RapidTable 候选计时 | 0.117s | 0.387s |
| TableFormer 候选计时 | 0.525s | 1.120s |
| Paddle CPU 对应 | 15.65ms | 51.31ms |
| RapidTable CPU 对应 | 13.69ms | 58.12ms |
| TableFormer CPU 对应 | 14.55ms | 68.95ms |

TableFormer 包含文件校验/读取的整个重放 P95 为 75.83ms。候选模型较慢，最终 CPU 对应耗时与其他路线处于同一量级。各模型计时起止边界不同，不能将这些数值当作整份文档端到端性能；详细墙钟/冷加载数据见 audit。超过预算的项照常保留，不靠重跑挑选最好成绩。

共核验 1,040 个提供方产物回执，其中复用开发/验证 420 个 OCR/Paddle/Rapid 产物、新跑 TableFormer 开发/验证 140 个、新测试四提供方 480 个；全部成功。780 个对应产物全部完整，六份双口径评分全部 complete。三路 OCR 哈希一致，原选择封存中的对应源码/阈值及评分代码未改。8 项针对性测试通过，覆盖外来 OCR/图像拒绝、原始框语义、封存缺失/篡改、失败分母、合并格中点边界和不支持的行序；没有为研究脚本重复运行整个产品回归。

## 下一步开发顺序

1. **先把标签边界约定纳入正式评测契约。** 明确区分文字范围、PDF 行列范围、完整网格范围；保留旧指标作历史追踪，完整格定位采用预先确认的网格标签。用合并格、空格、宽列间距和有框线实例做人工抽审，并对接官方结构图像标签交叉验证。不要先根据旧“偏大”统计去缩小模型框。
2. **接入可选择的 TableFormer raw 几何提供方。** 复用本轮已验证的转换与坐标契约，保留原始预测、来源哈希、原始编号和上下文；继续使用既有共享 OCR、对应器和降级策略。保留 Paddle/Rapid 对照，记录候选推理成本和缓存命中；先作为实验选项，覆盖未达 90% 时不改默认。
3. **对应器研发优先处理重复值与局部锚点。** 在开发集分别针对 1,374 个重复歧义和 1,435 个无局部锚点所代表的类型设计规则：利用独立邻居、行列顺序、跨度与排他归属，保留候选歧义和拒绝。合并格与空格分别验证，不降低 token 包含率、margin、IoU 或来源要求来换覆盖。新对应器仍应与固定 TableFormer raw + 现有对应器做对照。
4. **完成真实输入轨，再用新测试验收。** 本轮固定 reference edit，尚未包含 OCR/实际采用结构错误传播。后续加入原生 PDF、扫描页、中文和整页多表，并分别统计候选、结构、锚点、框及时间。本轮 120 文档现已曝光，后续调参不得再将其称为新封存测试。

本轮支持继续开发 TableFormer raw 的实验接入与局部对应，不支持宣布 DeloitteOCR 已达到整份文档生产质量，也不构成与完整 Docling 产品的端到端排名。
