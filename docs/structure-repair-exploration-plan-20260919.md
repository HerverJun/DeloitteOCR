# 复杂表格修复链路：探索计划

日期：2026-09-19。状态：**计划，尚未执行**。

配套机器任务：[structure-repair-exploration-tasks-20260919.json](structure-repair-exploration-tasks-20260919.json)。

## 要回答的问题

能否在保留用户当前已采用文字的前提下，安全地修正复杂表格中的少量行列、合并关系和跨度？如果能，Luna 的看图判断是否比同一套本地方案增加净收益？

这是一轮有退出条件的探索。交付可以是有证据的小范围改进，也可以是“目前证据不足，继续保留人工复核”的结论。不得把“建议能够生成”当成“建议正确”，也不得为了增加 API 调用数放松文字保全。

执行顺序：**确认阻塞原因 → 固定计分和保全契约 → 小范围本地原型 → 同输入消融 → 冻结方案 → 模型比较及新样本验证 → 有条件集成**。

本计划的“保留文字”表示结构操作不暗中改字，不表示当前 OCR 文字一定正确。确有错字，应通过独立的文字校对流程处理；本轮不把两种修改混为一次结构采用。

## 不可突破的保全契约

1. **当前采用内容是结构修改的内容基线。** 保存修订号、单元格字面值、已有来源、人工编辑和人工清空状态。保全比较使用原始字面串；不能用大小写折叠、数字转换、破折号替换或 Unicode 归一化掩盖改字。
2. **内容身份与几何证据分开。** 可为原本无 ID 的采用单元创建稳定内容身份，但不得据此声明它有文字框或完整格框。另一引擎的 OCR 内容只能提供独立证据，不能直接覆盖当前采用值。
3. **变更记录必须能追溯每一份内容。** 不能仅比较字符串集合：重复金额要核对身份、数量、归属和顺序。现有修订内，各候选使用同一内容命名空间；不能让相同短 ID 在不同候选中表示不同内容。
4. **合并保留组成片段，拆分需要真实边界。** 合并格保留原片段、顺序及显示分隔规则。拆分需有可核验的片段边界和归属；只有整格字符串时，不按字符长度猜子框或自动切分。无法证明则保持原结构或交给人工。
5. **结构补丁通过全表校验。** 检查完整网格、矩形跨度、重叠、文字归属、人工绑定、图像版本及修订。局部成功不能绕过全表冲突。行列插入造成的后续索引变化必须纳入影响映射，不能谎称这些格完全未受影响。
6. **表题和脚注仍是文档内容。** 依靠独立表区、版面证据和阅读顺序区分网格与表外内容；不能按“第一行像标题”就删掉，也不能靠参考标签生成生产边界。证据不足时拒绝扩大表区。
7. **不确定继续不确定。** 未知空值不等于真实空白；对称重复值不猜归属；财务合计只提供疑点，不能作为改字或结构正确的唯一证明。
8. **采用仍需用户操作。** 打开页面不外发，模型只能选择已通过硬校验的补丁、保持原样或弃权。接受后可撤销；拒绝、过期、取消和迟到响应不得改变结果。

若发现现有代码违反以上契约，先保存最小失败案例，修复或隔离该分支。不能把保全失败记成普通质量缺口后继续发布。

## 探索假设与停止规则

| 假设 | 最小实验 | 支持它的证据 | 不支持时的去向 |
| --- | --- | --- | --- |
| H0：重放忠实反映产品阻塞 | 对同一小批输入对比应用路径与重放路径的提供方、候选、修订及拒绝原因 | 逐层结果和语义一致；输入、来源和处理动作可追溯 | 修正实验工具，在新 run 重算；不改产品门槛迎合错误重放 |
| H1：采用文字与候选骨架可以分开 | 用现有来源／人工绑定／独立几何建立保留原字的对应；与旧 `preserve_values` 对照 | 出现原来不可用、现在能证明正确且保全文字的建议 | 若普遍缺几何，输出缺证据说明；只在具备证据的输入类型继续 |
| H2：局部修改比现有方案更稳 | 比较现有局部方案、改进局部方案和整表替换的同输入结果 | 正确修复增加，未改区域及原本正确内容受到的影响减少 | 保留原局部实现或保持原样；不把补丁无限缩小来隐藏失败分母 |
| H3：表区约束能防止标题／脚注侵入 | 真实多表页面、表题、脚注、多层表头及无边框表混合回归 | 阻止错误扩张，同时保留合法多层表头；文档内容无丢失 | 边界不确定时关闭自动生成该类补丁，保留原图人工复核 |
| H4：Luna 能进一步筛选合法建议 | 固定本地方案与“同一本地方案＋Luna”配对 | 通过产品硬校验后的全量净收益有改善，且不破坏文字保全 | 保留本地方案；API 只提供解释或维持原实验范围 |

每个机制先跑基线，再最多尝试 3 个有明确依据的变体。每个变体先限制在一个小批次；纯评测运行使用超时和断点。程序错误修复可重跑受影响检查，但不得把持续调参改名为错误修复。

研究继续条件：在真实开发材料中找到至少 5 个可证明正确的局部修复，跨至少 3 份文档，并通过全部内容保全检查。这个门槛仅用于判断是否值得继续，不构成正式质量通过。若在已约定的三种变体后仍达不到，交付负结果与缺证据类别，转向可执行的其他假设或结束对应分支。

## 任务与依赖

### 第一阶段：先把问题测准

- [ ] **T01｜建立隔离 run，核对输入和重放工具。** 比较小批应用路径与历史重放路径；核对 TableFormer／Paddle 来源名称、图像版本、来源 ID 和结构工具状态。所有导入接口先确认是否消费临时文件；只传副本。运行前后校验原始输入哈希，禁止复现此前误传源路径的问题。
- [ ] **T02｜建立逐层阻塞漏斗。** 分别统计输入数、采用表数、候选表数、可辨认对应数、通过网格数、通过文字保全数、可形成局部补丁数、满足发送预算数、模型调用数及最终可采用数。拒绝原因保留主因、辅因和影响格；候选级与表级分母分开。抽查具体实例，区分正确拦截、过度保守及工具错误，不把同一候选的多种原因重复计为多次失败。
- [ ] **T03｜固定数据和评测协议。** 复用历史材料作回归；自主寻找中文财务原生 PDF、真实扫描／照片及整页多表的公开材料。初轮探索最多 45 分钟，以 10–20 张有资格的真实开发表为启动目标。另按文档／模板预留约 10 份新文档、20 张表、1,000 个目标格作小规模确认；缺类别如实保留缺口。冻结分组、曝光规则、身份关联方法、随机检查、指标和继续条件，然后再看确认组结果。
- [ ] **T04｜冻结契约与失败用例。** 将上述八项契约转成有意义的检查。至少覆盖同值不同格、人工改字、人工清空、一个片段跨候选分裂、表题／脚注、多层表头、索引位移、整页多表、图像变化和组合补丁冲突。合成例只用于机制与不变量，不充抵真实质量样本。

T01/T02/T04 有产物后可开展原型；无需等待正式数据规模。T03 的协议部分必须在方案效果评测前完成。

### 第二阶段：让本地建议能够安全落地

- [ ] **T05｜测量现有建议的可修复空间。** 在开发组确认：有多少表本来就不需要改、有多少没有正确候选、有多少候选结构可用但缺内容对应、有多少只是无法满足现有预算。可用参考标签分析候选上限，但必须标记为离线诊断；这些标签不能参与候选生成或生产路由。先判断瓶颈是否真值得改。
- [ ] **T06｜试验“保留采用文字”的对应层。** 优先扩展 `preserve_values` 与现有来源记录。探索同源片段、独立几何／人工绑定、经证据约束的顺序和邻接关系三类路径；唯一同值只能作为候选线索，不能作为重复值身份的充分证明。无可靠定位输入单列降级。记录每次保留、迁移、合并及拒绝的依据。
- [ ] **T07｜试验局部结构补丁。** 从已有 `local_variants` 扩展，优先单个合并／拆分区域或表头局部变化。补丁显式记录前置修订、受影响内容身份、槽位变换、保留片段及前后状态。独立证明后才允许组合；组合必须重新做全表校验。冻结补丁大小／数量限制并记录依据，禁止逐案例扩大到能命中答案。
- [ ] **T08｜试验表区和上下文约束。** 使用独立检测区域、PDF 矢量／原生文字或已有可靠定位；区分 caption、footnote 和网格。测试标题入格、跨表吸附、表区裁掉真正表头等相反错误。缺可靠区域时保留整页上下文并拒绝无法解释的扩张，不以裁掉难点获得更好分数。
- [ ] **T09｜完成本地消融并作继续决定。** 在相同输入、文字和采用基线上比较：现有实现；仅新增内容对应；对应＋局部补丁；对应＋局部补丁＋边界约束。同时保留现有局部算法作为对照。输出内容不变量、全量净变化、建议覆盖、影响范围、耗时和逐例负结果。冻结一个候选实现，或记录假设未获支持，不继续围绕同一批答案调参。

### 第三阶段：判断模型有没有额外价值

- [ ] **T10｜构造忠实的模型输入。** 只从通过产品硬校验的同一批补丁生成证据。当前状态必须作为明确的“保持原样”选择；无法判断用“弃权”表示，二者均不改表。跨候选统一内容 ID，保留完整片段、来源和变换。遵守既有图片、候选数、字符数、输出长度和超时预算。需要压缩时，一一映射必须可逆并经端到端检查；不能通过裁去未归属内容、只展示成功区域或事后补齐响应 ID 获得通过。
- [ ] **T11｜执行 Luna 盲评与同输入本地对照。** 固定 `gpt-5.6-luna` 标识、可验证的推理设置、提示词、随机种子和请求哈希。先用小批合法候选验证；以每表一次、独立上下文为主，不让后续案例看到评分或先前答案。使用真实 API 时保存脱敏服务身份及用量；通过 Codex 子 Agent 模拟时使用不继承开发历史的上下文，并明确不能测得 API 费用／端点时延。无合法候选则报告 0 次触发；另做诊断必须单列，不能计作产品增益。失败不自动重发。
- [ ] **T12｜在未曝光的小规模确认组验证。** 在冻结代码后一次性比较原实现、新本地方案、新本地方案＋Luna。保持同一采用基线和候选池；本地候选排序与“保持原样”规则提前固定，不能逐样本按答案挑优。采用统一、事先定义的模拟人工采用规则，并明确这是反事实结果；真实人工效果单独测量。保留失败、无候选、超时和弃权，输出按文档／模板分组的区间。看过逐例错误的材料立即转入回归；修改方案后另建确认组。

若 T09 判定缺乏可安全采用的建议，T10 输出输入资格报告，T11/T12 记录无法进行模型增益验收的原因，继续完成报告及可用工程工作。不得以绕过门控的诊断替代这三项。

### 第四阶段：有条件地集成与交付

- [ ] **T13｜接入现有复核界面。** 对有证据支持的实现，清楚显示“修改哪里、哪些原字保留、为什么不能采用”；默认展示最小可用修改范围。复用现有接受、拒绝、保持、撤销和来源导出，核对金额／编号／空值／表外文字。仍由用户决定采用，不另造一套编辑器。
- [ ] **T14｜完成受影响回归。** 验证保全、并发修订、取消／过期、组合冲突、采用／撤销／重做、Excel／JSON／PDF 导出回读，以及长表预算和降级。对坐标语义改变检查导航与 PDF 文本层。先针对性检查，最后在当前源码路径优先的运行时做完整后端、前端和构建；浏览器按既有规则收口。工程失败必须修复或隔离后验证，不能用质量未测遮盖。
- [ ] **T15｜保存可复现证据和结论。** 每个假设分别标记 supported／rejected／inconclusive，记录工程、质量、模型模拟、真实服务四种结论。保存代码／配置／提示词／输入／标签／输出哈希、逐例结果、所有失败及执行命令。报告哪些输入能用、哪些仍须人工、相比现有实现是否值得保留。无可用改进也要交付完整负结果，不虚构版本升级。
- [ ] **T16｜按执行范围交付实验产物。** 默认交付源码改动、说明、受限结论和证据索引。若要求新版离线包，则独立生成新版目录与 ZIP，包内冒烟、逐文件 CRC／SHA256 校验通过后记录真实路径；不覆写 0.13.0rc1 包。若没有可发布实现，提供明确的研究结论，不重打相同代码冒充升级。

## 计分与通过条件

### 三层结论必须分开

| 层次 | 要求 | 可以说明什么 |
| --- | --- | --- |
| 工程可用 | 全部内容保全、合法性、采用／撤销和导出检查通过；每次失败都能解释 | 功能按约定工作，不能说明准确率已经提高 |
| 探索有希望 | 达到跨文档小样本继续条件；确认组未出现保全违规，纠正／改坏及区间完整报告 | 值得扩大研究；零观察到改坏不等于真实风险为零 |
| 正式质量通过 | 达到前轮冻结的独立规模与质量目标，并有对应类别证据 | 才有资格讨论该类别的默认启用；本轮小确认组不能替代正式验收 |

正式目标继续引用 [complex-table-todo-20260919.md](complex-table-todo-20260919.md)：至少 100 份独立文档、120 表、6,000 格，以及合并、重复、空白、原生／扫描／照片等分组要求；完整格定位 ≥90%、错位率 ≤1% 等是原有对应指标，不能套用到“结构＋文字”新指标上。性能继续观察既有 200ms 对应预算，同时单列新补丁验证和端到端成本，不通过换计时范围宣称达标。

### 本轮必报指标

- **逐层漏斗**：包括所有输入和未触发的表；可发送率、可采用率与建议正确率分别报告。高拒绝率不自动视为缺陷，需查明其原因。
- **内容保全**：遗漏、额外、重复、字面值变化、人工清空恢复、未改区域内容变化及不可追溯的归属变化，均按固定身份比较。保全违规数必须为 0。
- **结构和文字**：行列／跨度正确率与“结构＋文字同时正确”分别计分；计分用的归一化规则必须在 T03 冻结，并同时报告原始字面保真，不能把格式近似等同于无改字。
- **身份与行位移**：以冻结的独立目标身份关联；没有对应身份的格计为未匹配。另报严格槽位指标，避免插入一个标题行时只给出大量错格，却不说明错误来源与影响范围。
- **净收益**：纠正、改坏、仍错、保持正确、保持原样、弃权；全量与触发范围同时报告。按文档／模板分组计算区间，区间跨 0 时不声称稳定正收益。
- **整表与高风险内容**：结构和关键值全部正确的表数、原本全对而被改坏的表数；金额／编号／合并／空白／重复及整页多表单列。
- **修改成本与资源**：每次建议影响格数、最大伤害范围、人工操作数；真实操作时间与脚本耗时分开。记录本地时间、内存、候选预算及模型使用量；没有真实费用就写未测。

本地方案和加 Luna 的方案使用相同的保全标准。API 即使能增加可采用数，只要收益不稳定，也可保留为未默认启用的实验，或结束该分支。

使用新目录 `build/structure-repair-<date>-<nn>/` 与 `audit/structure-repair-<date>-<nn>/`。本计划与任务 JSON 保持静态计划；实际状态写入 run 目录。

状态使用 `pending`、`running`、`done`、`done_with_gaps`。研究假设被否定不等于执行失败，但必须有支持否定的证据。工程硬约束失败不允许记为工程通过。条件不成立的任务可交付不适用说明，质量和真实服务保持未测，不能假装执行了测试。

公开材料不足时切换来源，每来源最多 3 次有区别的尝试；后续数据批次最多 30 分钟。无人提供私人文档、没有人工操作员、缺真实 API 凭据均不阻塞本地工程和模拟能力验证。生成式请求不自动重发；并发不得绕过既有 GPU／任务锁。

运行时先查看实际 `--help` 和源代码契约。不要直接复制旧脚本的固定路径、自动覆盖或消费输入行为。现有服务运行时可由交付回执定位；系统 Python 曾缺 `pillow_heif`，不能将环境错误误判为产品失败。每个实验和修正重跑使用新名称，保存旧负结果。
