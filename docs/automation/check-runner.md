# Frozen check runner

`scripts/run_check.py` executes one command from the run's `checks.json`. The state must reference the same frozen plan/check digest and an absolute registered runtime. A task is first claimed with `scripts/state_tasks.py claim --run-root <run> --task Txxx`; after implementation, use `freeze` with explicit `--source repo:relative/path` and optional existing `--output repo:relative/path` entries. Required task outputs are checked at the end. `run_check.py --run-root <run> --task Txxx --check check_id` uses the recorded attempt. A task with several checks remains `verifying` while the next required check runs. Use `recover` to inspect a running/verifying attempt before deciding whether any work needs repeating. Once all receipts and acceptance criteria are reviewed, `state_tasks.py complete` validates a candidate done state through the planning validator and atomically closes it. A failed task gets a new attempt through `state_tasks.py retry`; old logs and receipts remain.

Commands are arrays copied from the frozen check definition. The only permitted argument expansion is `{run_root}`. Repository cwd is resolved beneath its registered root; runtime is an existing absolute path in `state.runtimes`. `.cmd` arguments are limited to a simple literal character set before Windows launches the registered batch entry, so filenames and untrusted shell metacharacters never enter its command line. The check environment is constructed from a small allowlist, with a per-check profile/AppData, TEMP/TMP, pytest basetemp and JUnit XML under the run. It does not inherit external credentials, Python/Node injection variables, or the user's home configuration. OCR gets its registered worktree `src` as PYTHONPATH; classification gets run-owned `ICP_DATA_DIR`. T005's auxiliary interpreter is recovered from its attested runtime record into `state.runtimes.fixture_python` with its lock SHA256, then checked before use. This is an explicit migration of a known local resource identity, not a guessed directory.

On Windows, a trusted isolated Python broker waits for a command message on stdin. The runner creates a Job Object with kill-on-close and no breakaway permission, starts the broker with `-I -S`, records its PID/creation time from the process handle, assigns it to the job, then sends the frozen command. The broker and all descendants are bound to that job. A timeout, missing terminal broker marker, nonzero child exit, or descendants surviving the direct child causes failure; the runner terminates only its own job handle and waits for it to empty. If assignment fails, it terminates/waits the exact broker Popen handle while the broker remains gated. It never kills by port, PID lookup or a stale PID snapshot. A test keeps an unrelated sentinel alive while verifying both timeout and grandchild cleanup.

The runner exclusively creates `attempts/Txxx/NNN/checks/check_id/run-001/`. It saves source/existing-output hashes before launch, reads them again afterward, checks every declared task output, and hashes newly produced outputs. A pytest result requires a runner-controlled JUnit XML report with passed assertions and zero failures/errors; unittests require the actual terminal `OK` and nonzero executed tests; other test scripts require a positive terminal summary and no failure summary anywhere. Exit zero alone cannot pass. Raw stdout/stderr and snapshot files are never overwritten. Each receipt binds the plan digest, source inputs and final outputs; an already-signed receipt's binding must remain the same when another check runs. An OS file lock, state revision comparison, old revision snapshot and atomic replacement serialize updates. A racing invocation leaves diagnostic evidence unattached and cannot mark another writer's state failed.

`scripts/import_legacy.py` verifies the full current T001–T005 state through the original planner, checks file identities and receipt/log bindings, and writes a read-only index labelled `manual_pre_T006`. It preserves original receipts, logs, timestamps and commit identities. It does **not** claim those checks were executed by this runner. The first fully automatic check is T006's own `harness`; later producers supply their check commands as their tasks are implemented. Neither protocol simulation nor a successful portal build counts as a real module HTTP/GPU/device check.

Shared entry points can change after an earlier task was marked done. Run the original planner's `verify-state`/`next` to identify stale done records. If a downstream task is active, invoke `state_tasks.py suspend --run-root <run> --task Txxx` first; this checkpoints its status and bindings as `blocked`, freeing the only active slot without incrementing its attempt. Reverify stale done ancestors one at a time with `state_tasks.py reverify --run-root <run> --task Txxx`; each archives the former record and receipt hashes under `reverify-history/Txxx/revision-NNN.json`, increments the attempt within `max_attempts`, and clears only the current task's bindings. Freeze current files, run all required checks, and complete. Completion accepts the target's new valid receipt while other preexisting stale tasks are still reported; it rejects new invalid tasks. When the ancestors recover, `resume` the checkpointed descendant and continue its current attempt. If its own bound inputs changed, start a controlled new attempt subject to its attempt limit. At no point are two tasks active. Old revision snapshots, receipts, logs, and archives remain historical evidence, not current proof.

`scripts/real_cli_smoke.py --planner <run>/workspaces/ocr/scripts/platform_plan.py --evidence-root <new-directory>` makes a separate valid small run. Its transcript records the unmodified original planner's hash and real `validate`, `init-state`, `next` (through claim), `verify-state`, claim/freeze/check/check/complete calls, then a deliberate source drift and full reverify. It preserves both attempt directories and the former receipt hashes. This demonstration is separate from the production T006 state.

`scripts/serial_reverify_smoke.py` accepts the same arguments and demonstrates two stale done ancestors while a descendant is active. Its 29-step CLI transcript includes the real validator's exit-1 stale report, suspend, one-at-a-time ancestor reverify and completion, attempt-limit refusal, resume, and a descendant check that reuses an ancestor's frozen producer command. A producer identifies who implemented a shared check; the consuming task must list it in `required_checks` and have the producer among its dependencies. Both smoke runs create independent valid run packages and leave the production state untouched.
