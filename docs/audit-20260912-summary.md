## 第一优先级：保护草稿、队列和项目数据

### 1. 保存失败后，再次加载失败会丢掉草稿的待保存状态

**已在真实 Edge 与当前服务中复现。** PUT 保存返回 409 后，点击“重新加载”，再让 GET 返回 503。画面仍保留本地文字，但再次点击“重试保存”没有发出任何 PUT；切换到另一张图片再回来，修改丢失。

原因是 [useEditor.ts:132](C:/Users/A/Desktop/OCR/frontend/src/useEditor.ts:132) 在 GET 成功前清空 `pending`。应在成功取得新结果、明确处理本地草稿之后替换状态；失败仍保留脏状态、重试保存和离开保护。放弃修改的动作也应明确命名。

### 2. 队列线程退出后，健康接口仍报告 ready

**已用隔离故障注入复现。** 数据库领取任务抛出 `database is locked` 后，线程退出而 `/api/health` 仍为 `ready`。这是异常恢复缺陷，不代表日常领取任务必然失败。

[task_queue.py:64](C:/Users/A/Desktop/OCR/src/ocr_workbench/task_queue.py:64) 的主循环没有处理 `claim()` 等步骤向外传播的异常。应区分可恢复故障与不可恢复错误，记录最后错误及线程存活状态；采用有限退避或明确恢复入口，并把队列故障反映到界面和健康检查。

| 问题 | 证据强度与影响 | 改进方向 |

| 图像写盘失败后残留无数据库记录的文件 | 磁盘满故障注入后图片记录为 0，但原图残留于项目目录。 | 用暂存目录完成文件生成与校验，数据库提交失败时补偿清理；增加可审查的孤儿文件维护机制。 |

## 第四优先级：建立专业批量工作流

这些属于能力提升，不能混同为当前已有功能全部失效。

- **复核进度**：把识别任务状态与“待校对 / 已确认 / 有疑问”分开，确认绑定输入版本及采用结果；增加下一张待校对导航、筛选和仅导出已确认结果。
- **交付追溯**：当前逐图 Excel 只有 `0001.xlsx` 等名字，汇总只有 `Table 1` 等工作表名。附来源索引，记录原图、图像版本、引擎、结果 ID、校对 revision 与工作表映射。
- **同条件模型比较**：默认按同图像版本、同批次分组，展示输入处理和人工校对状态；用对齐文本差异，并补充单元格、行列与合并关系差异。
- **人工结构修复**：增加新建表格、删除整表和 TSV 区域粘贴，沿用已有撤销历史并保留文本型编号。
- **键盘操作**：补齐 Shift+方向键矩形选区、图像坐标输入/微调、结果页签选中语义；以真正完成任务作为无障碍验收。
- **待核对提示**：仅对模型确实提供的置信度做可疑项标记与导航；没有分数时显示未知，不把不同引擎分数直接当成统一准确率。

## 工程扩展性与交付边界

工程代理在合成的 1000 张图片、4000 个任务项目上测得一次完整快照约 **2.98 MB**，当前界面每 1.2 秒取回一次，相关查询为全表扫描并临时排序。这证明传输、解析和渲染成本会随历史积累增加；本次没有做大项目浏览器性能分析，不能断言已经发生卡顿。建议先补项目查询索引，再采用变化版本号、增量更新/分页和按需渲染。

10 万字符文档连续 50 次微小校对后，SQLite 文件由 372,736 字节增至 5,394,432 字节；这是保存完整历史快照的可测成本。可以评估分组历史、压缩或增量保存，并保留明确的审计与撤销能力，避免直接静默删历史。

启动检查目前将 GPU/引擎就绪与进入整个工作台绑定。后续可以增加“仅校对与导出”模式，让兼容的基础运行时在 GPU 不可用时仍能处理已有项目。此建议不要求放松完整性检查或启动不可信的引擎代码。

数据库版本兼容属于后续升级与回退的 P3 改进。在隔离数据库中，将 `user_version` 设为 99 后，当前 Store 正常打开并把版本号改成 4。这里只证明版本标记被覆盖，没有模拟未来数据库真实结构，也不能据此断言现有用户数据已经损坏。[store.py:33](C:/Users/A/Desktop/OCR/src/ocr_workbench/store.py:33) 应先读取版本再做逐级迁移，高于支持范围时拒绝写入或进入经过验证的只读路径；备份及回退规则与升级说明一并提供。

README 已明确另一台干净 Windows、内网 A4000 与真实内网样本尚未验收。本轮没有补做这些外部机器验收，也没有重新验证四引擎推理精度、速度或离线发布包。
