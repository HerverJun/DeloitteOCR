## 1. P1 · 队列线程异常退出后，服务仍报告正常

**性质：已复现缺陷。**

**位置：** [task_queue.py:63](C:/Users/A/Desktop/OCR/src/ocr_workbench/task_queue.py:63)、[task_queue.py:77](C:/Users/A/Desktop/OCR/src/ocr_workbench/task_queue.py:77)、[service.py:111](C:/Users/A/Desktop/OCR/src/ocr_workbench/service.py:111)。

`run()` 仅用 `finally` 卸载引擎，没有异常恢复边界；`step()` 的 `store.claim()` 和最初的任务状态读取位于任务级 `try` 之外。失败状态写库、卸载引擎本身抛错也可能穿透该边界。健康接口固定返回 `ready`，队列状态没有工作线程存活或故障字段。

**触发与影响：** 对 `claim()` 注入一次 `sqlite3.OperationalError("database is locked")`，队列线程即退出；健康接口仍返回 `{"status":"ready"}`，队列看似空闲。实际遇到数据库 I/O、锁定等异常时，后续新任务可能一直等待，用户看不到“队列已停止”的诊断。此处证明的是故障处理行为，未声称常规使用必然遇到数据库锁。

**改进：** 在队列最外层捕获可恢复错误，记录结构化故障，做有上限的退避重试；持续失败时停止接收或明确挂起新任务。健康/状态接口返回工作线程存活与最近故障。恢复需复核任务状态，避免直接重复执行已提交结果。

**验证：** 注入一次临时 claim 故障后，恢复存储并提交任务，确认能继续完成；持续故障时应显示队列异常；再补卸载/失败状态写入异常，确认既不会静默退出，也不会重复生成成功结果。

## 2. P2 · 图片导入及版本写入失败会留下数据库未登记的文件

**性质：已复现缺陷。**

**位置：** [imaging.py:169](C:/Users/A/Desktop/OCR/src/ocr_workbench/imaging.py:169)、[imaging.py:279](C:/Users/A/Desktop/OCR/src/ocr_workbench/imaging.py:279)、[imaging.py:89](C:/Users/A/Desktop/OCR/src/ocr_workbench/imaging.py:89)。

导入先创建项目图片目录、移动原图并写 PNG，再开启数据库事务；版本转换同样先保存最终路径后写库。这些路径缺少异常清理或可恢复的文件提交记录。服务层最终只删除最初的 `inbox` 路径，已经移动出去的原图不在该清理范围内。

**触发与影响：** 模拟 `Image.save()` 因磁盘不足失败后，数据库图片数为 0，项目目录仍存在 `images/<id>/original.png`。用户看到导入失败并重试，会继续留下看不到的文件；处理版本写盘/写库失败也有相同模式。完整项目清理可以带走其中部分文件，但无法在保留项目的同时解释或回收这些孤儿。

**改进：** 使用暂存目录和明确的提交边界：文件写入完成、校验后再登记；失败时清理本次新文件。为进程强杀场景补启动时的孤儿识别/恢复，并确保只处理本次操作拥有的路径。将已有项目删除的恢复思路复用于导入与版本创建。

**验证：** 分别在原图移动后、PNG 写入中、数据库插入/提交时注入异常；恢复后应只有完整的可见图片，或没有此次新增文件。重试成功应只生成一份图片记录和一组受管理文件。

## 3. P2 · 常驻轮询随全部图片、版本和历史任务持续放大

**性质：有测量依据的扩展性风险；未证明当前小项目卡顿。**

**位置：** [service.py:140](C:/Users/A/Desktop/OCR/src/ocr_workbench/service.py:140)、[App.tsx:158](C:/Users/A/Desktop/OCR/frontend/src/App.tsx:158)、[store.py:36](C:/Users/A/Desktop/OCR/src/ocr_workbench/store.py:36)。

前端无论是否仍有任务，每 1.2 秒获取整个项目，服务返回全部图片、全部版本和全部任务。数据表缺少对应的 `images(project_id, created)`、`tasks(project_id, created)` 等索引；现有 `tasks_queue` 服务于出队查询，不能替代项目查询索引。

**触发与影响：** 隔离构造单次允许的 1000 张图、4 引擎共 4000 项任务，快照 JSON 为 **2,984,263 字节**。同一静态数据每分钟会被读取约 50 次，约 149 MB JSON 在本机服务与页面之间重复处理。EXPLAIN 确认 tasks/images 查询为全表扫描，并为排序创建临时 B-tree。这里不是外网流量；真正成本是本机查询、序列化、解析与 React 更新。多轮重识别、其他项目累计数据以及多窗口使用会继续放大成本。

本机一次端点函数取数约 31 ms，未包含 HTTP 序列化和浏览器渲染，因此不能据此声称当前已有严重响应延迟。

**改进：** 将队列状态与项目静态资料拆开；只轮询活跃任务或使用递增修订号/事件通知。图片和历史任务分页加载，补匹配查询的复合索引。前端避免同一项目轮询请求重叠，页面隐藏或项目空闲时降低频率。

**验证：** 用 1000 图×4 引擎及多批历史数据比较空闲分钟请求字节数、序列化时间和页面主线程耗时；确认空闲页面不会持续传送全量历史，同时任务完成和多窗口更新仍及时可见。

## 4. P2 · 每次微小编辑保存完整快照，长期校对空间成本缺少可见性

**性质：已测量的存储增长；保留策略属于能力建议。**

**位置：** [store.py:247](C:/Users/A/Desktop/OCR/src/ocr_workbench/store.py:247)、[maintenance.py:61](C:/Users/A/Desktop/OCR/src/ocr_workbench/maintenance.py:61)、[startup.py:108](C:/Users/A/Desktop/OCR/src/ocr_workbench/startup.py:108)。

每次有效保存都向 `edits` 写入完整 `text + tables`，同时在 `results.edited` 再存一份，历史未设保留或压缩策略。项目占用计算只统计项目文件、输出和缩略图，不包含共享 SQLite 中该项目的编辑历史。磁盘阈值主要在启动时检查，常规编辑/任务写入没有运行期间的低空间状态。

**触发与影响：** 10 万 ASCII 字符的文档做 50 次很小修改，产生 51 份历史快照，数据库从 **372,736 字节增至 5,394,432 字节**。这不是错误的撤销语义，但长文档或大表格反复校对后，实际占用可能远超左栏显示；用户不容易发现增长来源，直到保存或后续任务因磁盘空间失败。

**改进：** 保持可靠撤销的前提下，采用压缩快照、周期检查点加增量，或明确且可配置的历史保留规则。将数据库及历史占用纳入工作区/项目空间说明；增加运行期间低空间提示，优先保护已有校对数据。不要未经用户知情删除已承诺保留的历史。

**验证：** 用长文档和大表格进行数百次小修改，比较每次新增字节；跨检查点撤销/重做及重启后结果必须一致。占用界面应能解释数据库增长，低空间时应返回可行动错误而非仅通用失败。

## 5. P2 · GPU 或单个引擎故障会同时阻断既有文档校对与导出

**性质：明确的现有行为；建议新增降级访问能力。**

**位置：** [launcher.py:139](C:/Users/A/Desktop/OCR/src/ocr_workbench/launcher.py:139)、[startup.py:125](C:/Users/A/Desktop/OCR/src/ocr_workbench/startup.py:125)、[startup.py:140](C:/Users/A/Desktop/OCR/src/ocr_workbench/startup.py:140)、[startup.py:160](C:/Users/A/Desktop/OCR/src/ocr_workbench/startup.py:160)、[service.py:377](C:/Users/A/Desktop/OCR/src/ocr_workbench/service.py:377)。

正常启动器始终传入 `--verify-startup`。启动要求 NVIDIA 工具、至少约 14 GiB 总显存及全部引擎原生依赖通过；任一检查失败，服务在挂载 API/页面前退出。

**触发与影响：** 显卡驱动损坏、暂时更换较小显存设备，或仅某个模型环境损坏时，即使用户只想打开已经识别成功的文档、继续人工校对或导出，也进不了工作台。现有 16 GB 固定精度识别目标合理，但与无需 GPU 的资料访问耦合，增加故障期间的业务中断。

**改进：** 区分应用/数据安全检查与各引擎可用性；在不执行失败引擎的前提下提供“查看、校对与导出”模式，逐引擎显示禁用原因。核心应用完整性校验仍应保留，不能把校验失败一律忽略。

**验证：** 在隔离副本模拟 nvidia-smi 缺失及单引擎依赖失败，既有结果仍可读取/导出；识别入口明确禁用受影响能力。该项依据代码控制流审查，没有更改真实驱动或破坏任何安装。

## 6. P3 · 数据库打开流程会覆盖未知的新版本号

**性质：行为已复现；影响主要在后续应用升级/回退兼容性。**

**位置：** [store.py:33](C:/Users/A/Desktop/OCR/src/ocr_workbench/store.py:33)、[store.py:52](C:/Users/A/Desktop/OCR/src/ocr_workbench/store.py:52)、[store.py:72](C:/Users/A/Desktop/OCR/src/ocr_workbench/store.py:72)。

初始化先执行 `PRAGMA user_version=1`，按列名补字段后直接写为 4，没有先读取并判断磁盘数据库版本。隔离将当前兼容表结构的数据库标为版本 99 后，当前程序无报错打开，版本号变成 4。

**触发与影响：** 以后新版工作台改变数据结构，用户再用旧程序打开同一 `%LOCALAPPDATA%` 工作区时，旧程序既不拒绝未知版本，也会抹掉原始版本标识。本轮没有证明真实新版数据已损坏，但这种行为削弱迁移、回退和事故排查的依据。

**改进：** 在任何 schema 修改前读取版本；对高于支持范围的版本给出明确拒绝或经过验证的只读访问。采用版本递进迁移，迁移前创建一致性备份或恢复点，成功后才更新版本号。

**验证：** 保留旧版本数据库夹具，验证逐级升级和失败回滚；未知高版本应保持字节/版本标识不变并明确提示。当前已有字段的数据库重开应幂等。
