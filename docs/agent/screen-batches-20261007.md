# 批量图片转 Excel

适用场景是手机拍摄电脑上的表格、带少量桌面或窗口干扰的图片，以及普通表格截图。每张图片生成一个 `.xlsx`；同图多张业务表放在不同工作表，整批 ZIP 附原图与结果对应清单。一次最多 1000 张图片。

在“资料”上传图片，可全选图片后点击“批量转 Excel”；也可把固定资料集合交给智能审计，描述“把这批图片整批转 Excel，每图一个文件，最后给我 ZIP”。集合身份由服务器核实，不需要在消息中逐个输入文件名。

固定集合全部是当前图片版本、原生服务已就绪，且当前项目只有一个可写 OCR 关联时，服务器先核实该关联项目确实存在，再提供快捷启动条件。明确的批量转换可直接提交；服务未就绪、图片版本改变或有多个可写项目时仍先准备或选择项目。检查本身不启动服务。

日常“自动处理”先定位业务表区，再由 Hunyuan 识别一次；仅遇到技术失败时由 GLM 兜底一次。质量问题进入复核，不因此自动重跑其它模型。所有新批次候选均需人工确认，自动检查通过不等于人工已确认。默认策略和 GPU 排队由原生 OCR 服务管理，批量界面不自动启动另一个 GPU 服务；已经持久化的旧批次仍沿用原策略。

OCR 批量界面在开始前勾选“提高精度（耗时增加，仍需核对）”，新请求会明确选择 `business_language_v1`。原图业务表区的独立文字证据决定逐图路线：中文或证据不明用 Hunyuan，明确拉丁文本用 GLM；仅 GLM 技术失败时兜底 Hunyuan。成功的识别不为质量问题再调用另一个模型。每图原始额度为 360 秒，其中预留 90 秒兜底容量，实际剩余额度可以全部用于兜底；整批原始额度为 `max(36000, 图片数 × 360)` 秒，提交时固定。200、240、1000 张分别为 72000、86400、360000 秒。这些是成本上限，不是预计完成时间。

平台 API／Agent 工具接受显式策略，精度请求需同时指定 `primary_engine="glm"`、`fallback_engines=["hunyuan"]`、`max_upgrades=1`、`mode="accuracy"`、`upgrade_trigger="failure_only"`、`layout_evidence=true`、`require_human_review=true`、`budget_seconds=360`、`request_timeout_seconds=180`、`engine_route="business_language_v1"`、`technical_fallback_reserve_seconds=90` 及足额 `batch_budget_seconds`。省略字段仍沿用原生解析，单独传旧的 `mode="accuracy"` 不等于这条新路线。未知提交结果先查原回执，恢复不增加旧额度。

选择终态图片“只对这张图提高精度”会创建独立的固定 GLM 子批次，使用仅技术失败触发策略并保留原批次与结果，不继承主批的逐图语言分流。可选精度在模拟验证40图中减少识别错误，但全部40图仍需核对，没有人工减负或免复核资格。

平台只转发明确指定的策略选项，未指定的选项由原生服务解析。每个已提交批次的实际策略及其哈希会固定记录；恢复请求先查询原批次，后来修改默认配置不改变旧批次。实际回执若突然返回不同策略，平台保留原身份并要求核实。

进度分别显示完成、待复核、失败、取消和处理中。普通等待由后台观察器承担，不需要主控重复询问每张图片；Agent 只接收批次摘要和有限异常。运行中可以继续说“暂停原批次”“先下载已有结果”“继续原批次”或“取消剩余处理”。暂停保留原批次与已完成文件；追加指令不会重新提交整批。部分交付明确显示剩余处理或待复核范围。

原生服务提供同批实际任务的阶段估计后，平台进度页显示当前已排队阶段预计剩余时间。后续表区处理、精度升级、模型切换、导出和人工复核均另计。样本不足、当前任务已超出观测耗时、暂停或未知范围时不显示确定时间；页面沿用现有进度查询，不为估时调用主控模型。

用户中途收到“已继续”回复后，原生作业真正结束时会另发服务器完成事件，继续最终范围导出；原批次与所选图片升级任务分别保存完成状态。只有本轮交付已核验文件、没有后台或未知任务、所有相关屏拍作业已结束，且导出清单数量与最终可导出范围相符时，才直接结束转换，省去交付后的额外主控轮。旧的部分 ZIP 不满足此条件；混合其他业务作业时仍走普通 Agent 收尾。

复核入口并排提供原始图片、业务表区、选定结果和保留候选。修改单元格并“保存并确认本图”时，平台校验原结果身份、修订及修改前值，防止把旧窗口的修改写到新结果。也可稍后复核或保留当前结果，人工确认状态与识别成功分开记录。选择部分终态图片“提高精度”会创建新尝试及固定子集，原批次保留。

默认按文本导出原值，保留编号、前导零、长数字、日期文字和类似公式的原始内容。只有已人工确认的图片才能选择金额、数量或比例列按数值导出；变更候选或再编辑后需要重新确认和选择数值列。主控不能代签人工确认。

默认 ZIP 只包含已可交付结果；明确勾选“包含待复核文件”后可导出未确认版本，清单会保留状态。失败、取消和未完成图片不会生成假 Excel。重复下载同一选定结果和选项复用同一托管成果身份。

当前工程验证包括 240 项固定范围、批次身份恢复、分批进度、ZIP 对应、范围权限、候选编辑、上传最多三个并发、中途指令和冷恢复。真实模型质量、合成屏拍样本与真实主控开销的报告存放在独立的 `F:\OCR\output\ocr-screen-benchmark-20261007`。冻结 OCR 回执回放只验证流程与调度，重复回执不增加独立质量样本；合成屏拍表现也不能替代之后真实手机屏拍的复核。

候选产品版本为 `0.9.4`，平台兼容描述接受原生 OCR 数据库版本至 `20`，正式 current 仍为 `v0.9.3`。schema20 阻止旧 reader 按固定模型静默恢复逐图精度路线；平台还记录并从持久策略推导 `screen-business-language-route-v1` 能力要求。旧版本不能直接打开新增结构后的数据库；关闭 Agent 仅是功能关闭，数据恢复需使用相应版本的冷备并恢复到新的 F 盘目录。正式业务配置、模型和原有工作区不用于本轮评估写入。
