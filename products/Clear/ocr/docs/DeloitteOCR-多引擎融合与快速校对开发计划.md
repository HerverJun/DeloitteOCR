# DeloitteOCR 多引擎融合与快速校对开发计划

制定日期：2026-09-12。实施状态：**0.8.0rc2 已完成当前范围的融合与快速校对开发、工程验证及候选交付**。2026-09-12 按用户要求删除人工验收条款；本轮以公开数据质量报告、工程回归和交付回执为验收依据。证据见 [实施记录](fusion-implementation-status.md)。

本文是本轮开发的统一实施依据，整合 GitHub 项目调研、多引擎融合构思和快速校对方案。产品名称统一为 **DeloitteOCR**。早期文档与本文冲突的范围、阈值、数据安排和工期，以本文为准；基础工作台能力继续参考 [开发总纲](../开发总纲.md) 和 [使用说明](工作台使用说明.md)。

## 1. 目标与已确定的产品选择

目标是在现有四引擎工作台上生成有来源、可解释、可修订的融合草稿，让用户集中处理分歧与未决项，最后确认并导出表格或文本。

```mermaid
flowchart LR
    A[同图同版本的多引擎识别] --> B[表格或文字对齐]
    B --> C[生成融合草稿和来源证据]
    C --> D[逐项校对分歧与未决内容]
    D --> E[人工确认当前结果]
    E --> F[导出表格或文本]
```

| 决策 | 本轮安排 |
|---|---|
| 自动化程度 | 自动生成融合草稿，未决部分进入快速校对；最终确认由用户完成 |
| 准确率与速度 | 准确率优先，完整运行所选且具备对应能力的引擎；首版不提前停止或按分歧追加引擎 |
| 内容范围 | 表格和文本都做，先表格，再印刷体与手写文本 |
| 策略入口 | 保守、积极两档，默认保守 |
| 数据来源 | 先用现有公开数据，后续补充获准使用的内网真实样本 |
| 接受条件 | 通过开发与验证数据确定，不固定“50%以上”、固定票数或固定有效来源数 |
| 运行环境 | Windows 单机离线；OCR 沿用单 GPU 串行执行，融合在 CPU 上处理已有结果 |
| 估算 | 20–30 人日，不含等待内网样本、目标电脑或外部验收的时间 |

“50%以上取信”是提出方向时的例子。产品应把支持票数、来源覆盖和实测可靠性作为证据，再根据内容类型和策略决定是否替换基准值。支持比例不等于正确概率，自动规则通过也不等于人工确认。

## 2. 借鉴来源与现有基础

### 2.1 开源项目的借鉴分工

| 来源 | 借鉴方向 | 在 DeloitteOCR 中的落点 |
|---|---|---|
| [Calamari](https://github.com/Calamari-OCR/calamari) | 多字符串对齐、字符候选计票 | 普通文字的序列对齐与候选证据；接受规则独立验证 |
| [OCR-D CIS](https://github.com/cisocrgroup/ocrd_cis) | 跨 OCR 结果对齐、统一表示 | 对齐数据结构、插入删除和未匹配内容处理 |
| [FusionOCR](https://github.com/MxxScott/FusionOCR) | 异构引擎加权候选选择 | 比较加权策略；不直接采用英文分词或同下标匹配假设 |
| [ocr-read-packaging](https://github.com/alessandromaddaloni98/ocr-read-packaging) | 对齐、分歧和未决状态 | 保留候选及原因；本轮不引入其可选云端或 VLM 仲裁 |
| [Scribe OCR](https://github.com/scribeocr/scribeocr) | 原图与文字对位、围绕错误校对 | 局部证据、候选操作、处理后下一项 |
| [OctoOCR](https://github.com/1ampa55ag3/octo-ocr) | 单元格直接编辑 | 候选值进入既有表格编辑和保存流程 |
| [PaddleOCR Local](https://github.com/CHEN010325/paddleocr-local) | 同文档多模型顺序处理与对比 | 复用同版本同批次来源和单 GPU 队列 |

这些项目提供局部算法与交互参考。现有调研未验证到可直接接管四引擎、中文拍照表格、人工修订及 Windows 离线交付的完整组件，也未运行上游应用做同样本性能对照。

首版按交互和算法思路独立实现。Calamari 为 GPL-3.0，Scribe OCR UI 为 AGPL-3.0；若实际复用代码，先核对具体版本的许可证与依赖、再确定复用边界。其他项目的核查记录见 [GitHub 相似工作台调研](../research/GitHub相似OCR工作台调研-2026-09-12.md) 和 [投票融合可行性调研](../research/OCR多引擎投票融合可行性-2026-09-12.md)。

### 2.2 当前能力与约束

| 基础 | 当前能力 | 本轮增量 |
|---|---|---|
| 四引擎结果 | 独立原始输出、统一结果、图像版本与批次 | 固定来源快照、融合结果及每个识别单位的证据 |
| 多模型对比 | 文本差异、表格数量/行列/单元格/合并差异 | 可用于候选写入的可靠对应关系、聚合疑点 |
| 图像与表格编辑 | 区域高亮、版本切换、表格编辑 | 按真实坐标定位疑点，可靠降级 |
| 自动保存 | 串行提交、revision 冲突检查、修订历史、撤销重做 | 修改与校对决策原子保存、重试和恢复 |
| 采用与确认 | 显式采用结果、图片级确认绑定结果版本 | 融合结果接入相同流程，变更后确认失效 |
| 导出与存储 | 一致性快照导出、已确认筛选、迁移备份 | 融合来源与内容一致导出，新增数据纳入清理和恢复 |

当前引擎能力以 [engines.json](../config/engines.json) 及真实结果为依据：PP-OCRv6 有文字坐标和分数，但没有结构化表格；PaddleOCR-VL、GLM-OCR 可提供区域坐标，未声明可用的统一置信度；HunyuanOCR 未声明坐标和置信度。区域坐标不等于单元格坐标，解析得到的单元格不能假定带有 polygon 或概率。

现有表格差异按数组顺序和行列位置比较，可继续用于展示，但不能直接作为自动逐格写入的匹配依据。新增、缺失行列或多表顺序变化可能造成错位。

## 3. 数据、基线与实验隔离

### 3.1 复用现有数据

已核实的本机数据为 200 张公开样本：印刷体 82 张、手写 78 张、表格 40 张；已有四引擎各 200 条记录，共 800 条。

| 材料 | 已核实路径 | 用途 |
|---|---|---|
| 样本清单 | `E:\OCR-final-build\public-benchmark\benchmark.json` | 样本来源、类型及输入关联 |
| 四引擎评测记录 | `E:\OCR-final-build\public-evaluation-final\evaluation.json` | 复用原始输出、固定回放输入 |

这些路径是当前开发机的外部资料位置，不是随应用分发的依赖。实施时保存样本、输出、标注与文件哈希的清单；记录实际解析来源，不能仅凭已有汇总成绩代替原始输出核查。

### 3.2 固定划分与标注检查

1. 按原始文档分组，并按印刷体、手写、表格分层，固定 **60% 开发集 / 20% 验证集 / 20% 留出测试集**。同一文档的裁剪、旋转、增强及其他变体必须在同组。分组导致整数比例偏差时，记录实际数量，不拆组凑比例。
2. 保存固定随机种子、分组依据和划分清单。缺少来源标识的样本先追溯来源、检查重复，再纳入正式对照。
3. 复核参考标注，重点检查验证集与留出集的表格结构、合并关系、空值和数字。缺少结构标注时先补齐，不能仅凭文本答案宣称表格结构准确。原始标注和修订标注分别保留，记录修改原因。
4. 开发集用于实现、错误分析、按类型选择固定基准引擎以及拟定候选权重。验证集用于比较策略、选择参数和确定开放范围。
5. 验证完成后冻结代码、权重、阈值和策略文件，再运行留出测试。若依据留出错误继续调参，该集合转为开发参考，需要新的独立留出数据才能再次宣称独立验收。

这批数据此前已做过四引擎评测，须记录既往使用情况。此次划分不能抹去过去的调参接触；已用于策略选择的样本不能再作为未接触的测试证据。若无法证明独立性，报告应明确为回顾性公开数据验证，独立结论留给后续新增样本。

### 3.3 固定可部署的基准

基准引擎按内容类别在开发集上预先选定。每个样本都选事后最准确引擎的“理想上限”只能作为分析参考，不能冒充实际可部署基准。

至少比较固定基准、等权投票、按类别实测加权、强基准加证据替换四组结果；同时列出各单引擎成绩。所有方案使用相同输入版本、参考答案和计分规则，避免将预处理差异计为融合收益。

## 4. 融合算法

### 4.1 统一来源与识别单位

- 只接收同一图片、同一处理版本和明确同批次的原始 OCR 结果；记录任务、引擎、模型包、处理参数和结果指纹。来源关系不明时不能推定可比较。
- 同一引擎/模型来源只贡献一次证据；重复调用、重试或多个提示词不增加独立票数。人工修订和已有融合结果不能再作为新引擎投票。
- 每个单位记录预期来源、有效来源、各候选支持来源，以及失败、取消、不支持、未匹配等不同状态。空字符串是可能的识别内容，不能与失败或缺失结果混为一谈。
- 同时保留预期来源覆盖和有效来源内的支持情况。自动接受所用分母和最低证据条件写入策略，不悄悄剔除失败来源制造“100% 共识”。
- 不直接平均不同引擎的原始 confidence。缺失分数保留未知；跨引擎权重来自同口径实测。多个引擎可能共享模型、训练数据或版面处理，需单独报告共同出错，不能套用独立投票的正确率推导。

### 4.2 表格优先：先结构，后单元格

结构来源为 PaddleOCR-VL、GLM-OCR、HunyuanOCR。PP-OCRv6 只在区域对应可靠时提供辅助文字证据，不参与表格行列或合并结构投票；首版不从文字行下标或均匀网格伪造单元格。

表格处理依次完成：

1. **匹配同一张表。** 综合真实区域坐标、表头、标题和上下文。数组顺序或相同行列数不能单独证明对应；重复表头、多表重排和缺表必须识别为可能歧义。
2. **选择完整结构骨架。** 比较行列、单元格覆盖及合并关系，从已有结果中选一个完整合法的骨架。不能拼接互相冲突的合并结构或按格多数凭空组出新结构。
3. **建立单元格映射。** 只在对应可靠的结构内比较内容。缺行、缺列、偏移或合并冲突无法解决时，将受影响整表列为待复核，保留基准与完整候选表。
4. **选择完整字符串。** 单元格、金额、日期、编号按完整候选选择，保留前导零、长编号、标点、负号、小数点及空值。规范化可用于辅助比较，实际写入必须能追溯到原始字符串。
5. **保留分歧。** 保存选择理由、替代候选、支持来源及未决原因。平票或证据无法区分时保留基准值，供用户确认。

例如三个金额候选为 `1,280.00`、`1,280.00`、`1,260.00`，系统可以展示前者获 2/3 支持；能否自动替换基准取决于当前经验证的策略。不能据此称其“66.7% 概率正确”，也不能把不同金额逐字符拼出第四个数字。

### 4.3 文本：区域、行与片段对齐

一般文字可使用四引擎。先根据版面和阅读顺序关联区域，再对行与片段进行有长度上限的序列对齐，避免对整篇长文本无界计算。

- 对齐可靠的普通文本允许组合来自原始结果的字符或片段，每段保留来源依据。
- 金额、日期、编号和其他可明确识别的数字字段继续使用完整字符串候选；无法确定字段边界时保留基准并提示，不强行拆分投票。
- 显式记录插入、删除、行序变化与未匹配跨度。某一路独有的文字不能因为少数票就静默丢弃。
- 长段对齐不可靠或触及资源上限时保留基准，并将相关跨度列为待复核。
- 识别文本与结构化表格共同决定输出阅读顺序；不通过语言模型润色、自动补句或猜测内容生成来源中没有的文字。

### 4.4 原图定位的三级降级

| 证据 | 展示 |
|---|---|
| 有有效单元格坐标，且图像版本匹配 | 单元格高亮与带上下文的局部放大 |
| 只有可靠表格或文字区域坐标 | 高亮整表/区域，说明定位粒度 |
| 无可靠坐标、版本不匹配或关联有歧义 | 展示全图，聚焦编辑位置，保留手工缩放和定位入口 |

不生成虚构单元格坐标，不混用原图与透视、旋转等处理版本的坐标。重复数字的文本匹配只能提供候选关联，不能直接证明精确位置。

## 5. 两档策略与参数确定

### 5.1 要比较的三类候选算法

| 方案 | 方法 | 重点验证 |
|---|---|---|
| 等权投票 | 独立来源各一份支持，按对齐后的单位选择候选 | 简单多数的实际收益、平票和共同错误 |
| 按类别实测加权 | 根据开发集上表格、印刷体、手写等类别表现拟定权重 | 是否稳定优于等权，是否过拟合少量样本 |
| 强基准加证据替换 | 从固定基准出发，只在来源、对齐和支持满足条件时替换 | 保住基准正确内容，同时修复明确错误 |

不能预先认定某一种必然最好。验证阶段可以为不同内容类型选择不同算法，但组合与参数必须冻结后再做留出测试。

### 5.2 保守与积极的行为

| 维度 | 保守模式（默认） | 积极模式 |
|---|---|---|
| 自动替换 | 只有满足经验证的证据条件才替换基准 | 对齐可靠时选择当前策略最有支持的候选，保留低支持或冲突提示 |
| 优化顺序 | 先最少引入错误，再最多纠正错误，最后减少未决项 | 先最大净纠错收益，再最少引入错误，最后减少未决项 |
| 平票或不可区分 | 保留基准和候选，列为待复核 | 同样保留基准和候选，不随机决胜 |
| 结构或映射不可靠 | 整表或片段复核 | 同样复核，不能放宽到错位写入 |
| 人工确认 | 必须区分规则通过和人工确认 | 相同 |

上述优化顺序按词典序比较，不能为了少几个未决项牺牲更优先的准确性目标。两个模式都必须通过各自开放类别的验收；“积极”不意味着可以忽略新增错误。

策略文件应版本化，至少包含适用内容类型、固定基准、算法、权重、证据条件、支持率分母定义、对齐限制和模式。记录其开发/验证清单、冻结时间和哈希。用户选择模式即可，首版不提供未经验证的百分比滑块。

## 6. 工作台接入与数据接口

### 6.1 用户流程

1. 新增“融合识别”入口，选择表格/文字类型、保守/积极模式和参与引擎。复用同图同版本同批次且条件兼容的已有原始结果，或完整运行一次识别批次后融合。
2. 融合结果与单引擎结果并列，显示来源覆盖、策略及未决数量。新结果先进入预览；只有显式“采用结果”才改变正式编辑与导出目标。
3. 进入快速校对后显示当前候选、原始来源、当前值、选择原因与定位级别。按结构冲突、数字/日期/编号、空值、其他文字等筛选并逐项处理。
4. 提供采用候选、保留当前、手工修改、暂不确定、上一项/下一项。“下一项”只跳过；“保存并继续”必须保存成功后再移动。
5. 项目关闭重开后恢复处理进度。全部提示处理完仍由用户显式确认当前图片，再按既有流程导出。

再次融合创建新结果，不能覆盖已有人工校对。预览切换不能暗中切换修订目标；采用结果时沿用现有草稿保存和 revision 检查。

### 6.2 任务和 API

下列是本轮接口契约；已实现路由见 [融合使用与恢复说明](fusion-usage-and-recovery.md)。

| 接口或对象 | 必需语义 |
|---|---|
| 创建融合任务 | 接收来源 result IDs、内容类型、模式，校验版本/批次/能力后返回 task ID |
| 批次识别入口 | 可携带融合配置；保存预期来源，OCR 任务终态后再触发依赖融合 |
| `fusion` 任务类型 | 独立 CPU 执行路径和依赖关系，绝不送入模型加载器或 GPU 推理分支 |
| 结果来源标识 | 区分 single-engine 与 fusion；保存父结果、图像/模型/策略版本及每单位证据 |
| 疑点查询 | 稳定 ID、分页、筛选、未处理/有疑问/过期计数 |
| 决策提交 | 带预期 revision 和请求标识，事务化保存内容、编辑历史、决策与处理状态 |
| 既有接口 | 复用读取、预览、采用、编辑、撤销重做、图片确认和导出 |

融合任务只能在全部依赖 OCR 任务进入成功、失败或取消等终态后运行；来源失败或取消要显式计入证据覆盖。足够证据的定义由策略决定，不能把未完成任务当作弃权提前计算。融合任务支持取消和幂等重试；没有可用来源时明确失败并保留原因。

纯融合无需加载模型；兼容既有仅校对模式时，复用已有结果可以走 CPU 路径，需要新增 OCR 的操作仍遵守当前模式限制。

### 6.3 快照、统一结果和导出

- 创建任务时固定输入及策略快照，记录父结果指纹。后续来源新增或变化不能静默更新已生成结果，需要显式再次融合。
- 一个融合结果使用同一份规范结构生成表格、文本与 Markdown；单元格更新后同步再生相关表格文本、source offsets 和哈希，防止旧偏移继续指向错误内容。
- 原始输出、融合初稿、人工修订与决策历史分别可追溯；不得把融合值伪装成某个引擎原始输出，也不将来源引擎的分数或坐标直接冒充融合置信度和位置。
- TXT、Markdown、JSON、XLSX 均接入融合结果；内容和配套来源清单/JSON 从同一已保存快照导出。主表无需塞入全部证据，但必须能通过结果 ID、revision 和策略版本找到对应来源。
- 保留“仅导出已确认结果”选项。普通导出允许继续，明确显示未处理、有疑问、过期和未人工确认情况，不能把自动接受内容标为人工确认。

### 6.4 保存、失效与恢复

- 修改和决策进入既有串行保存队列，先处理草稿，再在后端同一事务内检查目标、图像版本、revision 与候选依据并提交。响应丢失后按请求标识安全重试。
- 保存失败、多窗口冲突或取消时保留草稿和当前位置，不增加完成数、不跳下一项；快速连点、切图和切项目不能绕过正在进行的提交。
- 疑点 ID 基于会话、稳定目标、结构指纹和候选依据，不能直接使用列表下标，也不能因任意一次 revision 变化让所有疑点重建。
- 普通单元格编辑只重新验证受影响疑点，内容和依据未变的其他决策保留。插行删列、合并拆分等结构编辑重新检查受影响表，必要时整表恢复待复核。
- 图像版本、采用结果或结果 revision 改变时，使相应人工确认失效；旧融合来源快照与决策历史仍保留。撤销/重做后重新判定相关疑点和确认状态，不能恢复已经不匹配的确认标记。
- 疑点清空只代表提示已处理，不能证明没有遗漏错误。图片确认继续绑定当前结果、图像版本和 revision。
- 新增来源、疑点、决策和快照数据通过现有备份机制迁移；数据库版本从实施时的最新值顺延。纳入项目占用统计、删除、级联清理、工作区迁移及异常恢复，不只保存在浏览器中。

### 6.5 建议模块边界

| 模块 | 建议职责 |
|---|---|
| 新增后端融合模块 | 表格/文本对齐、候选聚合、策略执行、证据生成；可独立离线回放 |
| 新增 `review_issues.py` 或同等模块 | 正式疑点判定、稳定 ID、决策有效性及增量重算 |
| 现有 service/store/task_queue/worker | 新任务类型、依赖调度、持久化事务、迁移和恢复 |
| 现有 tables/exporting | 规范结果、文本/表格同步、快照导出和来源信息 |
| 新增 QuickReview 组件及状态逻辑 | 候选展示、定位、操作与进度恢复 |
| 现有 App/ResultComparison/TableEditor/ImageCanvas/useEditor | 融合入口、预览采用、编辑焦点与串行保存 |

具体文件拆分依实现体量确定。正式融合与疑点判定以后端为准，前端保留展示与轻量筛选，避免维护两套不同的接受规则。

## 7. 阶段安排与交付物

按一名熟悉项目的开发者、现有模型与公开输出可用估算；各阶段按依赖顺序推进。

| 阶段 | 主要工作 | 可复查交付物 | 人日 |
|---|---|---|---|
| M1 数据与基线 | 核验 200 张/800 条记录，分组划分，复核标注，固定各类基准 | 数据/标注/划分清单、引擎能力与基准报告 | 2–3 |
| M2 表格融合原型 | 多表关联、完整结构选择、单元格候选、结构未决 | 可独立回放的 JSON/XLSX 原型、来源证据和失败案例 | 4–6 |
| M3 文本融合原型 | 区域/行/片段对齐、插入删除、数字保护和长段降级 | 印刷体/手写原型、CER 与字段错误分析 | 3–5 |
| M4 两档策略验证 | 比较三类算法，选择权重与接受条件，冻结并测试 | 版本化策略、保守/积极对照、留出测试报告 | 3–4 |
| M5 工作台闭环 | CPU 融合任务、预览采用、快速校对、事务保存、恢复与导出 | 可使用的融合识别和人工校对完整流程 | 5–7 |
| M6 回归与交付 | 工程与交互回归、500 张负载、说明与打包 | 候选包、源码、使用/迁移说明、验收报告及已知限制 | 3–5 |
| 合计 | 不含外部样本与目标机器等待 | 公开数据验证后的可选功能 | **20–30** |

M2、M3 先以独立结果检验对齐和候选质量。若错误主要来自不可靠结构对应，先收紧映射，不能通过放宽票率掩盖问题。

M4 按表格、印刷体、手写及两档模式分别决定是否开放自动替换。某一类别没有证明收益时，该类别保留候选建议与人工校对；已通过的类别可单独推进。不能仅因集成完成就宣称融合准确率提高。

## 8. 验收方法

### 8.1 质量与收益

| 范围 | 必报指标 |
|---|---|
| 表格结构 | 整表拓扑完全正确率、行列/覆盖/合并错误、缺表与多表对应错误 |
| 表格内容 | 完整单元格准确率；金额、日期、编号分别按完整字段计分 |
| 文本 | CER、插入/删除错误、阅读顺序问题、数字字段错误；归一化规则固定并保留原文核查 |
| 融合收益 | 相对固定基准纠正多少、引入多少、净纠正多少；基准正确却被覆盖的案例 |
| 自动接受 | 自动接受覆盖率与错误率同时报告，未决比例、来源缺失与共同错误分布 |
| 资源成本 | OCR、融合分别计时，并记录 CPU、内存及失败率；复用已有 OCR 时注明历史计时来源 |

测试中的主要准确率与关键数字指标不得劣于对应固定基准；自动替换仅在对应类别有充分的准确性改善证据时开放，否则保持候选建议。分别报告类别、模式、样本数、数据独立性和失败案例，不能用大量正确普通文字抵消少数错误金额。

公开表格仅 40 张，分组后的验证/留出规模更小。报告应说明样本量和不确定性；证据不足的细分类别不开放自动替换。历史指标或既有四引擎成功记录不能代替本次融合验收。

### 8.2 工程与交互回归

- 对齐：多表换序、同形不同表、重复表头、缺表、缺行列、合并冲突，不能把内容写入错误单元格。
- 保真：重复数字、`00123`、长编号、空字符串、小数、负号、日期和特殊字符；保存与 TXT/MD/JSON/XLSX 导出语义一致。
- 定位：缺失或越界坐标、仅区域坐标、图像版本不匹配，正确降级而不伪造位置。
- 任务：部分引擎失败、取消、进程异常、重试及响应丢失；依赖终态、CPU 路由、幂等和原始来源计票正确。
- 保存：revision 冲突、保存失败、快速连续操作、中文输入法组合输入、切图切项目及退出重开，不丢草稿、不虚增完成数。
- 状态：保留、暂不确定、跳过、撤销重做、结构编辑、来源/采用/版本改变，决策与人工确认按规则失效。
- 导出：待保存、过期确认、未决项、已确认筛选、多表合并及来源清单，均来自同一快照。
- 存储：迁移备份、异常恢复、项目删除、占用统计和工作区搬迁覆盖新增数据。

运行实施时已有的 Python 测试、前端测试和 TypeScript/Vite 构建，再验证受影响 UI 流程。为上述实质性行为补充必要测试，不以测试数量作为通过标准。

使用既有 500 张工程数据检查 CPU 融合的资源上限、分页、持续编辑和项目恢复；限制长文本对齐规模，避免一次性载入所有证据或让融合阻塞编辑。工程数据只用于容量与流程验证，不能计入识别准确率成绩。

如需截图，遵守工作区浏览器规则；最终证据优先用外部 Playwright/Chromium，加 `--disable-gpu`、`--disable-gpu-compositing`，完成后关闭测试浏览器。

## 9. 发布、回退与后续范围

首轮作为标明“已在公开数据上验证”的可选功能发布，默认保守模式。策略按类型逐项启用；保留单引擎结果和普通校对入口。回退某项策略只影响新任务，已生成结果继续绑定原策略与来源快照，不静默重算历史工作。

交付包含可运行候选包、源码、策略文件、使用说明、迁移/恢复说明、质量与工程报告、已知定位限制。候选构建、质量评测与工程验证分别记录，以对应范围的实际回执作为通过证据。

内网真实数据到位后，另建获准使用的标注集，重新校准权重和条件，并保留独立业务测试集。另一台干净 Windows 及实际 RTX A4000 的运行、显存、离线和性能验收单独执行，公开数据和本机结果不能替代。

本轮不增加新 OCR 模型，不接云端仲裁或语言模型润色，不扩大 PDF 范围，不做提前停止、动态追加引擎等速度调度。后续是否引入这些能力，以本轮的错误分布、时间成本和真实业务样本为依据。
