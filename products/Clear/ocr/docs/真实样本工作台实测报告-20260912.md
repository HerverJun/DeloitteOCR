# 真实样本工作台实测报告 · 2026-09-12

本轮用 Codex 内置浏览器操作当前工作区工作台，并让公开真实图片经过实际 GPU 识别、人工校对和导出。确认发现 **1 项 P2 缺陷：模态弹窗中的操作失败只显示在遮罩后的全局提示中**，无效引擎包和无结构化表格导出 XLSX 两条路径均真实复现；另发现 **2 项 P3 问题：损坏图片提示直接暴露 PIL 英文异常及本地暂存路径，正常仅校对模式被侧栏误报为队列异常**。本轮检查到的模型识别错误另列为准确率风险，没有据此认定工作台转换或导出损坏。

已完成的主要链路可用。任务快照记录 **16 项真实任务最终成功**；**14 份 UI 实际生成的导出文件、21 项内容与来源核验全部通过**；图像版本与原图的 **9 项核验通过**。仅校对模式补测没有新增 GPU 任务。这些数字是保存证据的任务、文件和检查数量，不是虚构的用户场景覆盖率，也不表示所有任务首次执行均无取消、暂停或重试。

### 保存、版本与导出核验

路牌文字校对后的最早 TXT 包含完整 `QA 校对标记 00123`。GLM 预览 XLSX 的来源是 `6993a7e01e8140439975951ec0b480ed`、GLM、revision 0；随后从所选范围导出的 TXT 来源是 `d94ee08e0f834775ad38c32ff8951b1b`、PP-OCR，除 Windows CRLF 换行外等于其原文。这验证了预览没有暗中改变采用来源。

最新路牌多表 XLSX 为 revision 11。第一工作表 A1 是标题“路牌人工校对”，因此数据从第 2 行开始：A2 为 `00123`，B2 为 `90071992547409931234`，C2 为字面文本 `=1+1`，三个单元格的实际类型都是字符串；A3 保留“多行”和“文本”之间的真实换行。第二张表独立保留。整个工作簿没有公式单元格。

逐图 ZIP 包含两个工作簿和 `sources.json`，共三张数据表；汇总工作簿同样有三张表及来源索引。仅已确认导出的实际请求只包含路牌结果，输出其两张表。不同导出方式中，相同 result/revision 的单元格值、类型和合并结构相同；较早批量文件固定在路牌 revision 10，不应与后来 revision 11 的内容混为同一次导出。

GLM 的 XLSX、MD 和 JSON 校对表在单元格值、坐标、行列数和合并范围上保持一致；JSON `original` 与编辑前快照完全相等。导出结果没有修改原始识别数据。

有两段中间操作不作为产品 bug：测试在 B3 插入行列后又删除了最后行列，形成了空 C 列、空第 4 行及表头合并变化；另一次快速操作被合并为一次保存历史，撤销时一并撤回了 TSV。两种状态都被导出忠实保留。核对操作顺序后，重新粘贴、等待“已保存”、来回切换表格再导出，最新路牌内容通过核验。没有用后来的正确文件覆盖原始中间证据。

图像证据独立验证路牌裁剪为 580×260、区域识别输入为 420×180；书籍旋转/增强版本为 708×1100、UVDoc 版本为 1100×708、透视版本为 1050×620。原文件逐字节等于下载样本，版本文件与数据库记录的尺寸、哈希及父版本关系一致。

仅校对模式下，项目二的路牌追加 `QA REVIEW_ONLY 保存导出`，等待“已保存”后导出 TXT。第 14 份文件完整保留该行，其余文本与补测前只读快照一致；随后恢复原文并保存。普通增强生成该图片的第 3 个版本；开始识别、区域重识别、去弯曲、队列继续和重试失败项均为禁用状态，引擎管理入口不渲染。该模式正常不启动队列，任务总数仍为 16。

## 确认缺陷

### P2 · 模态弹窗操作失败，错误被遮罩与可访问性隔离隐藏

**复现一：无效引擎包。** 在 1440×900 内置浏览器打开“引擎管理”，通过文件选择器导入 `edge-cases/invalid-engine.zip`。后端正常拒绝，返回“缺少有效的引擎包清单”。界面按钮可点击，操作结束后没有在当前模态内给出有效可见、可达的失败原因。

**复现二：无结构化表格导出 XLSX。** 打开没有结构化表格的已识别结果，在导出弹窗选择 XLSX 后点击“保存文件”。后端正确拒绝并返回缺少结构化表格的原因；弹窗仍打开，错误仍只写到弹窗外全局 toast。两次复现属于同一缺陷，不重复计为两个独立问题。

**实际证据。** 页面上存在红色 `.toast`，`innerText` 能读到错误；其计算层级为 `z-index:100`，位于模态遮罩后。toast 的祖先被设置 `aria-hidden=true`，常规 `getByRole('alert')` 返回空；屏幕阅读器的可访问性树也无法获得这条错误。用户会遇到“按钮可用、点击后操作没有完成，但当前弹窗无法说明原因”的状态。

**根因。** [EnginePackages.tsx:57](../frontend/src/EnginePackages.tsx#L57) 把错误只上抛全局 `onError`；[App.tsx:126](../frontend/src/App.tsx#L126) 的通知函数写入共享状态，唯一 toast 位于 [App.tsx:1452](../frontend/src/App.tsx#L1452) 的普通 App 子树，并不在当前 `DialogSurface` 内。[style.css:1226](../frontend/src/style.css#L1226) 与 [style.css:2120](../frontend/src/style.css#L2120) 把 toast 层级固定为 100；当前 Fluent Portal 默认层级为 1000000，模态行为又通过 Tabster 隐藏外部页面。视觉层级和可访问性隔离同时生效。

导出同样经过 [App.tsx:298](../frontend/src/App.tsx#L298) 的全局异常处理，只有下载成功后才在 [App.tsx:513](../frontend/src/App.tsx#L513) 关闭弹窗。后端缺表拒绝逻辑位于 [exporting.py:68](../src/ocr_workbench/exporting.py#L68)，拒绝本身正确，缺陷在错误传达。

**建议。** 在当前 `DialogContent` 内呈现持续可见的 `role="alert"` 错误区，保留用户输入和重试入口。非模态操作继续使用全局 toast。只提高 z-index 不会解决 `aria-hidden`；也不应通过移除模态隔离来修复提示。应一并检查引擎启用/删除、项目占用失败、项目创建/重命名、确认重新加载失败等共用全局 `onError` 的模态路径，这些扩展路径本轮没有逐一制造失败。

**回归标准。** 在上述两个真实复现中，弹窗保持打开时能通过其内部 `getByRole('alert')` 找到错误，无隐藏祖先；文字完整可读，用户能直接改选格式、换文件或重试。

### P3 · 损坏图片提示直接输出底层英文异常及本机暂存路径

混合导入 `broken.png` 时，工作台正确拒绝坏图，并继续保留合法导入图片；但错误正文显示 PIL 英文解码异常和本机 `inbox` 临时文件路径。普通用户难以据此判断应换文件、修复图片还是改格式，随机暂存位置也无助于处理问题。

根因是 [imaging.py:186](../src/ocr_workbench/imaging.py#L186) 的 `Image.open(temporary)` 异常直接进入 [service.py:209](../src/ocr_workbench/service.py#L209) 的 `str(error)`，再由 [App.tsx:344](../frontend/src/App.tsx#L344) 拼入用户提示，没有针对解码错误转换文案。

建议用户层显示“无法读取 broken.png，文件可能损坏或格式不受支持，请重新导出图片后重试”，保留原始文件名；完整异常与临时路径进入诊断日志。回归应同时检查坏图、扩展名正确但内容无效，以及同批次合法图片继续导入。

### P3 · 正常仅校对模式在侧栏被误报为队列异常

以同一测试服务入口添加 `--review-only` 后，健康接口返回 `status=ready`、`review_only=true`、`queue.healthy=false`。这是该模式正常不启动 GPU 队列的状态；页面顶部也正确显示仅校对提示，编辑、导出和普通增强均可用。

侧栏“任务队列”按钮却显示“队列异常，请查看恢复提示”。打开队列后，当前项目任务均已完成，没有它要求查看的恢复提示。此按钮用于打开历史队列，能够打开是正常行为；问题是正常模式被误报为故障，不是识别或恢复按钮绕过禁用。

根因位于 [App.tsx:541](../frontend/src/App.tsx#L541)：`queueHealthy` 仅由 `project.queue.healthy` 派生。侧栏 [App.tsx:774](../frontend/src/App.tsx#L774) 优先判断 `!queueHealthy`，直接在下一行输出异常提示，遗漏 `reviewOnly` 分支。[WorkspaceLayout.tsx:78](../frontend/src/WorkspaceLayout.tsx#L78) 只渲染传入的 `sidebar`，没有另行派生队列状态。

后端 [service.py:49](../src/ocr_workbench/service.py#L49) 在仅校对模式下跳过 `queue.start()`；[task_queue.py:56](../src/ocr_workbench/task_queue.py#L56) 将健康定义为线程存活且状态为 running，因此未启动时自然为 false。[service.py:122](../src/ocr_workbench/service.py#L122) 已正确将仅校对模式视为服务 ready。前端主提示区 [App.tsx:798](../frontend/src/App.tsx#L798) 也已经处理 `reviewOnly`，并只在完整模式提供恢复入口，进一步说明侧栏是遗漏状态分支，而非测试钩子造成队列故障。

建议侧栏先区分仅校对模式，例如显示“仅校对模式 · 1 项已完成”，只有完整模式下队列应运行却不可用时才提示异常。继续保留现有识别、区域重识别、去弯曲和队列恢复按钮的禁用边界。回归应分别检查仅校对正常未启动、完整模式正常运行和完整模式实际故障三个状态，确保文案与可用操作一致。

## 模型准确率风险

以下错误已存在于模型 raw 输出中；独立读取 raw、解析 HTML 并与工作台 `original` / cells 比较后，没有发现抽查转换路径额外改数值、丢行或改变单元格内容。不能把模型错误算作工作台导出 bug，也不能把数据转换保真算作识别准确率通过。

| 抽查项 | 观察 |
| --- | --- |
| PubMed 数值数据 | PaddleVL、Hunyuan 各保留 4/4 数据行、28/28 数值单元格；GLM 为 26/28 数值单元格，第二数据行 `10.8→18.8`、`±5.7→±1.7`，另有组名和上标错误 |
| 表格分组表头 | 三个模型生成不同 colspan；PaddleVL/Hunyuan 的分组标题可能关联到错误列，需要人工核对。模型 HTML 与工作台结构一致 |
| PP-OCR 手写 | `>300` 被识别为 `7300`，改变数值阈值含义；“空气”“冰雹”存在漏字 |
