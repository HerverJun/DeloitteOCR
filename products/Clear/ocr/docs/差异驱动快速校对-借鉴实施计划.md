# DeloitteOCR 差异驱动快速校对：早期借鉴实施计划

> 本文保留早期仅做差异校对的方案，已由 [多引擎融合与快速校对整体开发计划](DeloitteOCR-多引擎融合与快速校对开发计划.md) 统筹替代。下文的 8–12 人日、真实样本先行及暂不做自动纠错，均不是当前整体计划要求。当前按公开数据先行、自动融合草稿与人工确认闭环实施；2026-09-12 已同步删除人工验收条款。

制定日期：2026-09-12。基于 DeloitteOCR 当时的工作区源码及 [GitHub 相似项目调研](../research/GitHub相似OCR工作台调研-2026-09-12.md)。本文件保留早期设计，当前功能状态见 [融合实施记录](fusion-implementation-status.md)。

**目标：让用户按照疑点清单完成“定位原图 → 判断候选 → 修改或保留 → 保存后下一项”，集中处理拍照表格中的数字、日期、编号疑点。** 识别效果沿用现有模型，验证对应关系、定位降级、保存恢复和导出一致性。

首轮预计 **8–12 人日**，按一名熟悉当前项目的开发者、已有可用模型与样本估算。单元格几何定位如果需要新增识别模型，另行估算；首轮通过可靠降级完成闭环。

**借鉴来源与落点**

| 来源 | 借鉴什么 | 在 DeloitteOCR 中的实现方向 |
|---|---|---|
| [Scribe OCR](https://github.com/scribeocr/scribeocr) | 原图与识别文字对位、低置信提示、围绕错误的校对操作 | 疑点定位、局部证据展示、处理后下一项；使用现有 React / Fluent UI 体系实现 |
| [OctoOCR](https://github.com/1ampa55ag3/octo-ocr) | 点击单元格直接编辑、改动写回正式编辑状态 | 沿用 DeloitteOCR TableEditor 和保存队列，增加从疑点定位单元格和采用候选值的入口 |
| [PaddleOCR Local](https://github.com/CHEN010325/paddleocr-local) | 同文档多模型顺序处理、来源清晰的对比结果 | 复用现有同版本同批次分组，以固定识别结果生成疑点，保留来源与处理记录 |

Scribe UI 为 AGPL-3.0；本计划按交互和行为独立实现，不安排复制其 UI 源码。OctoOCR、PaddleOCR Local 为 Apache-2.0；如后续选定实际代码复用，再对该代码及依赖处理署名和许可。

**现有基础与真正需要补齐的部分**

| 现有模块 | 已有能力 | 本次增量 |
|---|---|---|
| [comparisonOps.ts](../frontend/src/comparisonOps.ts) | 同图像版本/批次分组，文字差异，表格数量/行列/单元格/合并差异 | 可靠表格对应关系、结构冲突抑制、疑点聚合及稳定标识 |
| [ResultComparison.tsx](../frontend/src/ResultComparison.tsx) | 选基准、看原始或校对内容、差异展示 | “开始快速校对”入口、参与比较的引擎与已采用结果说明 |
| [TableEditor.tsx](../frontend/src/TableEditor.tsx) | 编辑、合并拆分、行列操作、低置信筛选及下一单元格 | 外部定位指定表格/单元格、候选值写入、焦点与快捷键协调 |
| [ImageCanvas.tsx](../frontend/src/ImageCanvas.tsx) | 图像版本、文字区域高亮、缩放、框选 | 基于真实坐标的局部视图和清晰的定位级别 |
| [useEditor.ts](../frontend/src/useEditor.ts) | 自动保存、串行提交、切换前 flush、失败保留草稿、撤销重做 | 校对决策进入同一提交队列，成功保存后移动游标 |
| [store.py](../src/ocr_workbench/store.py) | revision 冲突保护、修订历史、图片级复核、数据库迁移备份 | 持久化校对会话/决策、事务化采用候选、断点恢复及失效规则 |
| [exporting.py](../src/ocr_workbench/exporting.py) | 一致性快照导出、来源信息、仅导出已确认结果 | 导出快照关联校对决策；有未完成项时明确告知 |

当前 `tableDifferences` 按表格数组顺序及行列下标比较。它适合展示差异，但新增/缺失一行时可能造成大量位置差异，不能直接作为自动逐格修改的依据。

另一个实际限制：抽查 `audit/airgap-final/inference` 下的表格结果，GLM、Hunyuan、PaddleVL 分别有 17、16、17 个单元格，单元格坐标和置信度均为空；PP-OCR 没有结构表。这只是当前几个既有样本的事实，不推断所有模型输出都如此。`tables.py` 中 HTML/Markdown 表格解析也将这些字段置空。因此，“逐格原图放大”不能成为首版无条件承诺。

**首版用户流程与范围**

用户选定图片当前采用结果作为修订目标，从同图同版本同批次已有结果中选择比较来源，点击“开始快速校对”。比较基准用于组织差异，修订目标始终明确显示；切换预览不会改变修订目标。

界面继续使用现有三栏：左侧显示图片及剩余疑点数，中间显示来源图像和可用局部区域，右侧显示当前疑点、候选值、当前采用值及编辑框。

疑点操作为：**采用某候选值、保留当前值、手工修改、标记有疑问、下一项**。其中“下一项”只是跳过；“采用/保留/修改并继续”必须等待保存成功。有疑问项进入待复看列表，不计为已完成。候选值仅写入明确选定的目标单元格，原始识别结果保持独立。

首版覆盖：

- 数字、日期、编号的文字差异，以及一方为空的可比单元格。
- 整表缺失、表格对应不确定、行列或合并关系不同的结构疑点。
- 当前引擎真实返回分数时的低置信提示；缺失分数显示未知。
- 已有结果中的两引擎起步比较，可加入更多已有结果；同一疑点聚合多个候选，避免四引擎产生六份重复差异。
- 项目内逐图处理、保存后继续、关闭重开恢复。

数字、日期、编号只是疑点分类，不自动推断业务语义。前导零、小数点、负号、千分位和长编号始终保留原始字符串；多数引擎一致仅作为证据，不自动认定正确。

PDF、新模型、自动纠错、复杂自动表格重排，以及 Scribe 的文档字体拟合叠字，放在这次迭代之外。原图文字叠加只在有可靠位置时作为辅助视图；普通局部放大优先交付。

|---|---|---|---|

| M1：疑点生成 | 建立保守的表格/单元格对应；生成数字/空值/结构/低置信疑点；聚合候选、排序并分页 | 可重复生成的疑点数据、对应关系与降级原因、关键对齐测试 | 2–3 人日 |
| M2：校对界面 | 疑点清单、定位表格/单元格、原图局部视图、候选操作、保存反馈、键盘导航 | 单张表格的交互闭环；坐标不足时可继续人工核对 | 2–3 人日 |
| M3：保存与批量 | 决策和修改事务化保存、revision 检查、重开恢复、撤销后重算、逐图切换、导出衔接 | 完整项目闭环，处理状态与最终内容一致 | 2–3 人日 |

M0–M1 完成后先检查疑点是否可信。无法可靠匹配的表格进入整表复核，仍可完成首版；不能用行列下标强行填充匹配。M2 与 M3 合并完成后，才形成可供实际使用的保存闭环。

**M1：疑点生成的具体规则**

1. 固定比较会话：记录图像版本、批次、来源 result ID/原始内容指纹、修订目标与规则版本。未知批次仍按现有规则隔离，不能推定属于同批次；新生成的识别结果由用户显式加入并刷新会话。
2. 表格对应：优先使用可验证的版面来源区域、标题/表头及结构上下文。形状一致不代表同一张表；多表顺序变化、重复表头、没有足够锚点时降级为“对应关系待确认”。可由用户明确选定对应表，再建立本次会话的匹配。
3. 单元格对应：首版仅对结构一致且表格对应可靠的区域逐格比较。遇到插行、删列、合并冲突或疑似整行偏移，先显示一项结构疑点并暂停该区域逐格候选写入，转到现有表格编辑器处理。
4. 生成与合并：同一目标位置的不同引擎值聚合为一项，保留来源及原文。一方为空称“空值差异”，不直接断言漏识别。对比用的格式化表示与实际写入字符串分离，不能格式归一化后丢失前导零等内容。
5. 排序：先处理影响对应关系的结构疑点，其次数字/日期/编号、空值差异，最后其余文字与低置信提示。分数只使用同引擎规则，不统一平均或跨引擎排名。
6. 无结构表：PP-OCR 文字块只作为具有可靠空间对应时的辅助文字证据；不从纯文本行号伪造表格单元格。

建议把持久化会话所需的匹配与疑点判定放在新增后端模块 `review_issues.py`，前端负责展示与轻量筛选。现有 `comparisonOps.ts` 的原始差异展示继续复用；提取共用样例验证两处含义，避免前后端各自维护不同的正式判定规则。

**M2：定位和交互的具体规则**

定位必须携带对应图像版本，按以下顺序选择：

| 证据条件 | 展示方式 |
|---|---|
| 有有效的单元格 polygon，且版本匹配 | 高亮单元格范围，显示带上下文的局部放大 |
| 只有表格/版面区域坐标 | 高亮并放大整表，说明当前定位到表格区域 |
| 无可靠坐标或区域对应不确定 | 聚焦右侧编辑单元格，保留全图缩放/手动定位入口，显示“暂无精确位置” |

坐标从本地结果直接使用；必要时补充统一结果中已有的真实表格区域来源。内容文本匹配只能形成候选关联，重复数字不能据此自动宣称精确位置。首版不按均匀网格估算单元格边界。

快捷键只在快速校对面板生效，界面同时提供可点击按钮。例如 Alt＋上下切疑点，Ctrl＋Enter 保存当前处理并继续；输入框内保留正常文本编辑行为，中文输入法组合期间不触发提交。处理一项后稳定保持位置，避免自动重排造成跳项。

**M3：持久化、修订和导出的具体规则**

- 新增“校对会话”和“校对决策”存储，通过现有备份/迁移流程升级数据库。版本号在实施时按仓库当前最新值顺延，不能预占可能被其它开发使用的编号。
- 每个疑点有稳定标识，依据会话、目标位置/结构指纹、来源候选及规则版本生成；当前列表下标不能作为 ID。结果 revision 用于并发检查，不直接作为导致所有疑点随一次编辑全部换 ID 的组成部分。
- 决策保存来源 result、来源位置、来源原文、旧值/新值、处理方式、时间及提交前后 revision。采用候选时只复制文字内容，不把来源引擎坐标或置信度混写进目标引擎结果。
- 候选操作先进入 `useEditor` 已有串行队列、保存待提交草稿；后端在同一事务里校验当前目标、版本、revision 和候选依据，写入正式编辑历史与决策。使用请求标识支持安全重试，避免响应丢失后重复记账。
- 操作失败或多窗口冲突时，保留当前草稿与疑点，不计完成、不跳下一项。按钮等待当前提交结束，批量导出等待已有保存队列完成。
- 普通单元格修改后仅重算受影响疑点。候选依据、对应关系和决策后文字未变化的其它已处理项保留；改变采用结果或图像版本时，旧会话标记过期并保留历史。
- 插行、删列、合并拆分等结构改动后，受影响表的对应关系及决策重新校验，首版可保守地将整表重新置为待核对。撤销/重做沿用既有编辑历史，并重新判定相关决策是否仍有效；历史事件不删除。
- 疑点清空只意味着已处理提示，不能证明没有遗漏错误。完成一张图片仍由用户显式确认，继续沿用已有 `result_id＋version_id＋revision` 绑定的图片级复核状态。
- 导出前展示未处理/有疑问/过期计数；沿用“仅导出已确认结果”的可选规则，不新增一刀切禁用导出。用户选择普通导出时允许继续，导出内容以已保存的采用结果为准。
- JSON/来源清单中的决策摘要必须与内容来自同一快照，并包含本次来源、目标及 revision。首版无需改变 Excel 主表版式。

新增会话/决策应纳入项目占用统计、项目删除、级联清理及工作区迁移逻辑。它们存储在项目数据库，不能仅保存在浏览器 localStorage。

**验证与通过条件**

工程验收采用关键行为测试与现有回归，不按新增测试数量作为通过标准：

- 对应关系：同形不同表、多表交换顺序、重复数字、缺整表、插行/删列、合并差异，均不得把候选值写入错误单元格。结构不可靠时明确降级。
- 内容保真：`00123`、长编号、小数/负号、日期、空字符串、中文输入法和特殊字符，保存与 Excel/JSON 导出保持原文语义及现有规则。
- 定位：缺失/越界坐标、旋转或透视后的版本、仅整表坐标，均有正确定位或诚实降级，不叠加错误版本坐标。
- 保存：保存失败、响应丢失重试、多窗口 revision 冲突、快速连续操作、切图切项目、退出重开，均不丢修改、不虚增完成数。
- 状态：保留当前值、暂不确定、仅跳过、撤销/重做、改变候选来源/采用结果、结构修改后，处理状态和图片复核状态符合上述规则。
- 导出：待保存、确认失效、有疑问项、仅导出已确认图片、多表合并单元格和来源摘要均与同一快照一致。
- 批量：使用既有 500 张工程数据检验按需生成、分页和持续处理。每张只计算所需会话，统计疑点数量、响应时间、内存；长计算不能阻塞正在编辑的输入。
