# 构建与复现

构建机需要 Windows x64、Python 3.12，以及编译系统级隔离验收工具时使用的 MSVC/Windows SDK。目标机运行便携包不需要这些开发环境。

## 资产准备

1. 通过 `scripts/fetch_assets.py` 下载 CPython 3.12.10 Windows x64 嵌入式 ZIP、固定 llama.cpp 构建及其 CUDA 12.4 运行库。每项生成 SHA-256 记录。
2. 用 `scripts/prepare_models.py --output <模型目录>` 下载模型。`source-manifest.json` 固定仓库 revision。必要时可显式传入构建代理；运行时没有代理依赖。
3. `scripts/verify_model_sources.py --bundle <包目录> --output <记录.json>` 将本地权重与上游该 revision 的 LFS SHA-256 比对。
4. 根据 `config` 中构建依赖与交付包 `locks/*.txt` 准备 Windows CPython 3.12 wheelhouse。GLM 使用 CUDA 12.6 的 `torch==2.10.0+cu126`、`torchvision==0.25.0+cu126`。不要误装 PyPI CPU 版并让程序静默回退。

## Paddle Windows wheel 修正

本次上游 `paddlepaddle_gpu-3.3.1-cp312-cp312-win_amd64.whl` 的实际编译配置为 cuDNN 9.9.0，但 METADATA 依赖为 `nvidia-cudnn-cu12==9.5.1.17`。实测发出了底层不兼容警告；3.2.2 同样存在此问题。

`scripts/patch_paddle_wheel.py` 仅修正发行包元数据：本地发行版本 `3.3.1+ocr.1`，cuDNN 固定 `9.9.0.52`，重建 wheel RECORD。所有推理代码与二进制保持逐字节一致。上游及修正后 wheel 哈希记录在 `paddle-wheel-patch.json`，不会把修正包伪称为未经修改的官方发行物。

```powershell
python scripts/patch_paddle_wheel.py --wheel <上游wheel路径> --output-dir <修正wheel目录>
python scripts/install_from_wheels.py --bundle <包目录> --archive <CPython嵌入式ZIP> --wheelhouse <完整Paddle依赖仓> --overlay-wheels <修正wheel及cuDNN9.9目录> --name ppocr
python scripts/install_from_wheels.py --bundle <包目录> --archive <CPython嵌入式ZIP> --wheelhouse <完整Paddle依赖仓> --overlay-wheels <修正wheel及cuDNN9.9目录> --name paddlevl
```

其余运行环境可由 `prepare_runtime.py` 创建，冻结后使用 `install_from_wheels.py` 从精确版本依赖仓离线重建。所有环境使用 CPython `_pth` 相对路径，不复制开发机 venv。控制运行时只需标准库。

## 混元转换与 Windows 本机库

llama.cpp 固定 `b10894`，commit `d344123fe2de081a72e02d6869360dfcbc0b528b`，Windows CUDA 12.4 构建。`scripts/convert_hunyuan.py` 调用同一 commit 的上游转换脚本，分别生成 F16 主模型和 F16 mmproj，不使用量化或 DFlash。转换源 revision、权重哈希和产物哈希随包记录。

`scripts/bundle_msvc.py` 从微软提供的 x64 CRT **Redist** 目录收集可应用本地部署的运行库；不从 System32 随意拷贝 DLL。来源目录与文件哈希记入 `config/msvc-source.json`。CUDA DLL 来自 NVIDIA Windows wheels 和 llama.cpp 官方 CUDA 运行库资产。

## 收口

1. `sync_bundle.py` 同步应用源码、配置、夹具和验收入口。
2. `audit_dependencies.py` 递归检查实际安装版本及启用的 extras，包括本地修正后的 Paddle 元数据。
3. `run_acceptance.py` 实际运行四引擎；每项立即写出记录，返回非零表示失败。
4. `lock_bundle.py --bundle <包目录> --metadata-only` 记录实际安装版本与模型 revision；`collect_licenses.py --bundle <包目录> --llama-source <固定commit源码目录>` 收集许可索引。
5. `package_bundle.py --bundle <包目录> --output <交付ZIP路径>` 流式打包并记录实际入包字节 SHA-256，生成 manifest、ZIP64、归档哈希及回执。大模型与原生库不重复压缩，其他文件使用 DEFLATE；小文件使用有界并行预读。输出目录必须在包外，不覆盖既有交付 ZIP。
6. 打包后使用 `ocr.cmd verify` 全量核对便携目录；使用 `verify_archive.py` 从 ZIP 逐文件解压读流并核对同一 manifest，另外生成交付验证回执。文件冻结后不要继续同步或修改包内容。

合成夹具可由 `make_fixtures.py` 在 Windows 上重建，字体为系统微软雅黑。它们用于兼容性和输出保真检查，不是准确率排行榜。

## 中文路径兼容修正

实际跨盘搬迁测试发现 Paddle Windows C++ 模型读取把中文路径报告为“空 JSON”。`windows_paths.py` 在可写的 ASCII 临时目录内创建指向当前包模型目录的短暂目录 junction；使用 Windows 原生重解析点 API，不要求管理员权限，不复制权重，也不绑定原构建路径。识别结束或正常异常退出时只移除 junction，保留目标模型。单元测试覆盖异常清理及目标权重保留。强制结束整个进程时可能留下小型临时 junction 目录，但不会额外复制模型或遗留引擎进程。

图片使用 Python Unicode 文件 API 解码，再按 Paddle 官方数组输入形式提交 BGR 数据。模型和识别算法没有替换；原图、预处理图片哈希及坐标版本照常保存。

运行时 DLL 审计只允许包内应用库、Windows 系统库和 Windows Defender 的指定 `MpOAV.dll` 注入模块。后者是操作系统安全组件，明确列入记录，不将其误当作需要从开发机复制的 OCR 依赖。

## 系统级隔离验收

`offline_guard.cpp` 是可审计的 Windows Filtering Platform 验收工具，用 MSVC `/MT` 编译成无开发环境依赖的原生 EXE。在 x64 Native Tools 命令提示符运行 `scripts\build_offline_guard.cmd "<包目录>"`；或用第二个参数提供自己的 vcvars64.bat 路径。

管理员运行：

```powershell
.\tools\offline_guard.exe "<完整包目录>" "<全新证据目录>"
```

工具为本包五个 Python 解释器、llama-server 和自身创建 IPv4/IPv6 出站连接阻断规则，允许 loopback。规则是动态 WFP 会话，只在验收进程存活期间存在，退出或崩溃都会由操作系统清理。它不禁用网卡、不启用或关闭防火墙 profile，不阻断其他应用。

验收先检查各 Python 运行时及原生 Winsock 外网探针确实返回 `WSAEACCES 10013`，同时检查 loopback 可用，再实际运行四引擎。不能添加规则或探针失败时会停止，不把普通离线模式当作系统断网成功。

日常识别不需要管理员权限；管理员权限只用于这项操作系统层面的验收。
