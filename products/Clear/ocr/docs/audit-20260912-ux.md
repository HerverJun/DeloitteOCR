## 1. P1：保存失败后的「重新加载」会无提示丢弃草稿，请求再次失败时还会清空恢复依据

- **证据**：[App.tsx:830](C:/Users/A/Desktop/OCR/frontend/src/App.tsx:830)、[App.tsx:839](C:/Users/A/Desktop/OCR/frontend/src/App.tsx:839)、[useEditor.ts:122](C:/Users/A/Desktop/OCR/frontend/src/useEditor.ts:122)、[useEditor.ts:132](C:/Users/A/Desktop/OCR/frontend/src/useEditor.ts:132)。保存失败提示只写「校对尚未保存，请重试后再切换资料」，旁边的「重新加载」直接调用 `reload`。函数先清空 `pending.current`，再读取服务器结果；读取失败没有恢复 pending。
- **触发与影响**：断网/本机服务瞬断或编辑冲突后，用户将「重新加载」理解为普通重试。GET 成功时，本地未保存文字和表格会被覆盖；GET 失败时，画面可能仍显示本地修改，但 pending 已丢失，后续 flush 不再保存它，切图或关闭页面也可能失去草稿保护。这与刚修复的迟到请求串图不是同一问题。
- **改进**：改成明确的「放弃本次修改并重新加载」，操作前允许保留/下载草稿；只在 GET 成功且用户确认放弃后替换状态，失败保留 pending、dirty 标记和关闭保护。可以为冲突提供「保留本地副本 / 查看最新版本」。
- **验证**：编辑文字和表格后令 PUT 返回 409，再分别令 reload GET 成功和失败；检查提示、草稿、随后切图/关闭的保护。再恢复连接，验证可重试保存或保存草稿副本。
- **结论性质**：代码确定存在状态清空顺序和提示缺失；完整浏览器路径尚待复测。

## 2. P2：「查看」历史结果隐式改变「采用结果」，影响批量导出

- **证据**：[TaskQueue.tsx:97](C:/Users/A/Desktop/OCR/frontend/src/TaskQueue.tsx:97)、[App.tsx:662](C:/Users/A/Desktop/OCR/frontend/src/App.tsx:662)、[App.tsx:370](C:/Users/A/Desktop/OCR/frontend/src/App.tsx:370)、[App.tsx:394](C:/Users/A/Desktop/OCR/frontend/src/App.tsx:394)。队列按钮标为「查看」，其处理函数却向 `/images/{id}/selection` 写入结果；「当前识别结果」下拉框也复用写入采用状态的函数。批量导出优先读取这个 `selected_result`。
- **触发与影响**：先在对比区采用 A，再从队列「查看」旧结果 B，随后导出选中图片。实际导出将使用 B。用户在专门的「采用结果」按钮之外，难以预期一次浏览会改变正式输出。
- **改进**：把正在预览的结果 ID 和正式采用的结果 ID 分开。浏览历史只更新预览；只有明确「采用」动作更新导出选择。单结果导出在对话框注明导出当前预览还是已采用结果。
- **验证**：采用 A→队列查看 B→离开再返回→批量导出，断言采用标记和输出仍是 A；显式采用 B 后才变化。
- **结论性质**：代码确定的行为与语义不一致；无需假设模型输出质量。

## 3. P2：批量导出的入口受当前预览图片是否有结果限制

- **证据**：[App.tsx:996](C:/Users/A/Desktop/OCR/frontend/src/App.tsx:996)、[App.tsx:387](C:/Users/A/Desktop/OCR/frontend/src/App.tsx:387)、[PhotoList.tsx:100](C:/Users/A/Desktop/OCR/frontend/src/PhotoList.tsx:100)。唯一「导出结果」按钮的禁用条件是 `!editor.result || busy`，但批量导出的目标来自独立的 `selected` 图片集合；勾选图片不会切换预览。
- **触发与影响**：当前打开未识别或失败的图片 A，勾选已经识别成功的 B、C，希望导出 B、C。按钮仍禁用，用户需要额外打开一张有结果的图片才能进入批量导出，选择范围与操作可用性不一致。
- **改进**：提供资料列表的「导出所选」入口，或让全局导出基于目标范围可用；对话框明确当前图片、所选图片、整个项目三种范围及可导出数量。保留现有导出前完整性校验。
- **验证**：A 无结果、B/C 有结果且被勾选时可以直接导出 B/C；选择含无结果项时，在对话框清楚标明受影响图片。
- **结论性质**：代码确定的入口限制，浏览器路径待复测。

## 4. P2：较小工作窗口的新用户首屏隐藏了主要导入入口

- **证据**：[WorkspaceLayout.tsx:36](C:/Users/A/Desktop/OCR/frontend/src/WorkspaceLayout.tsx:36)、[WorkspaceLayout.tsx:48](C:/Users/A/Desktop/OCR/frontend/src/WorkspaceLayout.tsx:48)、[App.tsx:552](C:/Users/A/Desktop/OCR/frontend/src/App.tsx:552)、[App.tsx:811](C:/Users/A/Desktop/OCR/frontend/src/App.tsx:811)。宽度小于 1200 时默认隐藏资料栏；宽度小于 1000 或高度小于 680 时进入单栏，默认显示校对。导入按钮在资料栏，拖入引导在原图区，校对空态却只提示点击「开始识别」。
- **触发与影响**：新用户在 CSS 视口 1024×576（例如小笔记本或放大浏览器窗口）首次打开空项目。资料栏和原图区都隐藏，主要内容提示一个尚不可用的动作；需要先识别左上角展开资料栏图标或自行尝试拖入。
- **改进**：空项目/无图片状态直接提供「导入图片」「导入文件夹」主按钮；空态按当前可执行步骤引导。小窗口下首次显示「资料」文字入口，并根据有无图片选择默认面板。
- **验证**：清除相关 UI 偏好，在 1024×576、1280×720、1440×900 的实际 CSS 视口检查首屏，并通过浏览器回归验证导入→识别流程。
- **结论性质**：断点、默认面板和按钮位置由代码确定；实际遮挡和发现成本缺少实测证据，不作为已截图结论。

## 5. P2：失败、暂停和恢复状态没有进入主工作区的下一步引导

- **证据**：[App.tsx:811](C:/Users/A/Desktop/OCR/frontend/src/App.tsx:811)、[App.tsx:607](C:/Users/A/Desktop/OCR/frontend/src/App.tsx:607)、[TaskQueue.tsx:104](C:/Users/A/Desktop/OCR/frontend/src/TaskQueue.tsx:104)。主结果空态只区分 queued/running 与其余状态；队列折叠摘要也只显示等待/处理中或已完成。失败原因、重试和继续只在展开的队列行内。
- **触发与影响**：没有历史结果的图片识别失败，或重启后任务变成 interrupted/paused，且队列已收起。右侧仍提示「识别结果将在这里显示」「点击开始识别」，用户容易再次创建任务，而非定位原任务并重试/继续；折叠摘要可能显示「0 项已完成」而未提醒失败/待恢复。
- **改进**：主结果区基于活动图片最新任务显示「失败原因 + 重试」「已暂停 + 继续」「等待恢复 + 继续」；折叠队列显示失败和待恢复数量。区分结果正在加载、任务未开始和真正没有结果。
- **验证**：分别构造 queued/running/failed/paused/interrupted/cancelled 和结果 GET 延迟场景，收起队列后仍能准确判断状态并完成对应下一步；重试/继续不生成重复任务。
- **结论性质**：代码确定缺少分支；用户重复提交的发生频率尚无实测结论。

## 6. P2：模型对比缺少可比条件和结果来源，难以支持专业判断

- **证据**：[App.tsx:194](C:/Users/A/Desktop/OCR/frontend/src/App.tsx:194)、[App.tsx:201](C:/Users/A/Desktop/OCR/frontend/src/App.tsx:201)、[App.tsx:944](C:/Users/A/Desktop/OCR/frontend/src/App.tsx:944)、[App.tsx:963](C:/Users/A/Desktop/OCR/frontend/src/App.tsx:963)、[App.tsx:1195](C:/Users/A/Desktop/OCR/frontend/src/App.tsx:1195)。对比加载当前图片全部成功历史结果，不按图像版本或一次批次筛选。卡片只展示模型名称、耗时和 `edited.text`，没有图像版本、处理参数或时间。差异算法按相同行号逐行比较。
- **触发与影响**：同一图片在原图和裁剪版本分别运行四引擎后，对比页可能混合 8 个结果，用户无法快速分清模型差异、输入范围差异和人工校对差异。仅插入一行就会令后续相同内容被报告为大量增删，降低差异结果可信度。
- **改进**：默认比较同一图像版本和同次识别的结果，提供历史范围切换；展示来源版本、预处理、时间和采用状态；明确切换原始识别/人工校对视图。差异采用 LCS 或成熟文本 diff，并支持同图定位。
- **验证**：原图+裁剪各四引擎、同引擎多次识别、人工修改后，确认默认分组和来源清楚。用「A\nB\nC」与「A\n新增\nB\nC」验证仅标注一处新增。
- **结论性质**：代码确定的范围和算法限制；这是决策质量问题，不代表识别结果本身有错。

## 8. P2：批量工作缺少「待校对 / 已确认」状态，识别完成不能表示资料可交付

- **证据**：[PhotoList.tsx:57](C:/Users/A/Desktop/OCR/frontend/src/PhotoList.tsx:57)、[workspacePreferences.ts:39](C:/Users/A/Desktop/OCR/frontend/src/workspacePreferences.ts:39)、[types.ts:50](C:/Users/A/Desktop/OCR/frontend/src/types.ts:50)。图片状态直接来自最后一个 OCR 任务状态，筛选项只有未识别、处理中、已完成、失败；Photo 没有校对确认状态。人工编辑后，列表仍与未经人工检查的识别成功图片展示相同状态。
- **触发与影响**：处理 100～500 张资料时，用户离开再继续，无法从列表识别哪些已经人工核验、哪些有疑问、哪些可以导出；只能凭记忆或外部清单管理。最后一次尝试失败也可能把已有可用采用结果的图片统一显示为失败。
- **改进**：将 OCR 任务状态与人工复核状态分别建模；新增「待校对 / 已确认 / 有疑问」及筛选、下一张待校对导航，确认绑定图像版本和采用结果。结果更新或再次编辑后重新标记待确认；导出可选择仅已确认结果。
- **验证**：20 张成功识别图片中确认 5 张、标疑 2 张，刷新/重开项目后状态不丢失；更换采用结果或编辑已确认内容时确认状态失效；结果仍可用但后续识别失败时两个状态都清楚显示。
- **结论性质**：代码确定的产品能力缺口，属于专业批量工作流提升，非现有功能失效。此处 P2 是产品优先级。

## 已有优点

- 原图、图像版本、原始输出和人工校对分离；结果对应其他版本时会明确提示并能定位，符合专业数据追溯需要。
- 自动保存、保存失败重试、编辑历史以及切换前 flush 已形成完整基础，当前修复加入串行队列与加载代次保护。
- 表格编辑保留文本、前导零和长编号，Excel 的非结构化结果校验与逐图/汇总导出规则明确。
- 图片筛选与选择分开，筛选外已选数量会提醒，并有清空入口；没有把隐藏选择默默忽略。
- 图标按钮普遍有中文 aria-label，表格行列标题支持键盘选择，双栏分隔条支持方向键、Home、End、Enter。
- 文件夹拖入、任务暂停/继续/重试、错误详情和输入完整项目名确认删除均已具备，不需要重做基础工作流。
