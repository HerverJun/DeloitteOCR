少样本文档图像分类框架
调研与技术选型

GitHub 项目调研  2026 年 9 月 18 日

建议采用 PyTorch 与 timm 构建一个精简框架，以冻结视觉编码器和线性分类头作为默认训练方式，使用 ONNX Runtime GPU 批量推理。DINOv2 ViT-S/14 是首轮候选，ResNet18 用作速度与效果基线；DINOv3 小模型纳入条件性对照，最终依据真实截图测试选定一个编码器。

在现成框架中，LightlyTrain 与“类别文件夹输入、训练、导出 ONNX”的流程较接近，可作为减少开发量的备选。其默认训练策略、许可方式和批量任务管理仍需与本项目适配。[19][20][21]

需求与选型依据

| 已明确的需求 | 对技术方案的影响 |
| --- | --- |
| 文档与截图分类，例如发票、收款码截图、其他 | 优先整图分类，保留布局；小二维码存在性判断需单独验证 |
| 二分类起步，扩展到三类、五类或更多 | 统一多类模型，固定类别编号与类别定义 |
| 每类几十张起步，可增加到几百张 | 优先冻结特征与正则化小分类头，标注和评估共用有限预算 |
| NVIDIA A4000 与 A6000 | 支持 GPU 训练和批量推理，以实际驱动和运行环境确定版本组合 |
| 一批通常十几万张 | 流式读图、批处理、断点续跑、持续落盘和特征缓存 |
| 希望交付 ONNX 模型，人力有限 | 交付可复现模型包，并提供少量样本纠错的更新流程 |

本次比较覆盖 12 个 GitHub 项目，核对了项目说明、关键导出材料、模型卡与许可信息，并记录查询时的仓库提交。推荐顺序属于针对本需求的工程判断；业务精度、显存和吞吐尚未实测，不能把公开数据集成绩直接作为上线承诺。

第一版按一图一类设计。若同一图既要标“发票”又要标“含二维码”，应改用多标签标注；若二维码很小，整图缩放可能丢失目标，这属于任务边界问题。

模型组件比较

以下组件提供模型或特征能力。它们可以复用到同一个训练与推理框架中，项目本身并不自动完成数据复核和十几万张任务的恢复管理。

| 项目 | 已核对的能力 | 针对本需求的判断 |
| --- | --- | --- |
| timm [1][2] | 统一模型接口、预训练权重、分类头替换和 ONNX 导出脚本 | 推荐作为模型适配层；导出成功率仍取决于具体模型和版本 |
| DINOv2 [3][4] | 支持冻结特征后的线性分类、逻辑回归及近邻分类；ViT-S/14 约 21M 参数 | 首轮优先验证；少量标注主要用于学习类别边界 |
| DINOv3 [5][6] | ViT-S/16 约 21M 参数，另有 ConvNeXt；已接入 timm | 适合做更新一代的对照；权重获取与自定义许可需要单独处理 |
| OpenCLIP [7][25] | 提供图像和文本编码器，可提取图像特征或做文本提示分类 | 作为替代特征候选；零样本文本提示不能替代本业务的准确率验证 |
| Microsoft DiT [8][26] | 面向文档图像预训练；base 约 86M 参数，有 RVL-CDIP 分类检查点 | 若主要混淆来自文档版式可加入对照；模型更大，旧训练依赖需要适配 |

默认采用冻结特征和线性分类头

将每张图片编码成固定长度向量，固定编码器参数，只训练一个带正则化的多类线性分类器。首轮选取固定的全局特征与归一化方案，避免同时搜索多层特征拼接、大量增强和复杂分类头。若使用 scikit-learn 训练多类逻辑回归，导出时需将相同权重、偏置与特征处理封装进 PyTorch 图；也可直接用 PyTorch 训练线性层。

DINOv2 的官方模型卡明确支持线性层和逻辑回归这类下游用法。[4] 这支持本方案的可行性，但不证明它必然胜过 ResNet18，也不证明几十张样本足以覆盖任意中文截图。

分辨率应跟随模型与业务共同确定

DINOv2 的 patch 大小为 14，官方说明输入尺寸不整除时会裁去末端；建议先比较 224 与 336 两档，不应把 320×320 固定为所有模型的统一输入。[4] 长截图优先验证完整内容缩放加补边；如果关键局部仍消失，再考虑分块或检测，不用增加网络规模掩盖输入信息损失。

训练与部署工具比较

| 项目 | 已核对的能力 | 选择建议 |
| --- | --- | --- |
| LightlyTrain [19][20] | 类别文件夹和 CSV、多类与多标签分类、DINO 模型、ONNX 与 TensorRT 导出 | 最接近完整训练流程的备选；需要调整截图增强及核对冻结策略 |
| PaddleClas [10][11] | 分类工具；PP-ShiTu 包含检测、特征提取和向量检索，提供 Paddle2ONNX 路径 | 已有 Paddle 工程时有价值；检索库需随部署交付，不能视为单个分类 ONNX |
| EasyFSL [9] | 原型、近邻及多种少样本方法，支持文件夹样本和预提取特征 | 借鉴方法与评估；首版采用简单独立预测，避免查询批次影响结果 |
| MMPreTrain [12] | 监督与自监督训练、多模态、模型分析与配置体系 | 已有 OpenMMLab 团队可复用；本任务引入完整体系的收益有限 |
| Ultralytics [13][14] | 分类训练、验证与 ONNX 导出接口完整 | 快速基线候选；文档裁剪和 AGPL 或商业许可是实际取舍 |
| ONNX Runtime [15][16] | ONNX 推理、CUDA 等执行后端、跨语言部署 | 推荐作为正式推理层；单独处理驱动、CUDA 与 cuDNN 兼容 |
| timmx [22] | timm 多格式导出、动态 batch、可嵌入归一化和输出校验 | 可作为导出辅助；其依赖追随较新版本，首版不作为必须组件 |

LightlyTrain 的分类文档已经给出 model.export_onnx()，因此它应进入实际候选，而不只是被视为预训练工具。[20] 不过，其示例默认含随机裁剪和水平翻转，直接用于文档截图前需要调整；完整训练框架也仍需外层的数据分组、特征缓存与复核预算控制。

EasyFSL 包含依赖整批查询样本共同估计的传导式方法，其公开耗时基于预提取特征。[9] 本项目需要独立图片结果稳定、任意 batch 和断点恢复，因此优先选择固定编码器加固定分类头的推理形式。

推荐主线为 timm 加少量任务代码；若团队希望最大限度减少训练和导出开发，可先评估 LightlyTrain 的适用性，再决定是否采用。两者只选一个正式训练入口，共用同一模型包与推理协议。

控制标注与维护成本

建议先用“发票、收款码截图、合同、其他”做一个四分类试验。类别按整图主要类型互斥定义；带二维码的发票仍归发票。若业务目标是“任何图片中存在二维码”，另设存在性任务，并保留小目标样本验证召回。

| 环节 | 建议的人工预算 | 用途 |
| --- | --- | --- |
| 初始目标类别 | 3 类各 50 张，共 150 张 | 覆盖不同模板、来源、分辨率与拍摄或截图方式 |
| 初始其他类别 | 100 张 | 包含普通杂图及收据、订单、报销单等相似负例 |
| 独立评估 | 从上述预算中预留各类约 20% | 按来源和近重复分组；测试数据不用于训练和调阈值 |
| 纠错更新 | 最多先做 3 轮，每轮 40 张 | 用于验证有限投入下是否有持续收益 |
| 试验总预算 | 约 370 张人工确认图片 | 这是试验工作量示例，不是精度达标所需张数 |

若每类目前只有三十张，先按实际样本运行同一流程，并明确评估不确定性。训练部分可以用按来源分组的交叉验证选择少量参数，独立测试集保持不变；组数不足时，记录限制，不进行大量模型和参数反复筛选。

每轮只交给人少量有价值的图片

每轮 40 张可以先分为约 20 张边界模糊样本、10 张外观新颖样本和10 张分层随机抽查，优先去除高度重复的图。具体配额属于工作流建议；目标是同时发现边界错误、新模板，以及模型高分误判。人工确认的标注才进入下一版训练集。

主动挑出的难例不代表总体错误率。总体质量要用独立测试及按真实业务来源抽样的结果评价；若分层抽样改变了类别占比，汇总精确率时需按实际抽样比例加权。

其他类和待复核状态分别维护

“其他”需要明确的负例样本；它不等于模型见过所有非目标图片。“待复核”是输出状态，表示当前分类未达到接受条件。低分拒绝不是可靠的未知类别检测，高分也不保证正确。

十五万张中即使只有 1% 待复核，也有 1500 张。系统应保留完整未确认清单，并只挑选当轮人工预算内的代表样本；未确认图片不能自动计作正确分类。若业务要求全部图片最终归类，应另行计入所需人工或接受相应错误率。

模型交付与批量推理设计

训练侧负责样本清单、固定划分、特征提取、分类头训练、评估和导出。推理侧独立使用 ONNX Runtime，加载一次模型，按批处理图片并持续记录结果。部署逻辑与训练框架解耦，方便之后替换编码器。

| 交付内容 | 必须记录的信息 |
| --- | --- |
| model.onnx | 编码器、特征归一化和分类头；固定 H/W、动态 batch；明确输出为 logits 或概率 |
| metadata.json | 类别编号、RGB 顺序、缩放补边、插值、输入布局、归一化、阈值、模型与预处理版本 |
| metrics.json | 测试集与分组版本、各类指标、接受覆盖率、拒识率、导出一致性、硬件与吞吐 |
| 训练与版本记录 | 权重来源和哈希、训练配置、样本清单、软件锁定版本、可恢复的分类头检查点 |

普通 ONNX 张量输入不自动包含文件读取、JPEG 解码、EXIF 方向和任意尺寸图片预处理。这些步骤由统一推理封装执行，并与训练侧共用一份确定的处理契约。[2][23] 原始文件与训练样本按版本保留，纠错不直接覆盖旧模型。

让十几万张任务可恢复

图片扫描、CPU 解码预处理、GPU 推理和结果写入采用有界队列衔接。先测试 batch 16、32、64 等少量档位，以吞吐和显存选择；不因 A6000 显存更大就把整批图片加载进内存。坏图记录失败原因，任务可继续；断点恢复依据文件身份与模型版本，避免漏跑和重复归档。

结果至少包含图片路径、文件身份、预测类别、分数、接受或待复核状态、错误信息及模型版本。先写 CSV 或 JSONL；按类别复制图片作为独立可选步骤，单独统计耗时。

缓存只在模型和预处理一致时复用

DINOv2 小模型的全局特征为 384 维。[4] 十五万张以 float32 保存特征的原始数组约 230 MB，另加文件索引和元数据。该数值是容量换算，不是实测文件大小。缓存键绑定图像内容、编码器权重、输入尺寸、预处理和特征提取方式；修改其中任何一项需重新提取。

只改分类头时，可以直接利用缓存重新分类。初次推理仍需完整运行编码器。FP32 先建立正确性基线，FP16 经指标与阈值一致性验证后启用；只有确有计算瓶颈时再引入 TensorRT。CUDA 与 cuDNN 按 ONNX Runtime 官方兼容表匹配。[16][17][18]

验证方案与通过条件

先解决数据可分性与导出正确性，再投入界面和极限加速。模型对比共用相同分组划分、标签、预处理约定和评价口径；评估集上反复挑出的最优结果不能再被当作独立测试成绩。

| 阶段 | 执行内容 | 决定什么 |
| --- | --- | --- |
| 一  数据与基线 | 固定类别定义和样本划分；跑 ResNet18 与 DINOv2 小模型的冻结特征加线性头 | 少样本能否分开目标类与相似负例 |
| 二  有限纠错 | 最多先做三轮，每轮人工确认40张；记录每轮收益与用时 | 在可接受人力内，误报和漏报是否下降 |
| 三  条件性对照 | 需要时加入 DINOv3；版式混淆明显时再比较 DiT 或 OpenCLIP | 效果不足来自特征、输入信息还是样本覆盖 |
| 四  导出核对 | 同一输入比较 PyTorch 与 ONNX；覆盖单张、多张和末尾不足一批 | logit 偏差、类别与拒识结果是否符合约定 |
| 五  批量验收 | 代表性图片先测吞吐，再跑十五万张；验证坏图、重复文件、重启恢复 | 业务整批时长、结果完整性与资源使用是否可接受 |

评价指标应反映人工成本

报告每类 precision、recall、F1、混淆矩阵、目标误报数、漏检数、接受覆盖率、待复核量及人工分钟数。二分类中应明确误报率的分母是所有负例，不能与精确率混用。小测试集只能支持粗略判断，应同时列出实际样本数和错误数。

例如十万张中有1000张发票，召回率95%会找到950张；若其余99000张的误报率为1%，还会混入990张，输出发票的精确率约49%。这个假设说明，类别稀少时“总体准确率高”不代表筛选结果好用。

速度目标需要计入全链路

以十五万张为例，一小时完成需要约41.7张每秒，二十分钟需要125张每秒。这是目标换算，不是对 A4000 或 A6000 的性能承诺。分别测量解码预处理、GPU 前向、结果写入和图片复制，并记录输入分辨率、batch、精度及磁盘条件。

业务尚未指定可接受的误报、漏报和完成时长。首轮应提供不同阈值下的质量与复核量，由实际成本确定接受条件；若改善停滞，应检查长图缩放、类别重叠和文字依赖，再决定是否增加局部分析或 OCR。

实施顺序与许可取舍

第一版必须具备的能力

统一类别文件夹或路径清单；坏图和近重复分组；固定训练评估划分；冻结特征与分类头；ONNX 模型包；批量推理、断点恢复和结果清单；可按预算导出待确认图片并导入修正标签。模型候选经验证后保留一个默认配置。

优先用命令行和配置文件建立完整运行路径，复核界面只需支持缩略图、快捷改类和确认保存。多 GPU 调度、向量数据库、复杂元学习、自监督重训练与大模型自动标注留待出现明确收益时再加入。两张 GPU 可以分别处理任务，初版不必实现分布式训练。

现成框架与精简框架如何选择

本需求的默认选择是 PyTorch 加 timm：冻结特征后的训练逻辑较小，能够直接围绕缓存、少量人工复核和模型包设计。LightlyTrain 已提供更完整的训练和导出流程，可减少开发量；若选择它，需要验证其训练方式能否满足少样本预算，并保留同一批量推理协议。[1][19][20]

PaddleClas 的 PP-ShiTu 提供更接近“样本库检索”的现成能力，适合类别频繁变化的识别流程。[11] 但样本库、特征与检索后处理属于额外部署资产；首版固定三五个类别并要求完整 ONNX 分类器时，线性分类头更便于交付。此判断针对当前需求，不是通用算法优劣结论。

许可与版本需要随具体权重记录

timm 代码为 Apache-2.0，DINOv2 官方通用模型卡标为 Apache-2.0，ONNX Runtime 为 MIT；timm 中不同预训练权重仍需分别查看来源。DINOv3 使用自定义许可，官方权重入口包含申请接受流程，不能将它记为 Apache-2.0。[1][4][6][15]

Ultralytics 与 LightlyTrain 提供 AGPL 和商业许可路径。将模型转成 ONNX 不能被理解为自动消除原有许可条件。OpenCLIP 代码许可与每个权重的条款也应分别记录。以上用于说明技术选型的依赖差异，具体交付范围以所选版本及权重条款为准。[14][21][25]

仓库更新不等于业务效果

timm 发布页在调研时列出 v1.0.29；OpenCLIP 主分支提示训练接口重构，并建议需要旧稳定接口的使用者固定 v3 分支或3.x发行版。[7][24] DiT 原始训练说明包含较旧 PyTorch 与 timm 依赖，宜复用模型而非直接搬用旧环境。[8]

EasyFSL、MMPreTrain 和 PaddleClas 的所查默认分支提交时间较早，见下一页。它们仍有可复用能力，但新建项目应先验证安装、导出和 GPU 运行组合；一次提交的早晚不能单独证明项目质量或停止维护。
