# 本地 OCR 模型与产品发展评估 · 2026-09-18

结论：现有 PP-OCRv6 medium、PaddleOCR-VL-1.6、GLM-OCR、HunyuanOCR-1.5 是有竞争力的本地部署组合。在本次核对的官方仓库范围内，已打包的主要权重没有明显落后；但不能称为囊括当下所有最强模型。新出现的 TeleOCR、OvisOCR2 值得参与同条件测试。产品下一阶段的主要机会包括复杂表格、漏识别、局部复核、可编辑输出和运行成本；仅增加模型数量，不能证明最终质量提高。

本次工作核对了本项目配置、E 盘交付包的模型锁定记录、已有质量报告，以及官方 GitHub / Hugging Face 元数据、模型卡和 OmniDocBench 仓库。只下载了公开文本与元数据，没有下载新权重、执行候选模型代码或更换交付包。本文中的候选效果和资源需求来自上游资料；新模型均未在本项目实测。核对时点为 2026-09-18，未来仓库和榜单可能变化。

## 现有四个引擎：强在哪里，版本是否落后

| 引擎及项目实际路线 | 核对结果 | 合理定位及局限 |
|---|---|---|
| PP-OCRv6 medium；Paddle native CUDA，检测、识别、方向分类 | medium 检测和识别权重与当前官方仓库头一致。官方 v6 提供 tiny / small / medium 三档，medium 是其中最大的档位 | 快速文字识别、真实文字坐标及置信度，是复核定位的重要底座；不能独立提供完整表格结构，不能用文档解析榜单给它排名 |
| PaddleOCR-VL-1.6；Paddle 完整文档解析 + PP-DocLayoutV3 | 权重与当前上游一致；官方 2026-05-28 发布 1.6，同范围未发现更高编号的 VL 正式权重 | 当前主力文档解析候选，表格、公式、复杂版面有竞争力；区域框不等于可靠的逐字、逐格坐标 |
| GLM-OCR；Transformers BF16 + 官方 SDK 版面/裁剪/格式化组件 | 当前仓库头变化，但逐文件比较确认模型权重未变；config、tokenizer config、README 改变，新增 processor config | 保留为不同识别器和困难样本对照；新配置需与运行时联动回归，不能将仓库更新理解为更强的新权重 |
| HunyuanOCR-1.5；llama.cpp b10894 / Windows CUDA 12.4 / F16 GGUF + 视觉投影 | 来源 tencent/HunyuanOCR 的锁定版本与当前上游一致；官方最新介绍为 1.5 | 在现有小规模回顾性样本中有互补价值；当前交付路线未启用官方另行提供的 DFlash 加速分支 |

部署可行性进一步区分如下：

- **TeleOCR**：2026-08-17 以 NaviDC-OCR 名称发布，09-10 改名。官方给出 Transformers / PyTorch 路线，也链接社区 GGUF / llama.cpp 支持。其官方模型卡和元数据标注 Apache-2.0。适合先试原始精度，再验证 GGUF 转换与实际文档流程；不能假定已有社区 GGUF 与最新仓库权重完全一致。HF 张量统计约 14.15 亿参数，与官方“约 1.2B”的标称计数不同，因此容量估算应以实际文件为准。本次原始 safetensors 约 2.83 GB，不能把文件大小当峰值显存。
- **OvisOCR2**：Qwen3.5-0.8B 后训练而来，模型卡标注 Apache-2.0。官方示例依赖 vLLM 0.22.1 与 Triton GDN prefill，提供整页 Markdown / HTML 表格。其官方示例不能直接证明 Windows 原生可用；需验证兼容推理实现，或在允许的 Linux 环境独立测试。原始权重约 1.71 GB，同样不等于总显存需求。整页输出还需校验遗漏、重复、阅读顺序及坐标回连。
- **MinerU 4.0**：这里的 4.0 是软件产品版本，不能称为“4.0 OCR 权重”，也不能直接赋予 MinerU2.5-Pro 的榜分。当前 README 描述默认 ONNX + llama.cpp Vulkan 路线并给出 Windows 安装方式，值得研究较轻的部署包、多格式输入和结构化导出。上游称标准/高级这条路线模型下载约 2 GB、最低 RAM 8 GB；这些不是应用完整体积或本机测量值，不能与本项目 26.94 GiB 完整 ZIP 直接比较。当前 LICENSE 为 Apache-2.0 加附加条件：关联方合并月收入超过 2000 万美元或 MAU 超过 1 亿涉及另行商业许可，向第三方提供在线服务还有标识要求。企业正式选型应按该版本许可确认适用条件。
- **Unlimited-OCR**：提供多图 / 多页联合推理；可作为跨页表格、连续段落和长期上下文的一条探索线。需要测长输出稳定性、峰值显存和是否增加跨页串行/幻觉，不能把单页准确率较低简单视为这个方向没有价值。

以上候选的官方可部署资料不等于在本项目 Windows + 16 GB 显存环境完成适配。当前交付包在 RTX 4070 Ti SUPER 16 GB 实测过四引擎和审校；目标 A4000、干净 Windows 和内网真实材料仍需单独验证。

## 最值得投入的改进

**第一优先级：建立真实业务的比较基准，并改善表格结构与定位。**

现有 `docs/tableformer-next-20260915-quality.md` 的新测试覆盖 120 文档、11,278 格：TableFormer-local-v3 在实际采用结构上的正确完整格定位覆盖为 69.71%，合并格为 43.75%，仍未通过生产质量门槛。这是几何定位覆盖，不是文字识别准确率。它指出行列跨度、空格、重复值、缺失输出和坐标对应有实质缺口。更好的表格文字模型并不会自动解决这些问题。

下一步应把结构完整性、内容正确性和坐标正确性分别计分；探索版面/表格召回、表内多尺度裁剪、跨页表头合并和可靠坐标回连。PP-StructureV3 的细粒度坐标路线可作补充比较，但不能未经实测便宣称替代 TableFormer 或已有定位方案。对于金额、日期、编号、负号和单位，应检查精确匹配与错列；合计/勾稽规则可触发复核，不能凭数学一致性强行改写原文。

**第二优先级：依据困难程度调用模型，并用局部证据纠错。**

现有程序已经有原生 PDF 文本优先路径、引擎选择、单 GPU 队列和局部审校，因此发展方向是在这些基础上增强质量判断与升级策略。例如原生文本质量检查、漏区检测、困难区域高分辨率重识别、第二引擎交叉核对、最后才给人看无法确定的分歧。PP-OCR 的字符置信度和 VLM 的表面自信程度不是同一尺度；需用业务验证集校准转交阈值。

PaddleOCR-VL 和 GLM 在当前项目中共用 PP-DocLayoutV3，版面阶段漏掉同一个区域时，多数投票很难补救。应评估能够提供新增正确区域、不同错误模式的模型，而非仅增加相似来源的票数。OvisOCR2 的整页路线、TeleOCR 的几何布局能力因此有探索价值，但有效互补性仍须实测。

`docs/fusion-quality-report.md` 已记录：自动候选替换缺少稳定验证收益，当前关闭；其历史样本有回顾性曝光，不能据此认定泛化效果。未来应直接测量“修正多少、引错多少、漏掉多少、减少多少人工时间”，并继续保留来源和撤销能力。

**第三优先级：增强审校模型，但优先保证证据输入。**

现有 Qwen3.5-4B 在有可靠局部框的合成页上可纠错，缺框、跨列或密集数字情况下也出现过错误建议。先保证足够清晰的原图、局部框和上下文，再比较 4B 与 Qwen3.5-9B 的量化版本。9B 是 16 GB 卡值得试验的候选，不是已保证能与多模型常驻、高分辨率多图和长上下文一起运行的配置；应串行加载并测峰值显存、超时和净纠错。

截至本次核对，通用视觉模型也已出现 Qwen3.8-27B（官方卡声明支持图像/视频，配置包含视觉编码器）。因此早前将 Qwen3.6 视作最新 Qwen 的调查结论需要更新。但约 27.8B 张量参数的理想 4-bit 裸权重就约 13.9 GB，实际量化元数据、视觉编码器精度、缓存和运行时开销还会增加；不能作为 16 GB 显卡的无条件默认升级。可在更大显存服务器上作为困难页审校对照，或单独测 CPU/GPU 混合路径的时间成本。MoE 的活跃参数量也不等于需要驻留的总权重。

**第四优先级：把输出做到业务可用。**

当前应用已有 TXT、Markdown、JSON、XLSX、可搜索 PDF；尚无 OCR 结果直接导出 DOCX 的产品流程。PaddleOCR 官方 3.5.0 已为 VL 系列及 PP-StructureV3 等增加 DOCX 导出，因此可以评估复用上游组件，减少重复实现。可编辑 Word 的标题层级、段落、表格、分页与原版视觉还原是不同质量目标，应分开验收。

新增导出必须反映用户已采用的修订和结构，不能绕过工作台直接导出某引擎未校正的原始结果。进一步可以发展业务模板：合同要素、票据字段、明细表、字段来源坐标、校验结果和可追溯 JSON/API。检索与文档问答适合在来源稳定后扩展；金额、表格查询应尽量依据结构化数据计算并引用原页，避免完全依赖生成文字。

**第五优先级：缩短时间、减轻部署，再开展领域训练。**

Hunyuan 官方已提供 DFlash 及专用 llama.cpp 分支，可单独比较当前 F16 普通解码、量化和 DFlash 的端到端性能与输出一致性。官方通用硬件上的加速数字不能直接套用到 A4000。Paddle 的 HPD-Parsing 是高吞吐方向，但依赖定制 vLLM，当前更适合服务器研究线。也可评估按需引擎包、运行时共用、缓存、分辨率调度及 CPU/ONNX 路线，分别度量下载体积、冷启动、首结果时间和整批 P95。

领域微调应放在收集足够真实错误、固定标注规范之后。优先比较局部重识别和规则能否解决问题；对剩余稳定错误再考虑 OCR 微调、视觉语言模型 LoRA 或蒸馏。必须按原始文档、业务模板和来源分组隔离测试；模型辅助标注需要人工核对，不能用模型自己的答案证明自己正确。

## 可执行的比较顺序与采用条件

下面是建议的实验计划，不是已经取得的效果或排期承诺。

1. 冻结当前交付包为基准，从内网测试收集 300–500 页、按业务分布抽样的材料；补足拍照畸变、低清扫描、中文手写、印章遮挡、密集数字、复杂合并格和跨页表格。按原始文档分组，留出未参与开发的一部分；至少由第二读者复核关键字段和困难标注。
2. 先用约 50 页困难样本做部署/资源/失败模式筛查：TeleOCR 原精度优先；OvisOCR2 单独验证运行时；MinerU 4.0 作完整产品对照并确认许可适用条件。淘汰无法稳定运行或没有互补收益的候选，不为数量接入。
3. 对进入正式比较的候选固定权重、提示词、分辨率、解码、硬件与时间边界，在同一批材料上比较；保留原图、原始输出和失败分母。裁剪级试验不能替代整页召回试验；旧版/新版/不同量化分别记录。
4. 核心指标包括严格字符错误率、关键字段全串正确率、表格内容/拓扑/跨度、漏区与重复、正确坐标覆盖、每页 P50/P95 时间、峰值显存和失败率。人工流程另测每页复核时间、最终漏错和引入错误，不能用模型测试代替真人效率测试。
5. 开发集用于路由和阈值，验证集用于选择，封存测试只评一次。按文档做成对比较/置信区间，预先确定可接受的关键字段退步和耗时预算。只有净质量收益或明确成本收益成立，才替换相应路由；低频但严重的错误单列，不能让均分掩盖。

现有项目已具备开展内网试用的基础：离线封装、多模型、结构审阅、来源定位及多种导出形成了可用工作流。是否足够有竞争力，最终要用本单位材料证明比当前人工/现有工具更快、最终漏错更少、维护成本可接受。本次公开资料与已有测试不足以支持“行业最强”或“大部分业务可无人复核”的承诺。
