# DeloitteOCR 多引擎投票融合可行性

> 本文保留初次可行性调研及当时的候选算法示例。用户提出的“50%以上”仅是举例，不是固定指标。下文严格多数、至少三个有效来源、固定票数及先不做加权等建议均不作为当前要求；样本划分、算法比较、两档策略和工期统一以 [整体开发计划](../docs/DeloitteOCR-多引擎融合与快速校对开发计划.md) 为准。

调研日期：2026-09-12。问题：多个 OCR 引擎交叉识别，对表格或文本按超过 50% 的支持票生成可信结果，是否有开源实现，是否适合 DeloitteOCR 工作台。

**可行，属于 OCR ensemble / consensus fusion / voting 的已有技术方向。** 本轮找到字符对齐后投票、异构引擎加权候选选择，以及跨引擎对齐与分歧仲裁的开源实现。但未验证到一个能直接接管 DeloitteOCR 四引擎、中文拍照表格、合并单元格、人工修订和 Windows 离线交付的成熟完整组件。

本轮检查了 GitHub 搜索结果、7 个候选仓库的 README/元数据，并重点读取 Calamari、FusionOCR、ocr-read-packaging 的相关源码。未安装上游应用、未加载模型、未进行同样本准确率评测。下面的算法与产品建议不是已经实现或已经验证的收益。

**具体项目与代码证据**

| 项目 | 实际做法 | 能借鉴的部分与限制 |
|---|---|---|
| [Calamari](https://github.com/Calamari-OCR/calamari) | `SequenceVoter` 同步对齐多个字符串后逐字符计票；`ConfidenceVoter` 汇总字符候选概率 | 最直接的序列投票参考；主要是 OCR 模型集成及文字行识别，不是完整表格融合工作台。查询时 1,199 Star，GPL-3.0 |
| [FusionOCR](https://github.com/MxxScott/FusionOCR) | 当前主代码组合 TrOCR handwritten、TrOCR printed、EasyOCR、Tesseract，以加权 Levenshtein 距离选择词候选并输出分歧行 | 接近异构多引擎融合；面向儿童英文手写，仓库规模小、查询时 0 Star。当前按词下标组合，不能直接用于有漏词/插词的中文文档或表格。MIT |
| [OCR-D CIS](https://github.com/cisocrgroup/ocrd_cis) | `ocrd-cis-align` 对齐多个 OCR 结果；另有学习式后校正流程 | 可研究可靠对齐和已有识别结果的统一表示；不是现成多数投票器。查询时 33 Star，最近 push 2024-08-16，MIT |
| [ocr-read-packaging](https://github.com/alessandromaddaloni98/ocr-read-packaging) | 双引擎处理同一区域，以 Needleman–Wunsch 对齐比较；有分歧时交给可选 VLM，不能判断时返回未决 | 适合参考对齐、候选来源、未决状态和按需仲裁；产品目标是包装文字与参考图比较，不是自动合成 Excel。查询时 0 Star，MIT |

另外查看了 [MeterVision](https://github.com/bejranonda/MeterVision)、[HDARP](https://github.com/andenick/hdarp) 和 [Scribe.js](https://github.com/scribeocr/scribe.js)。MeterVision 文档描述仪表识别投票，但仓库简述和 README 的引擎组合不同，本轮没有把它作为已核实的实现主证据；HDARP 自述的准确率并非已审计基准；Scribe.js 当前文档说明额外识别与检查，但本轮未核实为通用多数投票接口。

关键源码：

- [Calamari SequenceVoter](https://github.com/Calamari-OCR/calamari/blob/master/calamari_ocr/ocr/voting/sequence_voter.py)：`process_text` 调用 `synchronize`，`perform_vote` 计票并返回字符及票数占比。它选择最高票字符，只提供其自身的候选选择机制；DeloitteOCR 的接受与未决策略需要另行验证，不能整段照搬。
- [Calamari ConfidenceVoter](https://github.com/Calamari-OCR/calamari/blob/master/calamari_ocr/ocr/voting/confidence_voter.py)：使用字符备选及模型概率。DeloitteOCR 当前三个结构表样本没有单元格概率，无法直接套用此输入假设。
- [FusionOCR main.py](https://github.com/MxxScott/FusionOCR/blob/main/main.py#L190)：`_weighted_pick` 最小化加权编辑距离；其 `confidence` 是距离变换的启发式分数，不是实际得票比例或经验证的正确概率。`consensus` 使用英文空格分词和同下标选择，且有两个 TrOCR 高分一致直接返回的分支。
- [包装文字对齐模块](https://github.com/alessandromaddaloni98/ocr-read-packaging/blob/main/src/ocr_read_packaging/alignment.py)：可参考序列对齐思路；包装应用用于弱化排版/词序差异的归一化规则不能直接用于金额、编号和表格列顺序。

**初次讨论中的严格多数示例（不是固定产品要求）**

第一，采用严格多数 `> 50%`，不是 `>= 50%`。四个来源的 2:2 没有多数；三个来源的 1:1:1 也不能因某个候选排在前面就选它。

第二，票率表示支持程度，不表示正确概率。例如“3/4 引擎支持”是可核查的事实；“75% 概率正确”需要有独立标注数据进行校准。多个引擎可能共享模型家族、训练材料、版面处理过程，或者一起受模糊图像影响。因此同错并非独立事件，四路一致仍可能识别错数字。

第三，分母和弃权必须事先定义。建议首版固定每类任务的预期参与集合：有能力承担该识别单位的引擎各一票；失败、超时、不支持该任务、无法可靠对应、图像版本不同等状态分别记录。不能悄悄删除失败来源，让仅剩的一票显示为“100% 共识”。重复调用同一模型或同一模型的多个提示词也不默认增加独立票数。

建议保存 `预期来源数 / 有效来源数 / 支持数 / 弃权原因`。首版的决策支持率用“支持数 ÷ 预期有能力参与的来源数”，同时展示有效覆盖率；至少 3 个有效来源且严格过半，才进入自动共识候选。这样 3/4 支持、另一路失败仍可能满足规则；2/3 支持但第三路失败，只剩两路有效，则继续列为待复核。这里是建议的保守初始规则，后续用业务标注样本调整。

**按 DeloitteOCR 当前能力讨论投票范围（票数为历史候选示例）**

| 任务 | 首版可用来源 | 建议识别单位与多数门槛 |
|---|---|---|
| 一般文字 | PP-OCRv6、PaddleOCR-VL、GLM-OCR、HunyuanOCR | 对齐后的文字行/片段；4 路至少 3 票 |
| 表格结构 | PaddleOCR-VL、GLM-OCR、HunyuanOCR | 对应同一张表的结构候选；3 路至少 2 票 |
| 表格内容 | 上述 3 路结构表结果 | 在可靠结构对应下按单元格完整字符串；3 路至少 2 票 |
| PP-OCR 对表格的辅助读取 | PP-OCR 有文字坐标、无结构表 | 可作为有可靠区域关联时的辅助证据；不能直接给行列/合并关系投票 |

所有计票都以实际成功且可对应的结果为前提。若以后建立了可靠单元格裁剪，再让 PP-OCR 识别同一裁剪区域，可以将它作为该区域文字内容的第四票；这需要新增、明确记录的区域识别任务，不能从现有整页文字下标推造第四票。

表格数量和单元格几何需要单独处理。目前已检查的三个结构表样本没有单元格 polygon/置信度。文字内容投票可从保守的表格/行列对应起步，但不能据此承诺每格均有原图精确定位。

**推荐的融合流程**

1. 固定同一图片版本、批次及引擎版本，收集原始输出和失败状态。沿用单 GPU 串行队列，融合本身在 CPU 处理已有结果。
2. 先建立文字区域或表格对应关系。多表交换顺序、漏行、重复表头、合并结构不同都可能造成错位；对应不可靠的区域进入结构复核。
3. 对表格结构先投票或明确选择一个完整结构骨架。结构比较包括行列、单元格覆盖与合并关系，不能只按相同行列数判定相同。首版优先采用已有的完整结构候选；不将不同模型的合并关系随意拼接。标题/表头和图像来源也用于识别是否同一表。
4. 在可靠对应的结构内，对每格完整字符串投票；对普通文本先对齐行/片段，再做字符或局部片段投票，最后按阅读顺序组回段落。
5. 达到规则的值自动进入新的“融合结果”；平票、来源不足、结构未决的位置标明待复核。数字、金额、日期、编号按完整字段取候选，避免逐字符拼出没有任何引擎完整支持的数字。缺字、空字符串与识别失败分开表示。
6. 检查结构合法性、来源和版本一致性。可用的合计等业务约束只用于提示冲突；不能据此自动改写原图内容或猜测公式。
7. 保存融合值、每个原始候选、支持来源、支持比例、弃权原因、规则版本及人工修改。融合结果是新的衍生对象，不能冒充某个单引擎原始输出。
8. 未决部分交给既定的快速校对清单处理。高共识内容可用于自动生成输出，但仍保留“规则自动通过”和“人工确认”两种不同状态，避免把自动计票计为人工复核。

不建议直接对整段文字要求完全相等，也不建议整张表只选票数最多的文件。长段落里少量换行或空格就会让整段失去多数；同一张表的不同格可能分别由不同模型识别得更好。以结构和字段为单位才能有效组合优势。

**示例：三个结构引擎的同一金额格**

| 来源 | 候选 |
|---|---|
| PaddleOCR-VL | `1,280.00` |
| GLM-OCR | `1,280.00` |
| HunyuanOCR | `1,260.00` |

在同图、同格、三个来源均有效的前提下，融合值为 `1,280.00`，记录“2/3 支持，66.7%”；另一个候选及出处保留。这允许自动输出一个明确选择的候选，并不声称它有 66.7% 的正确概率。字段是否可以自动确认，仍由业务样本验证后的接受规则决定。

金额三路全不同，则保留未决；首版不通过字符拼接或语言模型润色制造一个第四种金额。普通文本可以在可靠字符对齐后组合局部多数，但也要保留插入/删除与未决跨度，避免隐藏少数引擎独有的真实内容。

**接到已有借鉴计划的方式**

在 [差异驱动快速校对计划](../docs/差异驱动快速校对-借鉴实施计划.md) 中增加“共识融合”层：

`已有识别结果 → 可靠对应 → 结构/字段投票 → 融合结果及未决清单 → 快速人工校对 → 导出`

先用已保存结果离线回放，实现无界面的原型及报告。优先选择三个结构引擎、结构一致的表格单元格；基础票制先一源一票。加权票制、置信度校准、局部追加识别及自动仲裁放在初次试点后评估。不能把不同模型未经校准的 confidence 直接平均当权重。

融合来源、保存、撤销、确认和导出需要新增数据语义，原有计划的 8–12 人日不能未经重新拆分就承诺包含自动融合；首轮验证可以先只生成独立 JSON/Excel 原型，不改现有采用结果与工作区数据。

**该方向是否有效，应怎样验证**

- 固定真实样本和同一批原始结果，对比每个单引擎、严格多数融合、人工修订后的最终结果。
- 表格同时看结构正确率与完整单元格准确率；金额/编号另外看完整字段正确率。普通文本看 CER、漏字和多字。
- 记录自动通过覆盖率、自动通过内容的错误率、未决比例、人工校对时间、总识别耗时。不能只报告全部内容的平均准确率，把少数错误的金额藏在大量正确字里。
- 检查“融合改对多少处、改错多少处、最佳单引擎正确但被多数覆盖多少处”，据此判断增益是否真实。
- 权重与自动接受阈值只在开发集确定；用另外的保留样本验证。前述 20 张适合初步验证，不能据此认定可无人复核处理所有内网文档。
- 多引擎成本也需要计算：初版先使用已有结果，后续再比较“固定三/四路”与“先识别、分歧再追加来源”的成本和收益。两个先行引擎一致可能同错，不能把这类提前停止直接视为严格四路投票。
