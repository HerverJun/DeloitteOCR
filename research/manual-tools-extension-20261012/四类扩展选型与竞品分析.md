# Clear 手动工具扩展：图像篡改、人脸、音频、印章选型与竞品分析

调研日期：2026-10-12。现有正式版本：Clear v0.9.4 手动工具美化版。目标环境：Windows 11 专业工作站版、RTX A4000 16GB 或 RTX A6000 48GB、内网离线交付。本轮为资料与源码结构调研，没有安装依赖、下载模型权重、运行新算法或修改正式系统。

## 1. 建议先确定的选型结论

四个方向都有可参考的公开实现，但成熟度、许可和能输出的结论差别很大。优先考虑印章识别、人脸比对和音频转写；深度篡改检测应先在实际资料上验证，作为现有图像取证的补充。

| 方向 | 建议主路线 | 备选或参照 | 对现有产品的建议 |
|---|---|---|---|
| 图像篡改 | 现有六类经典工具 + CAT-Net 的受控验证；通用图像与文档文字篡改分别评估 | TruFor、Mesorch、DocTamper/OSTF；IMDL-BenCo/ForensicHub 用作评测参考 | 扩展 ClearForensics，不重新造一套重复的取证应用 |
| 人脸 | OpenCV Zoo 的 YuNet + SFace，先做单图检测、两图比对、有限参考库检索 | InsightFace 在解决权重授权后比较；高要求可比较 FaceMe SDK | 共享 ClearClassify 的图像操作组件，身份比对使用独立工作区与结果语义 |
| 音频 | 中文以 FunASR 的 Paraformer + FSMN-VAD + 标点/CAM++ 组合为首轮候选；多语种比较 faster-whisper | whisper.cpp/sherpa-onnx 作轻量部署路线；pyannote 作说话人分段增强 | 新建音频工作区，使用时间轴、转写与片段来源，复用平台资料/任务/成果 |
| 印章 | PaddleOCR 官方印章文字识别流水线，含章区域定位、弯曲文字检测与识别 | OpenCV 预处理/参考章对照；百度私有化方案作商用参照 | 先扩展 ClearOCR，再把单位名称/编号等结构化结果交给 ClearData 核对 |

上述“主路线”是下一轮 PoC 的优先级，不表示模型已备齐、已通过 Windows 推理或已完成业务准确率验收。图像深度模型尤其仍有授权和旧环境适配工作。

建议保留现有四个入口，先把篡改和印章能力放入对应工作台；人脸和音频成熟后可增加两个入口。能力分成四个调研方向，并不意味着必须增加四个独立应用。

## 2. 业务能力需要怎样拆分

| 用户说的方向 | 可落地的子能力 | 必须区别的结果 |
|---|---|---|
| 图像篡改 | 复制粘贴、拼接/修补、压缩/噪声异常、文档文字改写、局部生成内容、换脸/深伪 | 图像级分数、可疑区域、异常类型、来源凭证是不同证据，不能互相替代 |
| 人脸识别 | 找到人脸、质量筛选、1:1 相似性比对、1:N 参考库检索、同一批照片聚类 | 检测到人脸不等于识别身份；静态照片比对不等于活体认证或反深伪 |
| 音频分析 | 解码/波形/频谱、转写、说话人分段、声纹比对、声音事件、合成/重放线索 | 说话人 A/B 是录音内匿名分组，不是已确认的人名；转写不是完整音频真实性鉴定 |
| 印章识别 | 是否有章、位置/形状、章内文字与编码、同一文档多章、参考章辅助对照 | 识别文字、印章图像相似、电子签章验证、物理印章真伪鉴定属于不同任务 |

例如“合同扫描件上的章是不是假的”至少可能指：章中文字与合同主体不同、章图被复制粘贴、盖印形状与参考章不同、PDF 签名不可信。这四种问题需要不同的数据与检查，不能由一个红章检测模型包办。

## 3. 现有四工具的实际接入基础

本次读取现有源码、取证接入记录及内网资源核对记录，得到以下事实：

| 现有工具/基础 | 可以复用 | 新能力仍需要补齐 |
|---|---|---|
| ClearForensics | metadata、noise、frequency、jpeg、jpeg_grid、copy_move 六项经典分析；原图/热图、固定哈希、任务、人工说明和报告 | 深度模型适配、输出热图的语义、模型/阈值版本、文档文字篡改的独立样本 |
| ClearOCR | 文档/图片、页坐标、识别与校对、导出；已有 Paddle 等独立引擎环境 | 印章专用模型及字典/后处理、章区域与原页映射、多章结果、章内文字人工校正 |
| ClearClassify | 图片导入、缩略图、标签、批处理、结果复核和模型记录 | 人脸对齐、特征向量、参考库和相似性阈值；类别分类器不能直接替代身份比对模型 |
| ClearData | 文本/表格清洗、差异比较、来源与导出 | 将印章主体/编号或核准的人脸、音频结果作为明确结构化输入 |
| 平台公共层 | 资料固定原件、项目、任务、成果、来源与版本 | 音频片段的时间范围、转写修订和播放定位；新工具的安装/可用性/服务生命周期 |

具体接入不是“放一个 Python 文件就自动出现”。当前 `catalog/registry.py` 的 `KNOWN_APPS` 只有 `classification` 与 `ocr`，Data/Forensics 使用平台内工作台；扩展原生服务需调整登记、契约、服务启动、导航及成果类型。现有来源锚点的 `kind` 包含 file/page/table/cell/row/region，没有音频时间段类型，音频需要补充时间语义。

当前取证环境中发现 `opencv_python-5.0.0.93.dist-info`，仅确认了安装元数据，没有新增库加载测试。OpenCV Zoo 最新 YuNet 的动态输入模型明确面向 OpenCV 5.x ONNX Runtime 引擎，不能不核对后端就替换旧版模型。

### 4.2 权威评测与技术限制

[NIST OpenMFC](https://mfc.nist.gov/) 是图像/视频篡改检测与定位的评测参考，不是下载后即可部署的检测模型；当前网页显示该轮评测已结束，数据需要登记与许可。适合借鉴受控数据、多种处理与精度/鲁棒性分开评价的方法。

公开数据集上的分数不能直接推广到本项目的手机屏拍、合同扫描、重存 JPEG 或企业票据。应分别测干净原图、正常压缩/缩放/扫描、复制粘贴、改字/改数字、生成式修补，并保留大量正常图片作为负例。主要指标包括正常图片误报率、图像级检测召回与区域定位质量；单看篡改图片的像素 F1 容易遗漏业务误报。

IMDL-BenCo README 还提示过图像级指标计算 bug 与 CAT-Protocol 训练集差异，后续应固定已修正版本及完全相同的评测协议，不能拼接不同论文的“最高分”排行。

[C2PA 解释文档](https://c2pa.org/specifications/specifications/2.2/explainer/Explainer.html) 明确区分来源数据的完整性/信任与事实真伪判断。没有凭证不能据此判假，有效凭证也不直接证明被拍摄事件真实。离线验证还要固定信任列表，区分本地签名验证与需要外部凭证/状态获取的检查。

## 5. 人脸：开源与权威参考

### 5.1 候选项目

| 项目 | 可提供的能力 | 许可和部署条件 | 本项目判断 |
|---|---|---|---|
| [OpenCV Zoo：YuNet + SFace](https://github.com/opencv/opencv_zoo) | YuNet 人脸检测和五点关键点；SFace 对齐、特征提取、两图比对 | YuNet 模型目录 MIT，SFace 模型目录 Apache-2.0；ONNX/OpenCV，CPU 可运行 | 首轮优先；较小依赖面，适合有限参考库与手动比对；不能把论文/LFW 分数直接当现场准确率 |
| [InsightFace](https://github.com/deepinsight/insightface) | 检测、对齐、ArcFace 等识别和模型包；当前也有 GUI/服务路线 | 代码 MIT；官方训练数据及由其训练的模型明确仅非商业研究；手动和自动下载均受约束 | 强技术备选；若用于内网业务，应使用明确获准的权重或取得相应授权 |
| [DeepFace](https://github.com/serengil/deepface) | 统一封装多种人脸检测/特征/比对/检索算法 | 框架 MIT；README 明确外部模型/检测器条款会继承；依赖随所选后端扩大 | 快速对照实验好用；不建议为了一个比对功能打包所有模型后端 |
| [dlib](https://github.com/davisking/dlib) | 人脸检测、关键点和特征模型生态 | 代码 BSL-1.0；模型逐项不同，官方特别提示 ibug 300-W 的 68 点模型不可据代码许可直接商用 | 可作经典基线；Windows 编译和具体模型条款使其不优先于 OpenCV 路线 |
| [CompreFace](https://github.com/exadel-inc/CompreFace) | 带管理界面和 REST API 的完整人脸服务，支持验证/检索/检测 | 代码 Apache-2.0，Docker 部署，多服务/数据库；模型许可仍需独立检查；本次仓库元数据最后推送为 2024-10-05 | 更适合作为参考库、接口和管理交互竞品；对 Windows 便携包，部署面偏大，维护节奏需评估 |

轻量模型体积可以给出较可靠的参考：官方 Git LFS 指针列出 SFace 2021dec ONNX 为 38,696,353 字节，YuNet 2023mar 为 232,589 字节，2026may 为 229,738 字节，合计约 37.1 MiB 的模型量级。这里只读取了 LFS 文本指针，没有下载 ONNX；这不包含 OpenCV、Python、DLL、参考库和派生产物。

模型版本需与后端匹配：Zoo 当前默认 YuNet 2026may 为动态 H/W，文档针对 OpenCV 5.x ONNX Runtime engine；2023mar 为固定形状。当前项目虽有 OpenCV 5 安装元数据，仍要验证实际 `FaceDetectorYN`/`FaceRecognizerSF` 与引擎配置，不能只按版本号推断能用。

### 5.2 权威评价方法与产品范围

[NIST FRTE 1:1](https://pages.nist.gov/frvt/html/frvt11.html) 报告的是在指定 FMR 阈值下的 FNMR，不是一个通用“识别准确率”；[1:N](https://pages.nist.gov/frvt/html/frvt1N.html) 与[人口差异](https://pages.nist.gov/frvt/html/frvt_demographics.html)、[PAD](https://pages.nist.gov/frvt/html/frvt_pad.html) 也各有独立任务。被算法论文引用、某 SDK 声称参加 NIST，并不证明我们最终打包的版本经过相同认证。

首版建议范围是导入照片 → 检出/选择人脸 → 两图比对或限定参考库 Top-K → 人工核对与导出。显示原始相似性分数、当前阈值及“未找到可信候选/图像质量不足”；不将余弦分数直接显示为“同一个人的概率”。参考库增大时误匹配机会也增加，需要独立校准 1:N 阈值。

先做静态业务照片，暂不把门禁摄像头、活体、年龄/性别/情绪分析混进身份比对首版。身份库和标签也应与普通图像分类项目分开建模，保留来源、导出/删除和访问控制。

| [AASIST](https://github.com/clovaai/aasist) / [ASVspoof 2021](https://github.com/asvspoof-challenge/2021) | 合成/转换/重放语音研究与评测基线 | AASIST 代码 MIT，指定权重和训练/测试数据仍须分别核对；不同攻击任务/年份协议不同 | 音频反伪专项，后于基础工作区；不能据合成检测分数声称识别所有剪辑/拼接 |
| [WhisperX](https://github.com/m-bain/whisperX) | 转写、强制对齐和说话人分段的组合 | 代码 BSD-2-Clause，但对齐模型、pyannote 与其他依赖不自动继承该许可 | 借鉴时间对齐设计；不因“集成方便”打包全部模型 |

FunASR 当前 MODEL_LICENSE 有署名、行为约束与版本更新条款，属于需要固定文本核对的自定义模型协议。它不等同于“仅研究可用”，也不应简化写成 Apache-2.0。具体 checkpoint 的模型卡与随模型文件要一一对应，遇到声明冲突须澄清后再随包。

### 6.2 目标机器与首版界面

Whisper 官方 README 的原版推理显存参考为 small 约 2GB、medium 约 5GB、large 约 10GB、turbo 约 6GB；不是 faster-whisper、批量分段或 A4000/A6000 的实测结果。A4000 可作为中等规模单任务的评估目标，但不能据 16GB 总显存承诺与已有 OCR 大模型并发；A6000 也需要实际峰值和耗时记录。

建议界面采用“文件列表 + 波形/频谱与时间轴 + 对齐转写/说话人 + 片段检查”的结构。支持原音播放、句段点击定位、修订记录、TXT/SRT/VTT/JSON 与片段清单导出。时间范围应可回到原件，并记录原始采样率、声道、重采样/拼接偏移；不能把降噪后的音频直接覆盖原件。

转写评测要独立统计 CER/WER 与金额、日期、姓名命中；分段测 DER、重叠说话和长录音漂移；声纹测误接受/误拒绝及 EER/minDCF；反伪按具体协议测 EER、min t-DCF 等及跨编码/跨设备泛化。降噪后“更清楚”不等于内容更真实，模型情绪标签也不能推断说谎或主观意图。

### 7.2 推荐业务流程

整页导入 → 检测多个章区域 → 识别章内文字/编号 → 人工修正 → 提取主体名称/章类别/编号 → 与合同主体、供应商主数据或参考章比对 → 导出原页坐标和差异说明。

形状、星标、字距、布局、纹理及参考章叠加可以做辅助对照，但纸张变形、真实盖印压力、扫描/拍摄会引入差异；相同电子章图像被重复使用也不必然意味着伪造，需要结合业务来源。去红章、增强或图像修复只能是派生视图，被不透明印泥覆盖的信息可能无法恢复，应允许显示不可辨认。

若需求是验证 PDF 电子签章，需另行调研 PDF 签名、证书链、时间戳和签名后修改；国内特定电子签章格式/算法也需要对应验证实现。这不属于上述 OCR 模型的能力范围。

## 9. 内网部署与一次性封包的影响

### 9.1 推荐控制新增运行时数量

| 能力组 | 封包策略 | 特别检查 |
|---|---|---|
| 印章 | 优先复用已登记 Paddle 路线，额外装入固定章检测/识别/版面模型 | 现有模型是否真正覆盖章任务；模型配置、字典、前后处理、版本配套 |
| 人脸 | 先验证现有 OpenCV 环境或最小独立 OpenCV/ONNX 服务 | DNN 后端、对齐行为、模型许可、CPU 路径、参考库来源/迁移 |
| 音频 | 选一条主推理路线及一条必要 CPU 路线，隔离于现有 OCR 引擎环境 | 编解码、FFmpeg/PyAV/torchcodec、torch/torchaudio、CT2 与 CUDA/cuDNN DLL |
| 深度取证 | 按选定模型建立独立固定运行时，不升级/降级现有共享环境去兼容旧论文 | NumPy/PyTorch 版本、JPEG/DCT 原生依赖、模型许可、超大图处理 |

建议一次性交付的是“已经选定、许可清晰、可离线验证的能力及必要兜底”，不把所有比较过的研究项目、训练集和未授权权重都塞入默认包。程序、模型、配置、字典、分词器、编解码、运行库、许可证、哈希和离线诊断需要闭合；安装包及模型目录大小须在最终选定文件后实际统计，当前不能给出可靠的新增总包尺寸。

pyannote 的模型访问条件应在外网准备阶段完成，运行时读取本地目录并关闭遥测；Hugging Face/ModelScope 的访问 token 不应成为用户正常运行的必要条件。其他库同样要处理默认联网下载、版本检查和缓存位置。

目标机“557+”按之前登记理解为 NVIDIA 驱动版本，不是 CUDA Toolkit 版本。新方案是否兼容取决于选定运行库与构建；faster-whisper 当前 GPU 路线就要求 CUDA 12/cuDNN 9。已有包中的多套 CUDA/DLL 不能简单合并到一个 PATH。先测 A4000 的单任务峰值，再决定并发与卸载策略；CPU 就绪与 GPU 就绪分别报告。

所有新产物继续只落 F 盘。发行包路径可迁移、在空缓存和断网下启动、不可访问开发目录、模型与字典不会临时下载，是最终封包验收内容。本轮没有执行这些安装/推理验收。

### 9.2 统一结果要求

每个结果保存原件 SHA256、模型/checkpoint 哈希、算法及参数、阈值版本、运行时、实际设备、来源区域/时间段、处理历史和人工修订。文字识别、身份相似、统计异常、深度检测和签名验证应保留各自结果类型；“未执行/不适用/无法判断/无可信候选”也要能表达。

## 11. 资料证据、访问缺口与复核方式
