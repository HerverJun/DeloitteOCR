**OCR 主流模型调研｜2026-09-10**

本调研按工业落地和视觉算法研究两种视角整理，依据官方仓库、模型卡、论文以及公开评测；“主流”指常见工程方案和有代表性的活跃技术路线，并非市场份额排名。本文没有在统一硬件和业务数据集上实际运行这些模型。能力描述来自公开资料，选型建议是结合架构、输出形式和部署条件作出的判断。

目前最值得先建立的认识是：**读出文字、返回文字坐标、还原整页结构、理解文档含义，是四个相关但不同的任务。** 因而不存在对所有 OCR 场景都最好的单一模型。

对多数中文业务，可以从以下候选开始：普通图片、证件文字、工业字符、低延迟识别优先测试 **PP-OCRv6**；复杂 PDF、表格、公式与知识库解析优先对比 **PaddleOCR-VL-1.6、MinerU2.5-Pro、GLM-OCR**；统一文字定位、识别、抽取与翻译可以加入 **HunyuanOCR-1.5**；识别后还需要问答、跨区域理解和业务推理，可以加入 **Qwen3-VL / Qwen3.5**。

PaddleOCR、EasyOCR、docTR、MinerU、Docling 等名称经常被统称为“OCR 模型”，但它们有些是框架或完整系统。比较时应记录实际使用的检测器、识别器、布局模型和后处理配置。例如，PaddleOCR 同时提供 PP-OCR、PP-Structure 和 PaddleOCR-VL，三者的任务范围与计算成本不同；MinerU 软件 3.x 与其使用的 MinerU2.5-Pro 模型也不是同一个版本号。

可以用下面的任务划分理解技术路线：

| 路线 | 典型处理方式 | 主要优势 | 主要代价 |
|---|---|---|---|
| 专用检测与识别 | 找文字框 → 裁剪、校正 → 识别字符 | 速度、坐标、可调试性好；适合针对字体、字符集和拍摄条件优化 | 检测漏字会传递到识别；复杂表格、公式和阅读顺序需要额外模块 |
| 文档专用视觉语言模型 | 整页或区域图像 → 文本、Markdown、HTML、LaTeX 等 | 统一识别文字及结构化元素，减少手写规则 | 长输出解码成本；存在漏段、重复、补字或结构生成错误 |
| 布局与专用 VLM 混合系统 | 全局布局分析 → 区域并行识别 → 阅读顺序与跨页组织 | 高分辨率细节与整页结构兼顾，容易分别优化模块 | 完整系统比单一模型复杂，性能受调度与后处理影响 |
| 通用视觉语言模型 | 图片 + 指令 → 抽取、问答、推理 | 任务灵活，能够结合图像与业务语义 | 原文保真度、字符坐标与成本需要专项评估 |

**工程上优先关注的模型与系统如下。** 参数量用于判断规模，不能直接换算整套服务显存，也不能代替速度测试。M 表示百万参数，B 表示十亿参数。

|---|---|---|---|
| [PP-OCRv6 / PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR) | 2026-06-11 发布；tiny / small / medium 三档，模型组合约 1.5M / 7.7M / 34.5M | 专用检测与识别；单个统一识别模型支持 50 种语言；加强数码显示、点阵、轮胎印字等工业字符。LCNetV4、RepLKFPN 与 LightSVTR 支持轻量部署 | 中文通用读字、场景文字、需要框坐标和吞吐的服务。仅使用 PP-OCR 不等于完整表格或公式解析；需要时接 PP-Structure 或专门模块 |
| [PaddleOCR-VL-1.6](https://huggingface.co/PaddlePaddle/PaddleOCR-VL-1.6) | 2026-05-28 发布；核心 VLM 0.9B | 延续动态分辨率视觉编码器与轻量语言模型路线，配合布局解析；强化表格、中文古籍、生僻字、印章、图表与 spotting。官方提供 Markdown / JSON 文档流程 | 中文与多语言复杂文档、论文、报告、知识库。应分别验证全文完整性和结构正确性；字符级、表格单元格级坐标需求需核对具体管线，PP-StructureV3 提供更细的坐标信息 |
| [MinerU2.5-Pro / MinerU](https://github.com/opendatalab/MinerU) | 当前 README 的 VLM 为 MinerU2.5-Pro-2605-1.2B；软件已进入 3.x | 粗到细解析：先理解全局布局，再读取原始分辨率区域；有 pipeline / VLM / hybrid 路径。长文档处理、公式转 LaTeX、表格转 HTML、阅读顺序和跨页合并较完整 | 批量 PDF、论文、复杂知识库数据生产。比较的是整个解析系统时，要同时记录 backend、effort 和版本。项目目前使用基于 Apache 2.0 附加条件的自定义许可证 |
| [GLM-OCR](https://github.com/zai-org/GLM-OCR) | 核心模型 0.9B；2026 年公开技术报告 | CogViT 视觉编码器 + GLM-0.5B 解码器，采用多 token 预测与强化学习；官方 SDK 用 PP-DocLayout-V3 做布局，再并行识别区域；支持 vLLM、SGLang、Ollama 等 | 文字、公式、复杂表格、代码密集文档。体积与结构解析能力的平衡有吸引力；完整结果依赖布局、识别和格式化流程，不能只比较裸模型单次生成 |
| [HunyuanOCR-1.5](https://github.com/Tencent-Hunyuan/HunyuanOCR) | 2026-07-07 发布；1B 级 | 一个端到端 VLM 统一文档解析、文本定位识别、信息抽取、文字图像翻译和多图理解；加入 DFlash 推测解码加速，提供 llama.cpp 部署路线；加强古文字、低资源语种等任务 | 希望用一个模型覆盖多类文字视觉任务，或关注长结构输出速度。加速收益取决于输入与推理后端；适用腾讯混元社区许可证。旧 HunyuanOCR 榜单分数不能当作 1.5 的分数 |
| [DeepSeek-OCR 2](https://github.com/deepseek-ai/DeepSeek-OCR-2) | 2026 年 1 月论文；约 3B | DeepEncoder V2 根据图像语义组织视觉 token 的顺序，研究 Visual Causal Flow；支持动态分辨率、整页 Markdown 与纯文字输出 | 视觉编码压缩、阅读顺序建模研究及文档转文本。技术创新与通用业务最优是不同判断；对于表格完整性、密集小字和逐字保真仍需实测 |
| [dots.ocr → dots.mocr](https://huggingface.co/rednote-hilab/dots.mocr) | 2026-03-19 官方宣布 dots.ocr-1.5 更名 dots.mocr；约 3B | 多语言文档解析、定位、识别、语义理解与对话；将图表、UI、科学插图等结构图转换为 SVG，另有 dots.mocr-svg 变体 | 多语种文档及“文字 + 结构图形”解析。SVG 重建应检查几何与语义两类误差；官方明确 3B 容量在部分任务上仍有限制。早期 dots.ocr 的“1.7B”常指语言模型部分，不能直接与总参数量混用 |
| [Surya](https://github.com/datalab-to/surya) | 当前 README 为约 650M 的文档 VLM，文中称 Surya 2 | OCR、布局、阅读顺序和表格结构共享模型，另有小型检测及 OCR 错误检测模型；官方在 91 语言内部测试集上评测 | 文档 OCR、需要布局和表格结果的本地管线。项目明确自然场景照片不是主要目标；代码与权重许可证不同，权重商业使用有条件限制 |
| [olmOCR 2](https://github.com/allenai/olmocr) | 当前推荐 olmOCR-2-7B-1025-FP8 | 面向大规模 PDF 数据转文本；提供训练、评测、批量任务、S3 多节点协调和失败重试；结合合成数据与强化学习 | 大规模语料构建、英文及学术文档候选。需要较多 GPU 资源；官方本地 GPU 配置至少 12GB 显存；中文及其他语种应另测，不能用其英文文档评测外推 |
| [GOT-OCR 2.0](https://arxiv.org/abs/2409.01704) | 580M；2024 年发布 | 早期统一 OCR 路线的重要代表；同一模型处理文字、公式、表格、图表等“光学符号”，支持区域提示、多裁剪和格式化输出 | 学术复现、理解 OCR 向统一生成模型演进、轻量方案对照。对于 2026 年新建复杂文档项目，应与最新专用模型一起测试 |
| [Granite-Docling-258M](https://huggingface.co/ibm-granite/granite-docling-258M) | 258M；2025-09-17 发布 | SigLIP2 视觉编码器 + Granite 语言模型，融入 Docling，支持整页与框引导推理、公式和文档元素结构输出 | 重视小模型、Docling 生态及文档结构表示的项目。官方以英文为主，中文、日文与阿拉伯文标为实验支持 |
| [OpenDoc / UniRec](https://github.com/Topdu/OpenOCR) | OpenDoc-0.1B / UniRec-0.1B | 用小规模专用识别模型统一文字、公式与表格；OpenDoc 结合 PP-DocLayoutV2；OpenOCR 同时提供训练、评测与场景 OCR 实现 | 中英文轻量文档解析和算法研究候选；多语言覆盖及生态成熟度需结合项目要求判断 |
| [Qwen3-VL](https://github.com/QwenLM/Qwen3-VL) / [Qwen3.5](https://huggingface.co/Qwen/Qwen3.5-9B) | 多种规模；这里代表通用视觉语言模型路线 | 识别之外支持信息抽取、文档问答、跨区域关联和推理；Qwen3-VL 官方提供 OCR / KIE 示例，Qwen3.5 采用统一视觉语言训练 | 发票字段抽取、票据理解、图文问答、识别后的业务处理。不要把语言覆盖数等同于逐语种 OCR 质量；通用语义能力也不保证原文逐字符保真 |

还可以关注近期文档解析评测中的 **Dolphin-v2、MonkeyOCR-pro、Youtu-Parsing、Qianfan-OCR、FireRed-OCR、Logics-Parsing** 等路线。本次将它们作为扩展候选，没有逐一验证其完整部署链或把它们视为已获广泛工业采用的模型。PaddleOCR 在 2026 年 7 月新增的 HPD-Parsing，则体现了通过并行解码提高文档解析吞吐的研究趋势。[候选与评测来源](https://github.com/opendatalab/OmniDocBench#end-to-end-evaluation)

如果关注的是“视觉算法本身”，还需要认识下面这些基础模型。它们和上表的完整系统处在不同层级。

| 算法 | 负责什么 | 优势和特点 | 主要边界 |
|---|---|---|---|
| [DBNet / DBNet++](https://github.com/MhLiao/DB) | 文本检测 | 基于分割和可微分二值化，检测任意形状文本；DBNet++ 引入自适应多尺度融合；速度与精度平衡好，已被 PaddleOCR、OpenCV 等采用 | 输出文字位置，本身不识别字符；细小、粘连、极低对比度文字需要结合训练数据与后处理调优 |
| [CRAFT](https://github.com/clovaai/CRAFT-pytorch) | 文本检测 | 建模字符区域和字符间连接关系；适合不规则排列文字，是 EasyOCR 的经典检测器 | 字符间连接和阈值影响分组结果；仍需要识别模型 |
| [CRNN + CTC](https://arxiv.org/abs/1507.05717) | 裁剪后的文字行或单词识别 | CNN 提取特征、RNN 建模序列、CTC 对齐字符；训练与部署成熟，适合作为基线 | 对复杂弯曲、遮挡、长距离上下文的建模能力相对有限；不负责整页定位 |
| [SVTR / SVTRv2](https://github.com/Topdu/OpenOCR) | 场景文字识别 | 通过局部和全局视觉特征交互建模文字；SVTRv2 展示了 CTC 路线在不规则文字和效率上的竞争力；有适合工程的实现与训练工具 | 仍是识别模块，需要检测与裁剪；实际结果依赖字符集和训练数据。PP-OCRv6 的 LightSVTR 属于相关设计路线，不等于原样使用完整 SVTRv2 |
| [PARSeq](https://github.com/baudm/parseq) / ABINet | 带语言上下文的文字识别 | PARSeq 用排列语言建模，在共享模型中支持上下文推断与双向修正；ABINet 用视觉与语言分支迭代修正识别 | 上下文对模糊自然词有帮助，但编号、随机串、产品型号必须单独验证，避免向常见词修正 |
| [TrOCR](https://github.com/microsoft/unilm/tree/master/trocr) | 文字行或单词识别 | 预训练图像 Transformer + 文本 Transformer；官方有印刷体、场景文字和英文手写体检查点，微调路线成熟 | 通常先检测并切成文字行；不是把多栏整页直接还原为 Markdown 的解析器。英文手写能力不能直接外推中文手写 |

**Donut、Nougat、LayoutLMv3** 也经常与 OCR 一起出现。Donut 代表直接从图像生成任务结果的 OCR-free 文档理解，Nougat 侧重学术文档转标记文本，LayoutLMv3 通常结合 OCR 文本、位置与图像做理解。它们在技术演进和任务建模上有价值，但不能都当作“通用 OCR 引擎”互换。DocLayout-YOLO、PP-DocLayout 等主要负责布局区域定位，也不等于文字识别器。

成熟工具依然有价值，尤其适合作为部署基线：

| 工具 | 优势 | 使用边界 |
|---|---|---|
| [Tesseract 5](https://github.com/tesseract-ocr/tesseract) | 成熟 C++ / CLI 生态；LSTM 识别；100+ 语言；适合 CPU、离线运行及清晰印刷体；支持文本、TSV、hOCR、可搜索 PDF 等输出 | 对扫描质量、二值化、倾斜校正和版面设置敏感；复杂自然场景、中文手写与表格结构不是其突出强项 |
| [EasyOCR](https://github.com/JaidedAI/EasyOCR) | Python / PyTorch 上手快；80+ 语言；经典 CRAFT + CRNN 流程；返回文本框、文字和置信度，支持 CPU / GPU | 适合快速验证、脚本与多语言基线；不同语言模型并非任意组合；复杂文档结构需要另建流程 |
| [docTR](https://github.com/mindee/doctr) | 检测与识别模块清晰；有 DBNet / FAST、CRNN / PARSeq 等选择；文档对象保留 Page / Block / Line / Word 结构，便于训练和集成 | 它是可组合框架，表现取决于具体架构和词表；不能只用“docTR”这个名字代表一个固定模型或多语言能力 |
| [Docling](https://github.com/docling-project/docling) | 丰富文件格式、统一文档对象、结构化导出、OCR 与 VLM 后端、本地运行及应用生态 | 是文档处理框架；最终 OCR 质量由所选后端和配置决定。Granite-Docling 才是其中一个具体模型 |

对于不希望自行维护推理服务的团队，商业 OCR API 也应纳入候选。[Mistral 官方当前模型目录](https://docs.mistral.ai/models)已列出 **OCR 4.1**；其[文档处理接口](https://docs.mistral.ai/capabilities/document_ai/basic_ocr)支持文字与表格提取、页眉页脚、段落边界框、结构标签和不同粒度的置信度。它的优势是接入便利和结构化接口，代价是调用成本、服务依赖及无法按开源模型方式自行修改权重。API 别名 `mistral-ocr-latest` 会更新，复现时应记录实际返回的模型版本。本次未对商业服务做统一横评。

公开榜单可以缩小候选范围，但必须先看清评测口径。下面摘录的是 **2026-09-10 获取的 OmniDocBench 官方仓库中，明确标记为 v1.6_full 的整页解析表格**，仅展示部分带明确版本的候选，不是所有 OCR 任务的总排名。

| 模型 | 表中规模 | Overall 分数，越高越好 |
|---|---:|---:|
| PaddleOCR-VL-1.6 | 0.9B | 96.34 |
| MinerU2.5-Pro | 1.2B | 95.75 |
| GLM-OCR | 0.9B | 95.22 |
| PaddleOCR-VL-1.5 | 0.9B | 94.93 |
| DeepSeek-OCR 2 | 3B | 90.25 |

[表格及指标定义来源](https://github.com/opendatalab/OmniDocBench#end-to-end-evaluation)。PaddleOCR-VL-1.6 自身模型卡公布 96.33，榜单快照为 96.34；此处按榜单转录，不把不同来源的小数差异解释为能力变化。OmniDocBench 新闻区另有代码版本更新记录，此处使用表格自身的 v1.6_full 标签，避免混淆代码版本、数据版本与模型版本。

该表的 Overall 定义为：`((1 - 文字归一化编辑距离) × 100 + 表格 TEDS + 公式 CDM) / 3`。因此，96.34 不是“每 100 个字有 96.34 个识别正确”，也不是“96.34% 文档完全无误”。阅读顺序误差另列，没有进入这个综合分。

这份榜单还有三个实际限制：第一，它评的是整页文档结构解析，不能据此判断路牌、工业字符或低延迟 CPU OCR；第二，仓库的文字单项表仍列有 PaddleOCR 2.9.1、Surya 0.5.0 等旧版本，不能拿来代表当前版本；第三，不同模型的在线 API、布局前处理、PDF 渲染、后处理、输出 token 限制可能不同。OmniDocBench 由 OpenDataLab 维护，MinerU 也来自这一生态；本调研将这些数字视作公开报告结果，没有独立复现实验。

真正落地时，我建议按需求建立以下首轮测试清单：

| 业务需求 | 首轮候选 | 要重点测什么 |
|---|---|---|
| 中文截图、商品标签、证件文字、工业字符 | PP-OCRv6 medium；资源受限则 small / tiny | 文字检测召回、字符错误率、编号完整匹配、坐标准确性、端到端延迟 |
| 合同、报告、多栏 PDF、RAG 文档解析 | PaddleOCR-VL-1.6、MinerU2.5-Pro、GLM-OCR | 漏段、重复段、阅读顺序、表格单元格关系、公式及跨页连续性 |
| 多语种文字及图形结构解析 | dots.mocr、PaddleOCR-VL；文档场景加入 Surya | 按语言分别测；混排、生僻字、字体覆盖；SVG 则另测图形一致性 |
| 希望统一 OCR、信息抽取、文字翻译 | HunyuanOCR-1.5；Qwen3-VL / Qwen3.5 作理解候选 | 原文与生成字段一致性、字段完整匹配、响应时间及长输出完整性 |
| 英文手写行，自有训练数据 | TrOCR；与通用 OCR、专用文档 VLM 对照 | 按书写者划分测试集，测 CER / WER，避免同一人的样本泄漏到训练和测试两侧 |
| 本地 CPU、清晰印刷体、低维护成本 | PP-OCRv6 tiny / small、Tesseract | 同一机器上的冷启动、批量吞吐、内存与复杂页面退化 |
| 大规模 PDF 语料生产 | MinerU、olmOCR 2；按语种补充 PaddleOCR-VL | 每页总成本、长尾延迟、重试率、坏页处理和全文完整性 |

建议第一轮准备 200–500 张或页有代表性的业务样本，按打印体、手写、扫描、拍照、旋转、表格、公式、小字和语种分层，给其中关键字段和困难页做可靠标注。统一输入分辨率、硬件、批量大小和输出限制；字符准确度用 CER / WER，框用检测指标，表格用 TEDS / 结构正确性，业务字段用 exact match，性能看端到端 P50 / P95 延迟与每页成本。对于金额、身份证号、序列号等字段，“大部分字符正确”往往不够，需要单独计算整字段完全正确率。

原生 PDF 若能正确提取文本层，可以先用文本提取，再对扫描页或异常区域调用 OCR；纯扫描 PDF 才需要整页视觉识别。这个路由选择有时比更换模型更能改善成本和原文保真度。不要在没有检测文本层质量的情况下直接信任已有文本。
